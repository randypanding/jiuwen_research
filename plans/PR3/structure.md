# PDR-001 范式决策记录：Agent Swarm 软件开发范式选型

适用范围：openJiuwen（Agent Core / Agent Studio / JiuwenSwarm Harness）之上的 OPC 型开发 swarm（1 人类 + N agent）。
本记录只决策范式，不决策拓扑、配置与落地。所有后续架构必须以本记录为前提约束。

---

## 0 决策摘要

**采纳「Spec-as-Source 为本体、门禁与事务为物理层」的分层范式。不采纳传统波次-PR 范式作为治理主体，也不采纳纯 StrongDM 式无门禁全丢弃。**

三句话表述：

1. **真值只有一处：spec。** 代码是 spec 在某次采样下的实例。实例的价值在于揭示 spec 的**沉默**（未定义）与**分歧**（歧义），交付只是副产品。
2. **P1 的机械部分全部保留并加强，但被剥夺真值权威。** CI 门禁、PR、波次不再是"流程规范"，而是**准入事务协议 + 机械化 oracle**。它们只回答"能否进入共享世界"，不回答"什么是对的"。
3. **人类退出实现层，前移到契约层。** 人类只在规范 L1（业务意图）与 L2（开发契约）行使权力，L3（实现说明）与代码 diff 不看不批。人类的产出物是规范与判据的第一层定义，不是代码评审吞吐。

一句话理由：**swarm 里生成是并行且廉价的，准入是串行且昂贵的。P1 把人放在准入路径上，其瓶颈随 agent 数量线性恶化且结构性不可消除；P2 把人移出准入路径，其代价（oracle 债、不可再生物、token 成本）全部可通过分级与边界工程化有界化。选择可有界化的失效模式。**

## 1 问题重构：两个"范式"不在同一坐标轴上

把二选一拆成四个可独立决策的轴，是本决策成立的前提。混在一起讨论必然得出"折中"这种无法执行的结论。

| 轴 | 含义 | P1 传统波次 | P2 spec-as-source | 本决策 |
|---|---|---|---|---|
| A 真值载体 | 出现不一致时以谁为准 | 代码 | spec | **spec**（唯一，含"哪些制品被锚定"也由 spec 声明） |
| B 准入权威 | 谁签发"可进入共享世界" | 人类评审 + CI | 机械 oracle + judge | **硬门禁 ∧ 软门禁**，人类仅对 L2 契约行使否决 |
| C 变更单元 | 一次改动的原子粒度 | 补丁 diff | 再生单元 | **再生单元**，粒度由 architect 内部流程裁定 |
| D 收敛机制 | 多路结果如何归一 | 人工合并冲突 | 多实例 + 判别 + spec 收敛 | **实例测量 → spec 收敛 → 单实例准入** |

关键结论：A 与 B 可以分离决策。**"spec 是真值"不等于"没有门禁"；"有 CI 有 PR"不等于"代码是真值"。** 本决策 = A 取 P2、B 取"机械化 P1 + 软门禁"、C 取 P2、D 取 P2。这不是折中，而是**分层**：P2 定义本体论与改进回路，P1 的机械部分降级为执行机构，无真值权威。

## 2 swarm 施加的六条决定性约束

范式选择必须由 swarm 特有的约束推导，而非由"哪个更先进"推导。

**C1 受体带宽是唯一不可并行段。** 生成可 fan-out 到 N，评审不能。P1 的每个 PR 都要求一次人类语义确认，吞吐上界 = 人类阅读速率，与 agent 数量无关。这是 Amdahl 结构，不是流程优化问题。→ 必须把人类移出逐单元准入路径。

**C2 共享可变状态的并发代价是超线性的。** N 个 builder 并发写同一代码库，冲突与语义漂移随耦合面增长；而对 spec 的写是低频、少数写者（spec steward / spec moderator）、可串行、可评审。→ 应把并发写压在**可丢弃的实例空间**，把串行写压在**小而稳的真值空间**。

**C3 上下文经济决定单位成本。** 代码库大且高频变动 → 前缀缓存持续失效、上下文膨胀、模型有效能力下降。spec 小且低频变动 → 可全量入 prompt、可稳定缓存。cartographer 与 refactor 两个角色被单独设立，本身就是"代码侧上下文成本高昂"的证据。→ 以 spec 为主输入的范式在单位成本上占优。

**C4 复利只能沉淀在可被 agent 读取的载体上。** swarm 的长期价值来自记忆与技能累积。代码不承载意图与教训；commit message 与评审意见不是机器可执行的知识。spec + TEAM_MEMORY + 演进技能才是。openJiuwen 的记忆抽象本身就是文档型（MEMORY.md / TEAM_MEMORY.md 四分类）。→ 真值放在 spec 才能让框架的记忆机制真正承载学习。

**C5 熵：补丁累积 vs 再生重置。** 多 agent 增量修补同一模块，会加速局部结构腐化（DRY 破坏、抽象层混乱、死代码）。再生单元的整体重写是一次**熵重置**。swarm 的高吞吐使 P1 的熵累积速率超过人类重构速率。→ 需要把"重写"作为常规操作而非例外。

**C6 只有多实例并行才产生"spec 熵"这个可观测量。** 单线程范式无法区分"实现错了"与"spec 没说清"。N 份同源实例的通过/失败分布与行为差分，是 spec 质量的**唯一直接测量仪器**。这一条最关键：**swarm + P1 只是把人换成 agent，瓶颈仍在人；swarm + P2 才让并行性产出信息而不仅是吞吐。** 二者是互补的——选 P2 是为了让 swarm 的并行度有除吞吐以外的第二种回报。

## 3 两范式在 swarm 下的失效模式对照

| | P1 的失效 | 是否可有界化 |
|---|---|---|
| F1 | 人审带宽封顶吞吐 | **不可**。结构性 |
| F2 | 并发合并冲突与语义漂移 | 部分（加锁/串行化，但等于放弃并行） |
| F3 | 意图丢失，每 session 从代码重新推断 | 不可（需引入 spec，即滑向 P2） |
| F4 | 正确性实际仍靠测试承担（人审对 LLM 代码的检出率低） | 不可（则 oracle 投资无法省，却拿不到 P2 收益） |
| F5 | 熵累积快于重构 | 部分 |
| F6 | 多路差异被当作冲突噪声抹平 | 不可（丢失 C6 的仪器） |

| | P2 的失效 | 有界化手段 |
|---|---|---|
| G1 | oracle 债：没有强判据就等于没有门 | **可**：任何门必须有硬门禁；无机械见证的条款降级为 advisory，不得放行 |
| G2 | 不可再生制品（迁移、公开 API、协议、持久数据、基础设施状态） | **可**：可再生性分级 R0–R3，把不可再生物显式排除在丢弃语义外 |
| G3 | 再生非确定性伤害逐行语义敏感代码 | **可**：R3 冻结级 + 黄金输出 + 差分测试 |
| G4 | brownfield 冷启动：既有代码含无人写下的行为 | **可**：迁移梯度，spec 收割阶段先于丢弃阶段 |
| G5 | token 成本 | **可**：N 自适应，fan-out 是按不确定度触发的测量而非常量 |
| G6 | 实现不可人类审计 | **可**：审计上移到 L2 契约 + 证据收据，接受"实现不可审计"为显式代价 |

**判据即结论**：P2 的失效全部可以用"分级 + 边界 + 显式代价"限定在已知范围内；P1 的核心失效（F1/F3/F4/F6）在 swarm 下无界。故选 P2 作为本体。

## 4 决策：分层范式与严格优先序

```
第0层 宪法（不可协商不变量，固定化自然语言，会话内不可变）
        ↓ 授权
第1层 规范 Spec（唯一真值）
        L1 业务意图      人类定义、人类批准
        L2 开发契约      人类看 diff、可否决
        L3 实现说明      机器所有，人类不看不批
        ↓ 派生
第2层 判据 Oracle（场景 holdout + 机械见证 + judge rubric）  ← architect 产出
        ↓ 约束
第3层 实例 Instance（代码，可丢弃）                          ← 临时 builder fan-out 产出
        ↓ 准入事务
第4层 世界 World（已准入代码库、制品、运行环境）
```

**优先序（冲突裁决规则，不可绕过）**

1. 宪法 > spec > oracle > 实例 > 世界。任何下层与上层冲突，改下层；若确信上层有误，只能走"案例 → 规则变更提案 → 人类批准 → 新 session 生效"通道。
2. `准入 = 硬门禁通过 ∧ 软门禁通过`。硬门禁不过，软门禁通过无效；硬门禁过，软门禁不过也不准入。软门禁是**单调否决器**，永不救场。
3. 代码与 spec 不一致 = **spec 漂移事件**，默认判定为缺陷并阻断，不得默认"代码即事实"。例外须由 spec 显式声明该制品为锚定/冻结级。
4. 世界的既有行为不构成真值。它构成**约束**（兼容性），且该约束必须被写回 spec 才生效。

## 5 可再生性分级与"准入相变"

"代码可丢弃"必须被精确化，否则范式在第一次数据库迁移时崩掉。

| 级 | 名称 | 语义 | 允许操作 | 人类接口 |
|---|---|---|---|---|
| R0 | 一次性实例 | 完全由 spec-delta 派生，无外部消费者 | fan-out 再生、整体丢弃、refactor 重写 | 无（仅健康度统计） |
| R1 | 锚定制品 | 已准入且有内部消费者 | 可再生，但须先派生 spec-delta；再生后必须过契约面兼容门 | L2 契约 diff |
| R2 | 契约制品 | 有外部消费者（公开 API、协议、事件格式、CLI 面） | 只能演进不能重写；破坏性变更须显式版本化 | L2 契约 diff + 显式批准 |
| R3 | 冻结制品 | 状态型/不可幂等（迁移、持久数据、密钥、基础设施状态）、逐行语义敏感（加密、金额、并发原语） | 禁止 fan-out 与丢弃；仅前向追加；黄金输出锁定 | 显式批准 |

**准入相变（本范式的核心机制）**：
> **实例在准入前是"权重"，准入后是"状态"。**
> 准入前：无历史、无消费者、可任意丢弃与重采样，行为差异是测量信号。
> 准入后：进入世界，携带未被 spec 覆盖的行为，可能已被依赖。此后任何再生都必须经过 `spec-delta 派生 → 契约兼容门 → 差分门`。

R 级由 spec 声明，不由 agent 自行判断。**这保证了"存在例外"本身仍在单一真值内，不破坏 A 轴的唯一性。**

## 6 实例作为测量仪器：沉默与分歧的判别

这是 P2 相对 P1 的净增能力，必须仪器化，不能停留在隐喻。

**测量设置**：同一 spec-delta、同一 oracle、同一 R 级、同一接口冻结面，生成 N 份独立实例（builder 之间无通信，禁止共享中间产物）。

| 观测 | 判定 | 处置归属 |
|---|---|---|
| 全部通过 且 实例间差分为空（在 oracle 与随机差分输入上行为等价） | **spec 相对 oracle 已闭合** | 按次要判据选一实例准入；记录闭合度 |
| 全部通过 但 实例间存在行为差分 | **spec 的沉默**（未定义区被自由填充） | spec moderator 裁定：差异落在"允许自由度"→ 显式登记为 don't-care；落在"应约束"→ 产出 spec-delta |
| 部分通过部分失败 | **spec 歧义（分歧）** | spec moderator 收敛 spec；oracle 不动 |
| 全部失败 → 升级强档模型后成功 | **spec 不够清晰**（对当前档位不可解） | spec 澄清 + 记录档位需求 |
| 全部失败 → 升级后仍失败 | **spec 与 oracle 冲突 / spec 不可实现** | 升级为规范级事件，spec steward + architect 会诊 |
| 实例数 < 3 且已出现失败 | 信息不足 | 补生成至 ≥3 后再判 |

三条必须落进架构的推论：

- **差分测试是一等硬门禁（H5）。** 没有它就无法检出"沉默"，而"沉默"正是 P2 唯一比 P1 更危险的地方（全绿但语义未定）。
- **spec 必须能表达"未定义即自由"。** 否则每次差分都被判缺陷，spec 无限膨胀，退化为伪代码。don't-care 声明区是 spec 的必备结构。
- **N 是自适应测量参数，不是常量。** 触发 fan-out 的是不确定度（新领域、spec 新增条款、历史返工率高、blast radius 大、R 级高）。常规 R0 单元 N=1，另以抽样审计方式周期性跑 N=3 校准 spec 熵。这解决 G5。

## 7 双流水线与信息不对称纪律

范式要求两条目标函数不同的流水线，物理隔离，不得合并。

| | A 交付流水线 | B 标定流水线 |
|---|---|---|
| 目标 | 准入一个实例 | 降低 spec 熵，**全部丢弃代码** |
| 触发 | 波次内的 spec-delta | 不确定度告警、审计抽样、新领域探路、oracle 冲突排查 |
| 产出 | 已准入代码 + 证据收据 | spec-delta、oracle 补强、案例记录 |
| 成功定义 | 门禁全过 | 学到了 spec 的沉默/分歧位置（即使无一实例通过也算成功） |
| 团队 | 交付团队（临时 builder fan-out） | 独立标定团队（同样用临时 builder，但不同 leader、不同记忆域） |

**信息不对称是硬约束，不是礼仪**：

1. **场景 holdout 对 builder 不可见。** builder 只见 spec（L1/L2/L3）+ 接口面 + 本地可跑的自测；端到端场景集与判据 rubric 由 architect 持有、verifier 执行。目的：消除 reward hacking 的信息前提。
2. **生成者不得参与判别。** builder 不进入 verifier / spec moderator / judge 的任何环节；judge 不得评审自身参与生成的实例。
3. **临时 builder 不写任何记忆。** 实现细节只写团队记忆，且须经判别侧同意后写入。理由：可丢弃实例的偶然选择不得污染后续采样的先验。
4. **spec moderator 与 leader 分离，与 architect 分离。** leader 只编排；architect 产出任务划分/DoD/verification；spec moderator 只裁决 spec 收敛。三者上下文互不污染。
5. **judge 模型档位 ≥ builder 档位。** 判别方不得弱于生成方。

## 8 门禁代数

**`Admit(instance) = H(instance) ∧ S(instance)`，H 为硬门禁合取，S 为软门禁合取；两者均为否决型，缺一不可。任何门禁不得只有 S。**

规范条款到机械见证的映射义务：**每条 L1/L2 条款必须绑定 ≥1 个硬见证或 ≥1 个 holdout 场景；否则标记 `unverifiable`，只能作为 advisory 参与软门禁，不得作为放行依据。** 这是"任何门必须有硬门禁"的可执行形式，也是防止 spec 退化为散文的唯一手段。

硬门禁族（H，范式级必需，具体实现留给工程）：

| 代号 | 门 | 守护对象 |
|---|---|---|
| H1 | 构建 / 类型 / 静态分析 | 语法与结构底线 |
| H2 | 单元与属性测试 | 局部行为 |
| H3 | 场景 holdout 套件 | oracle 主体，L1 意图 |
| H4 | 契约面提取 + 破坏性变更检测 | L2 的机械见证，R1/R2 级兼容性 |
| H5 | 实例间差分测试 / 黄金输出 | spec 沉默、R3 逐行语义 |
| H6 | 不变量与运行时护栏（危险操作、依赖策略、许可、沙箱边界） | 宪法的可机械化部分 |
| H7 | spec↔code 漂移检测 | 真值一致性（reconciler 的机械部分） |
| H8 | 成本 / 资源 / 性能预算 | 经济与非功能约束 |

软门禁（S）的范式级约束：由 architect 编写 rubric，verifier 以固定 workflow 执行 LLM-as-judge 最佳实践（多次采样 + 集成、位置与顺序偏置控制、必须引用证据、允许弃权、有标注集做校准、禁止自评）。judge 只输出"否决 + 理由"或"不否决"，**永不输出"豁免硬门禁"**。

## 9 规范三层、波次与 PR 的重定义

**规范三层与人类接口**（已决，此处固定其范式含义）

| 层 | 内容 | 所有者 | 人类动作 |
|---|---|---|---|
| L1 业务意图 | 为什么、给谁、成功是什么 | 人类 | 定义 + 批准 |
| L2 开发契约 | 接口面、数据契约、不变量、DoD、兼容性承诺 | 人类与 architect 共写 | **只看 diff**、可否决 |
| L3 实现说明 | 结构、算法、模块划分、实现约定 | 机器 | 不看不批 |

人类报告面只含：L1/L2 相关事项、deep agent 的改进提案、整体运行健康度评分。**不含代码 diff、不含实例选择、不含 RU 升降档、不含个别例外。**

**波次（wave）的重定义**
P1 里波次是人力排期批次；本范式里波次是 **接口冻结窗口 + 独立可验证的 spec-delta 割集 + 一个准入事务边界**。波次存在的理由从"排期"变为"并行 fan-out 需要稳定的接口地平线"——否则 N 个 builder 会互相竞争彼此的接口。波次划分由 architect（一个集成了 workflow 的 agentic 过程，非单一 agent）从 spec 依赖图上切割。

**PR 的重定义**
PR 不再是"评审请求"，而是 **准入事务 + 证据收据**：包含 spec-delta 引用、R 级、被选实例、被丢弃实例的测量结论、H1–H8 结果、S 的判词与引用、差分结论、漂移检查结果。人类只在 R2/R3 或 L2 契约变更时介入。**保留 PR 的原因不是评审，而是原子性、可回滚、可审计。**

## 10 已决角色是本范式的推论（一致性校验）

范式的自洽检验标准：每个角色应对应范式中的一个必需函数，且信息隔离面与优先序不冲突。校验结果——已决角色集**完备且无冲突**，可直接进入架构设计。

| 角色 | 范式函数 | 层 | 形态 | 隔离要求 |
|---|---|---|---|---|
| leader | 编排、波次推进、事件驱动 | 3–4 | 持久 agent | 不判别、不写 spec；session 内不自演进 |
| architect | 切分波次、DoD、**编写 verification 与 rubric**、裁定再生单元粒度 | 2 | agentic 过程（workflow + agent 集成） | 不在生成团队内；持有 holdout |
| builder | 采样实例 | 3 | **临时 worker fan-out** | 不见 holdout、不写记忆、不参与判别 |
| verifier | **只执行**判据：跑 H 全族，跑 S 的 judge workflow，产出"哪些实例合格且可 diff" | 2–3 | workflow 为主 | 不写判据、不改 spec |
| spec moderator | 由测量结论裁决 spec 收敛：沉默→自由度或补条款；分歧→澄清；并裁定实现细节是否入团队记忆 | 1 | 持久 agent | 与 leader、builder 分离；session 内不自演进 |
| spec steward | spec 分歧的长期维护、条款一致性与版本 | 1 | 持久 agent | 与 leader 分离 |
| reconciler | 制订并执行 spec 漂移守护方案（H7 的策略侧），发现漂移即上报 | 1–4 | agent + 定时/心跳 | 只上报与阻断，不自行改 spec |
| cartographer | 代码定位、检索、CI 失败点定位与初步解释 | 3 | **agent as tool** | 无准入权；弱档位、高缓存命中 |
| critic | 红队攻击 spec 与实例，为 oracle 补场景 | 2 | agent | 不准入；产出进 oracle 而非直接改代码 |
| refactor | 准入后的质量提升后处理（熵重置） | 4 | 独立后处理 | 不得改变契约面，须过 H4/H5 |
| moderator | 代码库可读性治理：wiki、依赖树视角的改善要求 | 4 | agent + 定时 | 产出为 spec-delta 或 refactor 请求，不直接改代码 |
| deep agent（演进） | 监测并提案：模型档位策略、RU 升降档、规则变更、harness 优化 | 0–2 | Rail + 提案器 | **只提案不生效**；生效需人类批准且限于新 session |

三条范式级约束再确认：
- **判别侧（spec moderator / judge）与编排侧（leader）在单次 session 内一律冻结**，不得自我演进。演进只能通过 deep agent 提案 → 人类批准 → 新 session 装载。理由：判据在测量过程中变动，会使所有测量不可比。
- **RU 升降档、例外与异常一律不由人类即时决定**；只在形成后果后作为案例进入规则变更提案。人类只做规范第一层定义与规则批准。
- **cartographer / refactor 单独设立的正当性来自范式**：前者是"代码侧上下文成本"的隔离缓冲（保护主链路缓存命中与上下文纯净），后者是"熵重置"的常规化通道。二者与模型强弱分档天然对应。

## 11 openJiuwen 三层的范式级承载

范式与框架的贴合度是本决策的第三个支撑理由（前两个是 C1 与 C6）。

| 范式要素 | 框架承载 | 说明 |
|---|---|---|
| 可丢弃实例语义 | **JiuwenSwarm 临时团队**（即用即散、只读父记忆、不留痕、"团队即工具"） | 与"builder 临时 fan-out 不写记忆"逐条同构，是框架原生语义 |
| spec 侧学习沉淀 | **持久团队 + TEAM_MEMORY.md（decision/lesson/member/context 四类，仅 Leader 可写、成员只读）** | 与"实现细节只入团队记忆、由判别侧决定写入"同构 |
| 宪法与硬规则 | **Guardrail（事件驱动、分级处置、CRITICAL→AbortError）+ Rails（横切、可叠加、带优先级）** | 宪法的可机械化投影落 H6；不可机械化部分落 judge |
| 硬门禁编排 | **WorkflowAgent / 工作流 IR（确定性流水线）** | 门禁必须确定性，不能由自主 agent 自由决定是否跑 |
| 软门禁 | **verifier 的 judge workflow + IntelliRouter 档位** | rubric 外置、judge 档位可控 |
| 波次事务与续跑 | **Session state 持久化 + Checkpointer + interrupt/InteractiveInput** | 波次 = 事务边界；准入 = 提交点；失败 = 回滚到检查点 |
| 上下文隔离 | **ContextEngine 的 session_id + context_id** | 保证 judge / builder / leader 上下文互不污染 |
| architect 的 agentic 过程 | **DeepAgent 外层 TaskLoop + create_subagent + Workflow 嵌套** | 非单一 agent，符合已决定义 |
| 编排与通信 | **TeamRuntime（Card+Provider、P2P/PubSub、task_* 通配）+ AgentTeams** | 任务+消息+共享工件模型，无显式 handoff——正与"波次 DAG 事件驱动"契合 |
| cartographer as tool | **Agent as Ability / TaskTool** | 天然的 agent-as-tool 形态 |
| 演进受控 | **dev_tools.tune / SkillEvolutionRail（auto_save=False 人工审批）/ Auto Harness 提案** | 框架已把"引擎不自动改写 Agent"设为哲学，与"判别侧 session 内冻结"一致 |
| spec / oracle / DSL-IR | **Studio 的 DSL→IR 编译语义（DSL 可编辑可交换、IR 为执行契约）** | 与本范式"spec 为真值、实例为可执行产物"结构同形，可复用其版本-发布-回滚机制 |
| 单机优先 | 初期 `team.runtime.mode=local` | 分布式（pyzmq + A2X + PG + NFS）留作后期，不进入本期设计 |

框架未覆盖、必须自建的范式件（供后续架构会话）：spec 仓与三层结构、R 级注册表、holdout 场景库与差分测试引擎、证据收据格式、spec 熵与健康度指标体系、规则变更提案通道。Studio 的多智能体（中央路由）不作为 swarm 内核使用。

## 12 迁移梯度（brownfield 不做 flag day）

范式不允许一次切换，但允许阶段推进。每阶段有准入条件，未达标不得进入下一阶段。

| 阶段 | 真值 | 允许的丢弃范围 | 人类介入 | 进阶条件 |
|---|---|---|---|---|
| M0 收割 | 代码（事实上） | 无 | 看 L1/L2 与代码 diff | cartographer + spec steward 完成目标域 spec 收割；H1–H4 建立；漂移检测 H7 上线 |
| M1 锚定 | spec（对已收割域） | R0 单元可丢弃重生 | 只看 L2 diff；抽查 | 目标域场景 holdout 覆盖率达阈值；H5 差分门可用；spec 闭合度稳定 |
| M2 再生 | spec | R0/R1 常规 fan-out 再生 | 只看 L2 diff | 连续若干波次零逃逸缺陷；judge 与标注集校准一致率达阈值 |
| M3 工厂 | spec | R0/R1 默认再生，R2 演进，R3 冻结 | 只看 L1/L2 与健康度 | 稳定运行；deep agent 提案通过率与规则库成熟 |

不得跨阶段：**在 oracle 覆盖率不足的域宣布"代码可丢弃"，等于取消门禁。** 这是本范式唯一的致命误用方式。

## 13 撤退条件与观测指标

范式必须自带失败识别与降级路径，否则不可作为治理决策。

**核心指标（同时构成人类看到的健康度评分成分）**

- spec 闭合度：N-fan-out 中"全通过且差分为空"的比例
- spec 熵：单位 spec-delta 引发的分歧/沉默事件数
- 判据覆盖率：有机械见证的 L1/L2 条款占比；`unverifiable` 条款数
- 逃逸缺陷率：过了 H∧S 但后续被证伪的比例（对 oracle 的直接问责）
- 漂移率：H7 报警密度与修复时延
- judge 校准一致率：与标注集的一致性、弃权率
- 返工率与单位准入成本（token / 时长）

**降级触发（任一命中，该域自动回退一个阶段，并生成规则变更案例）**

1. 逃逸缺陷率超阈值 → oracle 不可信 → 回退到需要人类 L2 之外的额外确认
2. judge 校准一致率跌破阈值 → 软门禁停用（不影响硬门禁）→ 该域暂停自动准入
3. 漂移风暴（H7 报警密度突增且修复时延上升）→ 冻结 fan-out，转 B 标定流水线
4. 单位准入成本超预算且闭合度未改善 → 降低 N、缩小再生单元、提高档位门槛
5. oracle 与 spec 反复冲突（同一条款多次全失败）→ 升级为规范级人类议题

降级永远是**回退阶段**，不是"改判据"。判据的变更只走人类批准的规则通道。

## 14 范式级不变量（宪法·范式章草案，自然语言，供 LLM-as-judge 引用）

以下条款为不可协商不变量，普适表述，不硬编码，作为判别的决策来源。会话内不可变。

1. spec 是唯一真值。代码与运行世界的现状均不构成真值，只构成约束；约束必须写回 spec 才生效。
2. 代码是 spec 的采样实例。实例可以被丢弃，被丢弃的实例仍须留下其测量结论。
3. 任何门禁必须包含机械见证。无机械见证的规范条款只能否决，不能放行。
4. 硬门禁不通过，任何软性判断不得放行；硬门禁通过，软性判断有权否决。
5. 生成者与判别者不得为同一主体，且判别所依赖的判据不得对生成者可见。
6. 判别者与判据在一次会话内不得自我改变。改变只能经提案与人类批准，并自下一会话生效。
7. 人类只对业务意图与开发契约行使权力。实现层不接受也不请求人类裁决。
8. 例外不由现场决定。例外一旦产生后果，作为案例进入规则变更提案，由人类批准后成为未来规则。
9. 多实例行为差异必须被解释：或收敛为规范条款，或显式登记为允许的自由度。不得默认忽略。
10. spec 与代码不一致默认判为缺陷并阻断，除非该制品已被 spec 显式声明为锚定或冻结。
11. 不可再生与逐行语义敏感的制品禁止丢弃与重采样，只允许前向演进。
12. 准入必须是原子的、可回滚的，并附带完整证据收据。
13. 可丢弃主体不得写入长期记忆。记忆写入须由判别侧裁定。
14. 判别方的能力档位不得低于生成方。
15. 当判据不可信时，正确动作是降低自治级别，而非放宽判据。
