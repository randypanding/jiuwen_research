## 二、论文精读总结

### （一）代码检索与代码库寻址（文件一）

#### 近期高相关

### 1. SWE-Pruner: Self-Adaptive Context Pruning for Coding Agents
- 链接：https://arxiv.org/abs/2601.16746
- 总结：针对 coding agent 长交互上下文导致的高 API 成本与高延迟，指出既有压缩方法用固定指标（PPL）忽略代码理解任务特性、常破坏语法/逻辑结构。方法：agent 先形成显式目标（如"聚焦错误处理"）作为提示，再由 0.6B 轻量神经 skimmer 动态选择相关行。关键数据：SWE-Bench Verified 上 token 缩减 23-54% 且成功率不降反升，LongCodeQA 单轮最高 14.84x 压缩。证明"选择性略读"式上下文精简可行且有效，但机制是剪枝而非独立搜索 agent。
- 评分：A
- 理由：采用价值高，直接给出可复用的"任务感知上下文精简"框架与量化收益；回答程度高，直接量化 token 缩减与上下文净化；适应程度高，可嵌入任意 coding agent 作为上下文管理组件。

### 2. FastCode: Fast and Cost-Efficient Code Understanding and Reasoning
- 链接：https://arxiv.org/abs/2603.01012
- 总结：指出仓库级代码推理在"精度 vs 上下文成本"间存在瓶颈，既有 agentic 方法通过低效迭代式全文探索浪费算力。方法：将"仓库探索"与"内容消费"解耦，用结构侦察（structural scouting）在轻量语义-结构地图上导航、追踪依赖并定位目标，由成本感知策略约束的结构感知导航工具在单步优化中构造高价值上下文。关键数据：SWE-QA、LongCodeQA、LOC-BENCH、GitTaskBench 上推理精度超 SOTA 且显著降低 token。与"先侦察后消费"的专用搜索思路完全同构。
- 评分：A
- 理由：采用价值高，"scouting-first + 成本感知策略"可直接借鉴为专用搜索 agent 设计范式；回答程度高，明确报告精度与 token 双指标；适应程度高，结构地图导航可独立成模块服务主 agent。

### 3. One Tool Is Enough (RepoNavigator): RL for Repository-Level LLM Agents
- 链接：https://arxiv.org/abs/2512.20957
- 总结：针对大仓库中定位待修改文件/函数的困难，指出现有方法把它当仓库级检索任务、依赖多个辅助工具且忽略代码执行逻辑。方法：只用单一执行感知工具（跳转到被调用符号定义处），直接从基础预训练模型用 RL 端到端训练。关键数据：7B 超 14B 基线、14B 超 32B、32B 在多数指标上超 GPT-5 等闭源模型。与"确认代码位置"直接相关，证明"单一结构化工具 + 小模型"即可高效定位，但未直接测量 token 成本。
- 评分：B
- 理由：采用价值中高，"单工具 + RL"的极简定位思路有借鉴意义；回答程度中，只回答"定位"未量化成本/上下文收益；适应程度中，作为搜索 agent 的工具设计参考而非现成减成本方案。

### 4. Agent Retrieval Bench: Evaluating Repository Context Retrieval for Coding Agents
- 链接：https://arxiv.org/abs/2607.24882
- 总结：指出 coding agent 通常只按最终 patch 正确性评估，但 patch 依赖更早的"上下文获取"阶段。提出文件级上游检索基准：427 样本、25 仓库、308 个 base-commit 快照、39.2 万文件、790 万 chunk，覆盖 code2test、comment2context、trace2code、edit2ripple 四类正向检索任务及选择性检索子集。关键数据：无单一检索族占优（Qwen3-Embedding-4B 最佳 MRR、RepoMap 在 8K token 预算下最佳上下文产出）；记录轨迹在 27-35% 样本上漏掉全部 gold 文件；检索得到的初始上下文带来更高文件 F1 和更少探索。直接为"检索/上下文获取阶段"提供评测与成本-产出权衡证据。
- 评分：A
- 理由：采用价值高，提供可直接复用的检索阶段评测基准与预算化上下文产出指标；回答程度高，正面评估"检索驱动初始上下文减少探索"这一核心假设；适应程度高，可作为验证专用搜索 agent 收益的评测工具。

### 5. ContextBench: A Benchmark for Context Retrieval in Coding Agents
- 链接：https://arxiv.org/abs/2602.05892
- 总结：指出既有评测只关注最终任务成败，缺乏对 agent 如何检索与使用代码上下文的洞察。提出过程导向上下文检索评测：1,136 个 issue、66 仓库、8 语言，配人工标注 gold contexts，自动评测框架追踪轨迹、度量上下文召回/精度/效率。关键数据：复杂 agent 脚手架在上下文检索上仅带来边际提升；LLM 普遍重召回轻精度；探索到的上下文与被利用的上下文存在显著差距。为"上下文获取阶段"提供中间 gold-context 信号。
- 评分：A
- 理由：采用价值高，提供过程级上下文检索指标与评测框架；回答程度高，直接度量上下文获取的效率与质量差距；适应程度高，gold-context 中间信号可用于训练/评估专用搜索 agent。

### 6. Retrieval-Augmented Code Generation: A Survey (RACG Survey)
- 链接：https://arxiv.org/abs/2510.04905
- 总结：综述检索增强代码生成（RACG），聚焦仓库级方法，把 RACG 刻画为"上下文构造—检索优化—生成—环境交互"的耦合演化过程。用统一分析框架（检索基座、控制机制、评测设置）梳理检索策略、图/非图检索范式、训练驱动优化与自主 agent 架构，讨论可扩展性、可靠性、效率及 RACG 与长上下文 LLM 的"必要性边界"。为研究问题提供领域全景与定位框架，但无原始成本数据。
- 评分：B
- 理由：采用价值中，作为综述提供检索方法谱系与效率讨论框架；回答程度低-中，间接支撑而非直接回答成本/上下文问题；适应程度中，可用于定位专用搜索 agent 在 RACG 版图中的位置。

### 7. InlineCoder: Repository-Level Code Generation via Context Inlining
- 链接：https://arxiv.org/abs/2601.00376
- 总结：指出仓库级代码生成需理解跨函数/类/模块依赖，而既有 RAG 或上下文选择主要靠表面相似度、难以捕捉依赖。方法：把未完成函数内联进其调用图，把仓库级理解重构为更易的函数级任务：先由签名生成草稿"锚点"并做困惑度置信估计，再驱动双向内联（上游内联嵌入调用者捕获多样用法、下游检索把被调用者并入 prompt）。已录用 FSE 2026。与"构造干净上下文"相关，但摘要未给出成本/收益量化。
- 评分：B
- 理由：采用价值中，调用图内联的上下文构造思路可借鉴；回答程度低-中，聚焦生成精度而非 token 成本/上下文洁净；适应程度中，可作为搜索 agent 的上下文构造组件参考。

### 8. ProjAgent: Procedural Similarity Retrieval for Repository-Level Code Generation
- 链接：https://arxiv.org/abs/2607.08691
- 总结：指出现有检索多依赖词法/结构/语义相似度，忽略"过程逻辑相似但标识符/领域不同"的仓库函数。方法：把过程相似性作为显式检索信号，将目标函数分解为中间推理步骤，用 agentic 工作流逐步骤检索过程行为相似的函数，并与常规语义检索整合，另加保守静态分析反馈回路迭代修复。关键数据：REPOCOD 上 41.14% Pass@1，超过既有检索基线。属检索质量维度创新，与成本/上下文洁净无直接量化关联。
- 评分：B
- 理由：采用价值中，过程相似性可作为专用搜索 agent 的检索信号补充；回答程度低-中，回答"搜得更准"而非"花得更少/上下文更净"；适应程度中，可并入搜索 agent 的检索策略。

### 9. StackRepoQA: Benchmarking LLMs on Repository-Level Question Answering
- 链接：https://arxiv.org/abs/2603.26567
- 总结：指出多数基准聚焦孤立函数/单文件片段，忽略真实多文件程序理解。构建首个多项目仓库级 QA 数据集：1,318 个真实开发者问题与采纳答案、134 个 Java 项目；系统评估 Claude 3.5 Sonnet 与 GPT-4o 的直接提示与 agentic 配置，对比文件级检索与基于结构依赖图表示的 RAG。关键数据：基线精度中等，加入结构信号后提升，但仓库级理解整体精度仍有限；高分常来自对 Stack Overflow 答案的逐字复现而非真实推理。为仓库级检索质量提供证据，但未涉及成本。
- 评分：B
- 理由：采用价值中，提供仓库级 QA 检索评测数据与"记忆 vs 推理"警示；回答程度低-中，聚焦检索精度而非成本/上下文；适应程度中，可作搜索 agent 检索质量的评测参考。

### 10. SWE-Explore: Benchmarking How Coding Agents Explore Repositories
- 链接：https://arxiv.org/abs/2606.07297
- 总结：指出 SWE-bench 类基准把任务当作二元成败问题，忽略仓库理解、上下文检索、代码定位、bug 诊断等细粒度能力。提出隔离评测"仓库探索"的基准：给定仓库与 issue，探索器在固定行预算下返回相关代码区域排序列表；覆盖 848 个 issue、10 语言、203 个开源仓库，行级 ground truth 从成功解决同一 issue 的独立 agent 轨迹中蒸馏。关键数据：覆盖/排序/上下文效率指标强相关于下游修复表现；agentic 探索器明显高于经典检索；文件级定位已强，而行级覆盖与高效排序是区分 SOTA 探索器的关键轴。直接量化"探索/搜索能力 + 上下文效率"。
- 评分：A
- 理由：采用价值高，提供探索能力与上下文效率的评测基准及行级 ground truth；回答程度高，正面度量"高效探索"与下游修复的关联；适应程度高，可直接用于评估专用搜索 agent 的定位与效率。

### 11. Deep Agentic Search for Repository-Level Code QA: An Empirical Study
- 链接：https://arxiv.org/abs/2608.01507
- 总结：核心问题正是本研究问题：代码 agent 大量精力花在定位代码上，两种主流方案——语义搜索（预建向量索引检索代码块）与深度 agentic 搜索（规划 agent 把探索委托给独立子 agent、在隔离上下文窗口运行、只返回浓缩结果，以保护主 agent 免受 context pollution/rot）。在 SWE-QA 上实证对比并构建失败模式分类。关键数据：语义搜索正确率 65.2% vs agentic 搜索 46.2%，且每个正确答案成本不到一半；agentic 搜索 41.8% 的失败发生在规划者与子 agent 的交接处，且通常是"流畅自信但错误"的静默失败。结论：对可索引仓库的只读问答，检索更强更便宜，子 agent 隔离的"保护"并非免费。这是对本研究问题最直接的反证数据。
- 评分：A
- 理由：采用价值高，直接对比"子 agent 隔离搜索 vs 检索"的成本与正确性，是必须引用的关键证据；回答程度极高，正面检验"专用搜索 agent 保上下文"假设并给出反例；适应程度高，其失败分类与成本分析可直接指导专用搜索 agent 的架构取舍。

### 12. What Context Does a Coding Agent Actually Need to Act?
- 链接：https://arxiv.org/abs/2607.09691
- 总结：研究 agent 在"编辑"代码那一刻真正需要多少上下文：用 oracle 固定定位（把"找位置"与"行动"分离），只变化代码表示方式，在 SWE-bench Verified 上对照真实 issue 解决。关键数据：信号就在被编辑代码本身——自然语言摘要几乎答不出源码能答的行为问题（4/45 vs 27/45）；周边上下文几乎无关（多文件实例上把文件其余部分渲染为 UML 骨架/签名与直接删除无差异，N=70，McNemar p=0.75）；压缩上下文以 1/3 token 达到整文件效果（解决一个 issue 19K vs 94K token）；温度 0 推理在字节相同运行间翻转约 9% 结果（噪声底）。直接支持"上下文最小化/净化"且给出量化收益。
- 评分：A
- 理由：采用价值高，预注册实验证明压缩上下文 3 倍省 token 无损，可直接支撑"净上下文"设计；回答程度高，正面回答"agent 真正需要什么上下文"；适应程度高，其表示压缩与噪声底结论可直接用于专用搜索 agent 的上下文返回策略。

### 13. SWE-Pruner Pro: The Coder LLM Already Knows What to Prune
- 链接：https://arxiv.org/abs/2607.18213
- 总结：在 SWE-Pruner 基础上发现：agent 自身在读取工具输出时已编码了代码上下文相关性的内部表示，无需外部独立分类器。方法：在 agent 内部直接剪枝工具输出——小 head 把 agent 内部表示转成每行 keep-or-prune 标签，配以按工具输出行数键控的长度感知 embedding。关键数据：两个开源骨干、四个多轮基准上最多节省 39% 的 prompt+completion token 且保持任务质量；MiMo-V2-Flash 上 SWE-Bench Verified 解决率 +3.8%、长上下文 Oolong 精度 +2.2。机制是"agent 内剪枝"而非独立搜索 agent。
- 评分：A
- 理由：采用价值高，证明"利用 agent 内部表示做行级剪枝"可省 39% token 且不损质量；回答程度高，直接量化成本降低与质量保持；适应程度高，可作为专用搜索 agent 返回结果后的净化/压缩组件。

### 14. Do Context Files Help Coding Agents? A Two-Agent Ablation Study

### 49. AutoCodeRover: Autonomous Program Improvement
- 链接：https://arxiv.org/abs/2404.05427
- 总结：将 LLM 与基于 AST 的代码搜索能力结合，专门解决 GitHub issue。核心：LLM 先提取 issue 中的关键词，通过多路代码搜索 API（如 search_method_in_file）迭代检索上下文，利用 AST 程序结构（类/方法级别）而非纯文本文件来定位 bug，并可结合谱系故障定位(SBFL)进一步精炼上下文。在 SWE-bench-lite 上解决率达 19%，超过 SWE-agent，且平均每次任务成本仅 $0.43 USD；平均 4 分钟解决一个 issue，而人类开发者平均需要 2.68 天。
- 评分：A
- 理由：采用价值极高，直接展示了"专用代码搜索 agent"的完整架构（关键词提取→多路 AST 搜索 API→迭代上下文收集→故障定位增强），且成本数据（$0.43/任务）直接支撑"减少 token 花费"论点；回答程度极高，正是研究问题所描述的"专门负责代码搜索的 agent"范式的典型案例；适应程度高，AST 级搜索、迭代式上下文收集、SBFL 辅助定位等均可直接迁移。

### 50. OpenHands: An Open Platform for AI Software Developers as Generalist Agents
- 链接：https://arxiv.org/abs/2407.16741
- 总结：OpenHands（前身 OpenDevin）是一个通用 AI 软件开发者平台，支持 agent 通过写代码、操作命令行、浏览网页来与世界交互。平台支持新 agent 实现、沙箱安全执行、多 agent 协同和评估基准集成，在 SWE-Bench 和 WebArena 等 15 个任务上进行了评估。作为 ICLR 2025 接收论文，社区项目（188+ 贡献者，2100+ commits）。定位为通用平台而非专注于代码搜索的专用 agent。
- 评分：B
- 理由：采用价值中等，平台本身是通用框架，不专门针对代码搜索优化；回答程度中等，间接相关，其多 agent 协同机制和沙箱执行环境可为代码搜索 agent 提供基础设施参考；适应程度中等，可借鉴其 sandboxed 执行环境设计和评估框架，但核心搜索能力未深入。

### 51. A Survey of Context Engineering for Large Language Models
- 链接：https://arxiv.org/abs/2507.13334
- 总结：系统定义"Context Engineering"学科，超越简单 prompt 设计，涵盖上下文检索与生成、上下文处理、上下文管理三大基础组件，以及 RAG、记忆系统、工具集成推理、多 agent 系统等高级实现。调研 1400+ 篇论文，揭示当前模型在理解复杂上下文方面能力很强，但在生成同等复杂的输出方面存在明显不对称。明确提出：上下文工程是系统优化 LLM 信息载荷的学科，直接关系到 token 效率和模型性能。
- 评分：A
- 理由：采用价值高，综述提供了上下文优化的完整理论框架（检索、处理、管理），可直接指导代码搜索 agent 的上下文策略设计；回答程度高，直接回答"如何通过上下文工程减少 token 花费并保持上下文干净"；适应程度高，综述的分类法和设计原则可直接映射到代码搜索场景。

### 52. LLMLingua: Compressing Prompts for Accelerated Inference of LLMs
- 链接：https://arxiv.org/abs/2310.05736
- 总结：提出粗到细的 prompt 压缩方法，包含预算控制器（维持高压缩比下的语义完整性）、token 级迭代压缩算法（建模压缩内容间的相互依赖）、以及基于指令微调的分面对齐方法。在 GSM8K、BBH、ShareGPT、Arxiv-March23 四个数据集上实现最高 20 倍压缩且性能损失极小。被 EMNLP 2023 接收。
- 评分：A
- 理由：采用价值高，20x 压缩率直接解决"减少 token 花费"问题，方法可直接嵌入代码搜索 agent 的上下文管理模块；回答程度高，直接回答"如何减少 token 花费"这一技术问题，压缩后的 prompt 自然保持上下文干净；适应程度高，粗到细的迭代压缩算法可适配到代码上下文的压缩场景。

### 53. Lost in the Middle: How Language Models Use Long Contexts
- 链接：https://arxiv.org/abs/2307.03172
- 总结：经典发现：LLM 在利用长上下文中的相关信息时存在显著的"中部丢失"现象——当相关信息出现在输入上下文开头或结尾时性能最高，出现在中间位置时性能显著下降，即使对于明确支持长上下文的模型也是如此。研究基于多文档问答和键值检索两个任务进行了系统分析，被 TACL 2023 接收。
- 评分：A
- 理由：采用价值高，该发现是"保持上下文干净"这一目标的根本性理论支撑，直接说明长上下文中混入无关信息会严重损害性能；回答程度高，直接回答"为什么需要保持上下文干净"——因为长上下文中部信息会被模型忽略，所以必须通过代码搜索 agent 精确提取必要信息而非塞入大量上下文；适应程度高，该结论可直接作为代码搜索 agent 设计的核心原则。

### 54. A Survey on the Memory Mechanism of LLM-based Agents
- 链接：https://arxiv.org/abs/2404.13501
- 总结：系统梳理 LLM-based agent 的记忆机制，包括"什么是记忆"、"为什么需要记忆"、"如何设计和评估记忆模块"，以及记忆在多种 agent 应用中的重要作用。分类总结记忆的设计模式，建立统一综述框架，并创建持续更新的资源库。覆盖范围较广，不专门针对代码搜索场景。
- 评分：B
- 理由：采用价值中等，综述提供记忆机制的分类框架，但未聚焦代码搜索领域的上下文管理；回答程度中等，记忆机制中的"选择性检索"和"上下文管理"部分与代码搜索 agent 相关，但缺乏具体代码场景分析和成本数据；适应程度中等，其记忆分类法可参考用于代码搜索 agent 的上下文状态管理。

#### 相关但窗口外（可选参考）

### 55. CodeRAG: Finding Relevant and Necessary Knowledge for Retrieval-Augmented Repository-Level Code Completion
- 链接：https://arxiv.org/abs/2509.16112
- 总结：提出专门为仓库级代码补全设计的 RAG 框架，含三大核心组件：(1) 基于 log probability 的检索查询构建——通过探测不同代码块对生成的贡献度，选择最相关的块作为查询；(2) 多路径代码检索——同时使用稀疏检索(TF-IDF)、稠密检索(CodeT5p 编码)和数据流引导检索；(3) Preference-aligned BestFit 重排序——用 LLM reranker 对齐检索结果与代码 LLM 的偏好，并蒸馏为小模型以降低开销。在 ReccEval 和 CCEval 上显著优于 SOTA，被 EMNLP 2025 接收。
- 评分：A
- 理由：采用价值极高，多路径检索、log probability 查询构建、偏好对齐重排序三组件设计直接可复用于代码搜索 agent；回答程度高，直接回答"如何通过精准代码检索减少不必要的上下文"；适应程度高，整个框架就是为"代码搜索"和"上下文精简"而设计，蒸馏小模型做重排序直接服务于"减少 token 花费"。

### 56. Memory for Autonomous LLM Agents: Mechanisms, Evaluation, and Emerging Frontiers
- 链接：https://arxiv.org/abs/2603.07670
- 总结：将 agent 记忆形式化为"write-manage-read"循环，提出三维分类法（时间范围、表征基底、控制策略），考察五种记忆机制族：上下文驻留压缩、检索增强存储、反思性自我改进、分层虚拟上下文、策略学习管理。特别提到 coding agent 作为记忆的关键应用场景，并讨论写路径过滤、矛盾处理、延迟预算等工程问题。覆盖 2022-2026 年初的工作。
- 评分：B
- 理由：采用价值中等，综述中"上下文驻留压缩"和"写路径过滤"直接相关于"减少 token 花费"和"保持上下文干净"，但缺乏代码搜索的具体设计；回答程度中等，其记忆机制分类可为代码搜索 agent 的上下文管理提供设计参考；适应程度中等，可借鉴其"write-path filtering"和"latency budgets"等工程实践，但需进一步适配到代码搜索领域。

### 57. Evaluating Memory in LLM Agents via Incremental Multi-Turn Interactions
- 链接：https://arxiv.org/abs/2507.05257
- 总结：指出当前 LLM agent 基准主要评估推理、规划和执行能力，而记忆能力（准确检索、测试时学习、长程理解、选择性遗忘）被低估。提出 MemoryAgentBench，将长上下文数据集转换为多轮增量格式以模拟 agent 的渐进式信息积累。评估多种 agent，发现现有方法均未完全掌握所有四项记忆能力。
- 评分：B
- 理由：采用价值中等，其"准确检索"和"选择性遗忘"能力与代码搜索 agent 的上下文管理相关，但 MemoryAgentBench 是通用记忆评估而非代码搜索专用；回答程度中等，间接支撑"选择性遗忘"对应"只保留必要的代码上下文"、"准确检索"对应"精确定位代码位置"；适应程度中等，其多轮增量评估范式可用于评估代码搜索 agent 的上下文管理效果，但需领域适配。

## 三、开源项目精读总结

### （一）近期活跃

### 1. code-context (infino-ai)
- 链接：https://github.com/infino-ai/code-context
- 总结：定位为"coding agent 之下的检索层"，对整个仓库建本地索引（关键词 BM25 + 语义 + 混合 + SQL），通过 MCP server 和 CLI 暴露 search/sql/reindex 三个工具，索引以普通文件存放在仓库 .infino/ 目录。基于自家 infino 检索引擎（SQL + 全文 + 向量一体），官方基准声称比"文件工具"少 30-40% token、少 50% 工具调用，聚合类问题省 43% token/71% 调用。提供 Claude Code 插件与多客户端 MCP 配置，Apache-2.0，2026 年 8 月仍高频迭代（77 commits、v0.2.0）。
- 评分：A
- 理由：采用价值高，开箱即用的"专用代码搜索层"且自带可复现的 token/工具调用节省基准，直接可落地；回答程度高，其核心命题就是"用排名索引替代逐文件读源码以减少 token 并保持上下文干净"，与研究问题完全同构；适应程度高，MCP/插件/CLI 三面覆盖 Claude Code、Cursor、Codex、Gemini、Cline 等主流宿主，接入成本低。

### 2. Code Context Engine (CCE)
- 链接：https://github.com/elara-labs/code-context-engine
- 总结：Python 实现的代码库索引引擎，用 tree-sitter 把代码切成语义块（函数/类/模块）并本地向量化，混合向量+BM25（RRF）检索，11 个 MCP 工具（context_search、related_context、session_recall 等），还带跨会话决策记忆、压缩、美元级节省统计。官方在 FastAPI/Django/Express 等仓库上可复现基准声称检索省 94% token（Django 2,347 文件 recall@10=0.95），并自动为 Claude Code/Cursor/VS Code/Gemini/Codex 等多编辑器写配置。MIT，522 commits、v0.4.26，2026 年 8 月仍活跃迭代。
- 评分：A
- 理由：采用价值高，"索引后 AI 搜索而非重读文件"正是研究问题所指的减 token 方案，且有多仓库可复现基准背书；回答程度高，直接回答"专用代码搜索如何减成本/净上下文"，并额外提供会话记忆与压缩层；适应程度高，cce init 一条命令自动配置 8+ 编辑器/宿主，落地门槛极低。

### 3. Continue.dev
- 链接：https://github.com/continuedev/continue
- 总结：开源 coding agent（CLI + VS Code 扩展 + JetBrains 插件），Apache-2.0，曾是领先的开源 AI 编程助手，2.0.0 为最终版本（移除遥测、去掉登录）。仓库已明确标注"不再积极维护、对所有用户只读"。本身是 agent 宿主而非代码搜索层，历史上虽有代码库索引/检索相关能力，但当前定位是完整的编码 agent 产品。
- 评分：C
- 理由：采用价值低，项目已停止维护（read-only），作为可落地依赖风险高；回答程度低，它是"被搜索层服务的宿主"而非"搜索层本身"，不直接支撑研究命题；适应程度低，若仅作为宿主参考其 MCP/检索集成模式价值有限，且官方已建议转向其他方案。

### 4. ast-grep
- 链接：https://github.com/ast-grep/ast-grep
- 总结：基于 tree-sitter 的结构化代码搜索/静态分析/重写 CLI（sg），用"像普通代码的 pattern"匹配 AST 节点而非文本，支持 $MATCH 通配、YAML lint 规则、jQuery 式 AST 遍历、多核并行。Rust 编写、MIT，4,299 commits，长期活跃。解决的是"按语法结构定位/改写代码"这一精确检索问题。
- 评分：B
- 理由：采用价值中，作为结构化搜索/符号定位的基础组件可被搜索 agent 调用，但非完整检索层，需自行封装；回答程度中，只覆盖"精确结构定位"子问题，不含语义/排名/上下文精简，对减 token 贡献有限；适应程度中，CLI 易被 agent 以工具方式调用，但无 MCP/插件一等公民集成，需二次适配。

### 5. ripgrep
- 链接：https://github.com/BurntSushi/ripgrep
- 总结：Rust 编写的极速递归正则搜索工具（rg），默认尊重 .gitignore、跳过隐藏/二进制文件，支持类型过滤、多行、PCRE2、压缩文件搜索等，性能大幅领先 grep/ag/ack（Linux 内核树搜索 0.082s）。MIT/Unlicense 双许可，2,216 commits，维护极活跃。是当前所有 coding agent 默认的基线检索工具。
- 评分：B
- 理由：采用价值中，作为"精确文本定位"的基线工具与搜索 agent 的兜底/校验层，成熟可靠，但无语义与排名能力；回答程度中，只解决"已知文本找位置"，不解决"按语义找代码/聚合统计"，对减 token 帮助有限（且其输出本身常被整段塞进上下文）；适应程度高，CLI 即插即用，是搜索 agent 最易集成的底层依赖之一。

### 6. tree-sitter
- 链接：https://github.com/tree-sitter/tree-sitter
- 总结：解析器生成器 + 增量解析库，为任意语言构建具体语法树并随编辑高效更新，纯 C 运行时、无依赖、可内嵌，支持 Rust/Wasm 绑定，v0.26.9，6,339 commits，生态极活跃。是几乎所有 AST 型代码搜索项目（CCE、codebase-memory-mcp、cocoindex-code、semcode、codebase-index、ast-grep 等）的底层解析基石。
- 评分：B
- 理由：采用价值中，作为"按语义切块/提取符号"的基础设施被广泛复用，但本身不提供检索、排名或 agent 接口；回答程度中，支撑代码搜索的实现而非直接实现搜索，对减 token 是间接贡献；适应程度高，作为库嵌入度高，适合自研搜索 agent 时作为解析层选型。

### 7. universal-ctags
- 链接：https://github.com/universal-ctags/ctags
- 总结：Exuberant Ctags 的延续维护版，为源码中的语言对象（函数/类/宏等）生成索引/tag 文件，支持大量语言、optlib 自定义解析器、交互模式，是编辑器/工具做符号定位的传统方案。GPL-2.0，11,738 commits，v6.2.1（2025-10），持续活跃。
- 评分：B
- 理由：采用价值中，可作符号索引/定义定位的轻量组件，但输出为 tags 文件，需自行转成 agent 可用的检索接口；回答程度中，仅覆盖"符号名→位置"这一窄子问题，无语义/排名/上下文精简；适应程度中，CLI 成熟易集成，但与现代 MCP/向量检索栈相比属传统基础设施，适配成本中等。

### 8. SWE-agent
- 链接：https://github.com/SWE-agent/SWE-agent
- 总结：普林斯顿/斯坦福团队的开源 agent-计算机接口框架，让 LLM 自主使用工具修复真实 GitHub issue、找漏洞或执行自定义任务，曾在 SWE-bench 上达开源 SOTA，MIT，2,182 commits。官方已声明主要开发转向更简单的 mini-swe-agent（100 行 Python 达 65% SWE-bench verified），本仓库被后者取代。
- 评分：C
- 理由：采用价值低，它是"被搜索层服务的编码 agent 框架"而非搜索层本身，且已被 mini-swe-agent 取代，落地价值下降；回答程度低，不直接实现代码搜索/减 token 机制，仅作为宿主背景参考；适应程度低，若要复用其工具/接口设计需迁移到新项目，适配成本高。

### 9. Cline
- 链接：https://github.com/cline/cline
- 总结：开源编码 agent，覆盖 VS Code 扩展、CLI、JetBrains 插件、桌面端与 Kanban 多 agent 任务板，支持 Plan/Act 模式、规则与 skills、任意模型（Anthropic/OpenAI/Gemini/OpenRouter/Ollama 等）、MCP 服务器与插件（SDK @cline/sdk）、多 agent 团队与定时任务。Apache-2.0，6,940 commits、360 releases，2026 年 8 月仍高频迭代，社区规模大。
- 评分：B
- 理由：采用价值中，作为"宿主"它原生支持 MCP/插件，是专用代码搜索 agent 的理想挂载点，但自身不提供搜索层；回答程度中，不直接回答减 token 命题，但提供承载该方案的集成面（MCP/技能/规则）；适应程度高，接入搜索层（如 code-context、CCE 等 MCP server）零障碍，作为宿主适配度很高。

### 10. Codex CLI
- 链接：https://github.com/openai/codex
- 总结：OpenAI 的本地运行编码 agent（Rust 编写，Apache-2.0），支持 ChatGPT 账号登录或 API key，提供 CLI/IDE/桌面多形态，内置沙箱执行、MCP 客户端、AGENTS.md 等。9,263 commits、986 releases，v0.147.0（2026-08），极其活跃。是典型的"宿主"型 agent，通过 ~/.codex/config.toml 的 mcp_servers 可挂载外部代码搜索服务。
- 评分：B
- 理由：采用价值中，作为宿主可稳定挂载专用代码搜索 MCP（CCE、code-context、semantex 等都专门为其写了配置），但本身不提供搜索层；回答程度中，不直接实现减 token 机制，仅提供集成入口；适应程度高，MCP 生态支持完善，作为目标宿主适配度高。

## 四、关键提示（供下一步分析参考）

1. **最直接的正反证据**：正面——SHERLOC（专用定位 agent +5.95pp、总 token -23.1%）、LocAgent（定位成本降 86%）、FastContext（探索子 agent token -60%，已撤回）、CodeNib（省 50-87% token）、ContextSniper（省 51.5% token）；反面——Deep Agentic Search（子 agent 隔离搜索更贵更差、41.8% 交接失败）、Token Reduction Is Not Cost Reduction（token 减少≠成本减少，prompt-cache 占账单 87%）。
2. **落地工具首选**：A 级且活跃的 MCP 搜索服务器——code-context、CCE、codebase-memory-mcp、cocoindex-code、flupkede/codesearch、codebase-index、semantex；宿主——Cline、Codex CLI、OpenHands。
3. **设计约束**：评估"专用代码搜索 agent"收益时应使用"成功调整后的计费成本"而非 token 数；注意子 agent 交接失败模式；对可索引仓库的只读问答，向量检索可能优于子 agent 隔离搜索。
4. **评分分布**：论文 A 33 / B 21 / C 3；项目 A 11 / B 11 / C 4。A 级集中于"检索/定位/剪枝/上下文精简"直接相关方向。
