## 二、R2.2 上游网关吞并风险

### 2.1 LiteLLM（重点）

- **来源/Star**：https://github.com/BerriAI/litellm ；约 55,000 star（`dev.to/moksh` 网关对比文 2026-08，C/短）；YC W23 BerriAI｜ A/短
- **许可**：MIT（SDK 主仓）｜ A/长
- **model_prices_and_context_window.json 约束（任务重点核验项）**：
  - **启动时单次 fetch + 超时**：「By default the proxy fetches the latest map from GitHub at startup…」（`docs.litellm.ai/docs/proxy/custom_model_cost_map`，A）
  - **5 秒超时**：「The map is fetched once at startup with a 5 second timeout」（同上，A）
  - **条目数与覆盖率校验**：「the fetched map must contain at least 50 model entries and at least half as many entries as the bundled backup, or LiteLLM discards it. Both thresholds are tunable via MODEL_COST_MAP_MIN_MODEL_COUNT and MODEL_COST_MAP_MAX_SHRINK_RATIO」（同上，A）
  - **第二数据源钩子**：`LITELLM_MODEL_COST_MAP_URL`（HTTP(S)，不支持 file://）；离线用 `LITELLM_LOCAL_MODEL_COST_MAP=True` 走内置 backup 文件；另有**逐 deployment 价格覆盖**（litellm_params 内 `input_cost_per_token` 等，覆盖即脱离默认表，不回落混合计费）｜ A/长
  - **CI 校验**：仓库自带 GitHub Action `test-model-map.yaml`「Validate model_prices_and_context_window.json」，2,500+ 次运行（A）——即官方用 CI 保证价格覆盖与条数。
  - 典型失败模式：某新模型未入表 → `/v1/model/info` 返回 null 定价、用量记 $0（`litellm PR #36496` 描述，A）
- **是否已有 subscription/quota/entitlement 建模**：**是，且相当完整**：
  - Virtual Keys（`/key/generate`）带 `max_budget`、`budget_duration`（30s/30m/30h/30d 滚动重置）、`rpm_limit`/`tpm_limit`、`soft_budget`、`temp_budget_increase`（`docs.litellm.ai/docs/proxy/users`，A）
  - 预算分层：personal/user、team（`/team/new` max_budget/budget_duration）、team-member（`max_budget_in_team`）、agent（迭代数/美元预算）｜ A/中
  - `/key/info` 返回实时 spend；成本用自身 model cost map 计算美元｜ A/中
  - 注意：这是「**自身 proxy 过账的美元预算**」，是对充值/预付费 key 的额度，**不是跨厂商订阅承诺额度、也不是 Cursor/Copilot 这类编辑器的 included 池**；对我们的「订阅额度度量」不构成直接替代，但构成**功能重叠面**。
- **插件/callback 扩展点稳定性**：事件/callback 体系成熟（guardrails、spend tracking 事件、Custom callback 列表），2026-08 持续大量 PR（如 #36496 dashscope 成本表）｜ A/短
- **维护者对外部数据源态度**：「Prefer the per-deployment override… or replace the whole map with your own hosted copy」，官方默认采用**自维护一份大且全的官方价格表 + 放开自定义 URL/覆盖**；对第三方数据源是「可替换但非默认集成」| A/长。

### 2.2 new-api（QuantumNous）& one-api（songquanpeng）

- **来源/许可**：`github.com/QuantumNous/new-api`（AGPL-3.0，v0.10.7 2026-02，`pkg.go.dev`，A）；`github.com/songquanpeng/one-api`（MIT）｜ A/长
- **额度/计量建模**：三级（用户-令牌-渠道）+ 分组倍率/模型倍率：
  - 「额度 = 分组倍率 × 模型倍率 ×（提示 token 数 + 补全 token 数 × 补全倍率）」（`new-api-docs faq.md`，A）
  - 令牌额度与账户额度分离：令牌设最大使用量限制，账户为总池（同上，A）
  - 兑换码充值（`controller/redemption.go`）、EPay/Stripe 在线充值、按次计费（`new-api README`，A/中）
- **外部位（entitlement）**：**无 registry 化跨厂商订阅额度**；它计量的是「通过本网关的 API 调用」，与 Cursor/Copilot 的 included 池/订阅承诺是两套体系。是**「通道内额度」而非「厂商订阅额度」**。
- **定价数据源**：内置模型倍率表（可在「系统设置-运营设置」改），非外部定价数据源｜ A/中
- **插件/callback**：渠道权重/优先级、重试、日志扣费，扩展以渠道适配器为主（属性偏网关，非回调插件化）｜ C/中

### 2.3 Portkey（已并入 Palo Alto）

- **来源/状态**：「Palo Alto Networks closed its acquisition of Portkey on May 29, 2026」（`dev.to/moksh` 2026-08，C）；现称「PRISMA AIRS AI Gateway」｜ A/短
- **Star/商业模式**：约 12,500 star；OSS gateway 免费，hosted 免费 10k 日志/月 → Production $49/月 100k 日志 → Enterprise（同文，C/短）
- **订阅/quota/entitlement**：多租户 per-customer key 带 `Budget Limit`、`Rate Limit`（请求/分钟）、Alert阈值（`portkey.ai/docs/guides/use-cases/multi-tenant-ai-feature`，A/中）；成本归因按 user/team/agent/workflow｜ A/中
- **外部数据源 / 插件**：虚拟 key、语义缓存、guardrails 55+、40+ 字段/请求；无公开的「外部第三方价格/订阅源 hook」，价格基于其自身维护的模型表｜ S/短
- **态度**：商业优先、已被安全大厂收购，走向 enterprise 即命；作为**吞并源的概率因为这个收购更高**（网关厂商正被 consolidate）。

### 2.4 OpenRouter

- **计量**：**预充值 credit 制**。定金充值，逐请求扣 credits；`/api/v1/credits`（total_credits−total_usage）与 `/api/v1/key`（rate limit）；响应内 `usage` 恒含 cost/缓存明细（`openrouter.ai/docs/cookbook/administration/usage-accounting`，A）
- **订阅/modeling**：无「订阅承诺额度」概念，是纯预付费 credit 钱包；BYOK 按 list-price 月度免费额度计费｜ A/中
- **做数据源意愿高**：2026-08 推出 Activity dashboard（spend/requests/tokens/cache hit）与 **beta Analytics API** + 官方 `openrouter-analytics` skill（`openrouter.ai/blog/announcements/activity-dashboard/`，A/短）——是一个**开放、划算的第三方订阅源级合作对象**（按 credit 而非 subscription，但覆盖多厂商标准化成本）。
- 计费：无 token 加价，5.5% 充值费（min $0.80）（`dev.to/moksh`，C/短）。

### 2.5 网关风险综合判断

- **最接近「吞并」的是 LiteLLM**：它已把「美元预算 + 滚动周期 + team/personal/agent 分层」做进内核（Virtual Keys），且价格表开源可替。**它已事实上吞并了「预付费额度」这一块**。
- 但 LiteLLM 的额度是**自记账美元预算**，**不识别/不归一 Cursor 的 included 池或 Copilot 的 AI credits 这类「订阅承诺额度」**——它没有、也不激励去读编辑器订阅的消费池。因此「订阅承诺额度度量」这一细分**暂时不在网关路线图正中央**，是我们可占的缝隙（不意味着可以无视 LiteLLM）。
- new-api/one-api：仅通道内额度，不构成订阅额度威胁。
- 被内建替代概率：LiteLLM 若在未来 6–12 月加「订阅池/承诺额度 ↔ 用量对账」进入下，则威胁很大；判断概率中等偏高，需主动共建。

## 三、R2.4 厂商自研（第一方用量能力）

### 3.1 Anthropic

- **/usage、/cost** 页：Claude Console 提供用量与成本页（A）。
- **statusline rate_limits**：ccusage 等的 `statusline` 即消费 Claude Code 状态栏 rate limit 钩子（Beta），反映订阅层（5h/7d）余量（`@rockyzhangzx/ccusage` README，A）。
- **Admin API Usage & Cost**：
  - `GET /v1/organizations/usage_report/messages`（token + request，按 model/workspace/API key/service tier 归组）
  - `GET /v1/organizations/cost_report`（美元成本）
  - 需 `sk-ant-admin-...` Admin Key；「The Admin API is unavailable for individual accounts.」
  - Enterprise 另有 **Analytics API**（per-user 归因，覆盖 Claude/Claude Code/Cowork）（`docs.anthropic.com/.../usage-cost-api` + `aicosts.ai`，A）
- **半衰期**：长（接口稳定，2025 年即 GA）；**置信度 A**。

### 3.2 OpenAI

- **usage dashboard**：Organization-level `/v1/organization/usage/completions`（tokens/requests）与 `/v1/organization/costs`（美元）；Admin Key；`group_by` project/api_key/model/batch/user_id；分页（`aicosts.ai` 集成指南，A）
- **遗留端点已弃用**：「/v1/dashboard/billing/usage 和 /v1/dashboard/billing/subscription 是 legacy, undocumented, can disappear」（`aicosts.ai`，A/短）
- **Codex 用量显示**：Codex CLI 本机 JSONL（`~/.codex/sessions`）记录 token 明细；CodexBar 等读 `/api/v1/organization/limits` 显示 5h/7d quota（`CodexBar` OpenRouter/limits 文档，A/中）
- **Scale/Reserved Tier**：预购 Token 单元（committed usage），是 API 侧承诺额度（`openai.com/api-scale-tier/`，A）——这是**厂商自己做「承诺额度」**的证据，但只对自有 API。
- **半衰期**：接口中长；activity 计量语义（5h/7d）短频变化，需持续跟踪（A/短~中）。

### 3.3 Cursor

- **用量仪表板**：`cursor.com/settings` / `/dashboard/usage` 与 **Spending**（`cursor.com/dashboard/spending`）实时显示两个池：**Cursor Models 池**（Grok 4.6/4.5、Composer 2.5）与 **Other Models 池**（第三方模型，按 list price + Cursor Token Rate $0.25/M 计费）（`cursor.com/help/models-and-usage/usage-limits.md` + `cursor.com/docs/account/teams/pricing.md`，A）

- **管理后台/Admin API**（Teams/Enterprise）：spending data API、用量 toplines、spend limits、per-seat 用量归因；Enterprise pooled usage（A/中）
- **半衰期**：**短**（定价/池结构 2026 年内已多次改版，如 500 次快请求→两池/美元模式；`cursor.com/help` 与其他旧文档不一致），需要高频跟踪。

### 3.4 Copilot / GitHub

- **AI Credits**：1 credit = $0.01；Pro 含 $15 月额度、Pro+ 含 $70；chat/agent/Copilot CLI/Spaces 计 credits，补全与 next-edit 不限（`github.com/features/copilot` + `docs.github.com/.../monitor-ai-usage`，A）
- **个人用法**：Copilot 设置→Usage→「Uso en este ciclo」显示本周期 credits；用户级预算时显示「450 / 1000 AI credits」（A）
- **组织/企业**：Org settings → Billing → AI credits；`/organizations/{org}/settings/billing/ai_credit/usage` 与 enterprise 侧接口（`copilot-metrics-viewer` README + Docs，A）
- **半衰期**：中（credits 模型稳定，但额度数字与模型系数快变）。

### 3.5 论证：跨厂商可比性「厂商永远不会做」

- **证据链**：(a) 各家计量单位、池、重置逻辑完全不同——Anthropic 是 5h/7d 窗口，Cursor 是两池美元/请求，Copilot 是 AI credits($0.01/个)且按月，OpenAI 是 TPM 规模层级预购；(b) 各家把用量当**订阅留存/增值杠杆**，公开 cross-vendor 归一等于变现自己的 lock-in 失效；(c) 官方开源主推工具（LiteLLM、copilot-metrics-viewer）都只归一**自己或协议内**的 meter，无一家提供「Copilot credits + Cursor included 池 + Claude 订阅」的统一口径；(d) 各厂商的用量 API 语义/精度还互相不一致（token vs 请求 vs credits），归一需人工映射表，厂商无激励维护。
- **结论（论证成立）**：给「一个」中立第三层做「跨厂商承诺额度↔实际用量 的归一评价」是厂商结构性不会做的；这是本项目的**持久护城河**。置信度 A（推断 layer）/ 半衰期长。

### B) 3 个可结盟对象（及接触方式）

1. **ccusage / better-ccusage 生态（技术与社区对齐）**：接触方式——GitHub Issue/Discussion 提议「承诺额度 registry + 消费者侧反事实」为协作谱系；与其在「谁先合 Devin/pi」上缠斗，不如在**数据归一 schema**（如归一 token → 各订阅池「等价成本」映射）上共建，共享 star 势能。
2. **LiteLLM（网关侧共建/防吞并对冲）**：接触方式——以 PR 形式提议「第三方 subscription-pool 数据源 hook」（对标其已开放的 `LITELLM_MODEL_COST_MAP_URL` 与 per-deployment override），把「编辑器 included 池行情的归一表」作为可插 source；用它的回调/event 系统挂载用量 ingestion。**这是防「被内建替代」的正手**。
3. **OpenRouter（可复用、开放、有数据源意愿）**：接触方式——消费其 **beta Analytics API** 与 `/api/v1/credits`、`/generation` 的 `upstream_inference_cost`，作为多厂商标准化成本的一条现成管道；并可与 `openrouter-analytics` skill 对齐 schema，冲淡对手自研壁垒。

### C) 「相对 ccusage 的不可替代点」一句话 + 6 个月路线图判断

- **一句话**：ccusage 系只做「本地日志→**线性成本估算**」，我们做「**跨厂商订阅承诺额度与实际用量的可比归一 + 反事实评价（值不值得续/升/换）**」——这是它们 repo 里完全没有、且反其道（它们回避"值得不值得"、只报"花了多少"）的一层。
- **能否被其 6 个月路线图覆盖？** **低概率**——ccusage 的公开路线明显偏向「加 source（Droid/Codex/pi/amp）+ 性能（Rust 化）+ 删 MCP」，单维护者且刻意回避「替用户做订阅价值判断/云端 registry」；better-ccusage 偏向多提供商价格表。二者均无「承诺额度 registry / 反事实/厂商归一化」迹象。窗口期约 **6–12 个月**可主动占位。

### D) 上游集成路径 + 被内建替代概率 + 需提的 PR 清单

- **集成路径（防御性共建）**：
  1. 把自己的「订阅池行情/映射表」做成与 LiteLLM 兼容的**可替换 source**（对标其 map 覆盖/条数校验契约：≥50 条目、≥backup 一半、可 `LITELLM_MODEL_COST_MAP_URL` 更换），从而**避免在网关上另立协议，直接复用其预算引擎**。
  2. 以 OpenRouter Analytics/`credits` 为数据源做最小可用版，验证 schema，再扩展到 Cursor/Copilot。
  3. 以 ccusage 本地日志读入为**采集层之一**（与它们互操作而非交战）。
  - **已核验的杠杆证据**：ccusage 的价格表靠 CI 自动同步 LiteLLM `model_prices_and_context_window.json` 快照（2026-08-13 commit「update LiteLLM snapshot」）——即**整个 ccusage 生态的成本估费底层已经挂在 LiteLLM 价格表上**。这意味着：如果你的「订阅池行情表」能进 LiteLLM 的 map/覆盖体系，就能自然辐射到 ccusage 系所有工具，形成上游一次性覆盖下游生态的杠杆。
- **被内建替代概率**：中–高（特别若 LiteLLM 未来补「订阅池/承诺额度」）。判断建立在：LiteLLM 已内建美元预算、维护活跃、官方鼓励自定义数据源。因此**必须通过共建把我们的表变成网关的默认之一**，否则 6–12 个月内可能被 LiteLLM 的「额度/common」吸走入口。
- **需提的 PR 清单**（建议优先级）：
  1. LiteLLM：`docs/proxy/custom_model_cost_map` 增加「第三方订阅池 data source」段落 + env `LITELLM_SUBSCRIPTION_POOL_URL` 骨架（复用已有 URL/超时/条数校验范式）。
  2. LiteLLM：在 `model_prices_and_context_window.json` 或独立收编表中加入 Cursor/Copilot「included 池折算美元」的 `subscription_pool` 字段草案（对齐其 `aliases`/成本 key 风格）。
  3. ccusage：Discussion 提交「承诺额度反事实」RFC，争取共同 schema（token→池成本归一映射）。
  4. OpenRouter：以 `openrouter-analytics` skill 为锚，提交「统一多厂商用量归一」的互操作 proposal。
