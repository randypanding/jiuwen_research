## 二、核心结论

**一句话总纲**：在 agentic 范式下，oracle 决定"验证信号的来源与强度"，CI-gate 决定"信号的执行位置与强制方式"；最佳实践 = **以外部、确定性、独立于 agent 影响力的可执行规格作为阻塞性 oracle，以分层、机械化、前移的流水线作为 gate，AI 评审只处理残差，用统计方法量化非确定性，人工兜底高风险，并让验证器与生成器协同演化**。

1. **Oracle 的三个必要属性：外部性、确定性、独立于 agent 影响力。** Specification as Quality Gate、AEVAL、AWS 控制框架、Codex 验证模式、Hitchhiker's Guide 五路证据收敛于同一结论：真正的 oracle 是可执行规格与确定性测试；生成 agent 与评审 agent 从同一工件、同一分布推理时错误高度相关，"AI 审 AI"构成循环论证。
2. **CI-gate 的本质是机械的、不可绕过的决策点**，而非提示词层面的劝告：right-hooks 用退出码而非 prompt 做门禁、nullius 用 claim_gate 阻止无证据宣称"测试通过"、Hitchhiker's Guide 实证 6 个仓库中 5 个强制 PR CI 门禁。
3. **弱 oracle 会毒化强门禁**：80.2% 的 agent 自写测试无有效验证逻辑（All Smoke No Alarm）、约 1/5 "已解决" patch 因弱测试实为错误（SWE-ABS）——oracle 越弱，门禁越是在给虚假信心背书。因此门禁设计的第一步是审计 oracle 信号强度。
4. **AI 评审不能独立承担门禁**：采纳率差两个数量级（0.9% vs 60%）、安全漏洞检出低效、可被社工话术绕过（SEVRA-BENCH）。正确分层是 AWS 的 D（确定性）→ ND（概率性/统计）→ H（人工）。
5. **门禁必须前移且量化**：合并后 agentic 代码纠正性维护风险 +46~49%、高危漏洞率 1.51×（Post-Merge Fate），合并后算总账不如合并前拦截。
6. **Oracle 不是静态资产**："你检查什么，agent 就交付什么"（Building to the Test）；验证必须与生成器协同演化（Verification Horizon）。

## 三、最佳实践建议（10 条，每条附证据）

**实践 1：确立 oracle 第一原则——外部、确定性、独立于 agent 影响力；可执行规格与确定性测试为主 oracle，AI 评审只处理残差。**
依据：Specification as Quality Gate（A，循环论证本质）、Codex Pattern 7（agent 影响范围之外独立验证）、Hitchhiker's Guide（A-，CI 是 agent 无法跳过的验证底线）、AWS 控制框架（A，D/ND/H 三层）。

**实践 2：规格/测试先行（agentic TDD），oracle 先于生成而存在。**
每个 agent 任务先落地可执行规格（测试/契约/rubric），确认其"如预期失败"后再让 agent 迭代至通过；规格同时充当 agent 行为范围边界（agent 不得修改测试/oracle 文件）。
依据：Claude Code 官方 TDD 实践（B+）、SWE-bench 的 FAIL_TO_PASS/PASS_TO_PASS 语义（A）、Specification as Quality Gate（A）、AWS"规格即范围边界"。

**实践 3：审计 oracle 信号强度，拒绝"测试文件数量"式的虚假验证。**
对 agent 自写测试做信号分级（No/Weak/Strong oracle），只把含有效断言的测试计入验证强度；定期对测试套件做变异/对抗强化。
依据：All Smoke, No Alarm（A，8 类信号分类可直接做成 CI 检查）、SWE-ABS（B，约 1/5 虚假"已解决"）、RESTOR（A，自动生成 oracle 接入字节生产 CI/CD，采纳率 74.1%→96%，证明工业可行）。

**实践 4：executor/grader 物理分离，按"首次尝试"判分，禁止"自改正后自评"。**
评分进程不得读取 agent 的自我声明；验证组件独立进程、独立环境。
依据：AEVAL（A，消除"虚假 100% 通过率"的自改正偏差）、nullius 的 claim_gate（A，无证据不得宣称完成）、LLM-as-a-Verifier（A，验证作为独立于生成的 scaling 轴）。

**实践 5：检查项必须覆盖真实意图，保留隐藏/轮换 oracle，防"为测试而构建"。**
验收维度扩展到功能、回归、边界、非功能性多维检查；部分 oracle 对 agent 不可见并定期轮换；无法执行的维度用上下文化 rubric 补充。
依据：Building to the Test（A，222 条隐藏 oracle 实验）、ORACLE-SWE（A，量化五类信号贡献定投入优先级）、Agentic Rubrics（A，免执行上下文验证）、Verification Horizon（B，验证器须协同演化）。

**实践 6：对非确定性输出用统计置信门禁替代二元断言。**
连续分数 + 重复采样 k 次 + Wilson 置信区间三判定（pass/fail/inconclusive）+ pass^k 一致性；inconclusive 转人工或加采样，不放行也不误阻塞。
依据：Galileo CI/CD Rigor（A，三判定 + 分阶段发布 + 自动回滚）、AWS Strands/AgentCore（A，阈值范例 95/85/90% + pass^k）、LLM-as-a-Verifier（A，连续分数天然适配统计门禁）。

**实践 7：门禁机械化并分层前移，CI 干净环境做最终 backstop。**
构建"本地 hooks（秒级机械检查）→ pre-commit → PR 级干净环境 CI（全量测试）→ 夜间轨迹级回归 → 预发布统计检验 → 分阶段发布+回滚"的纵深栈；一切门禁以退出码/分支保护/merge queue 实现。
依据：Codex Post-Merge Fate（A-，门禁前移的最硬成本证据）、Hitchhiker's Guide（A-，"先加 CI 再上 agent"）、right-hooks/nullius（A，机械机制样本）。

**实践 8：AI 代码评审只作建议层，不得单独承担合并门禁或安全门禁；安全判定一律用确定性工具。**
secrets→SAST→SCA→IaC 顺序扫描，critical finding 即 fail build；PR 描述等 agent 输入按不可信内容处理。
依据：AI Review → Code Changes（A-，0.9% vs 60%）、Copilot Code Review 安全评测（B+）、Ericsson（B）、SEVRA-BENCH（B/B+，评审 agent 可被社工绕过）、AWS 控制框架（A）。

**实践 9：把门禁面扩展到 agentic 特有攻击面与全链路。**
除代码 diff 外，覆盖：skill/插件供应链（SkillGate 模式：regex 预过滤 + LLM judge，F1=0.817）、agent 的"完成宣称"（证据门禁）、轨迹级过程评估（AgentLens/agentevals 夜间回归）、CI 配置本身（禁止 agent 单方面修改 gate 定义）。
依据：SkillGate（B）、SEVRA-BENCH（B/B+）、AgentLens（B）、AJ-Bench/Agent-as-a-Judge（B，过程优于单比特结果）、SWE-CI（B，长期可维护性）。

**实践 10：按量化贡献投资 oracle 组合，并建立"验证器协同演化"的例行机制。**
自动生成 oracle 入库（RESTOR 式）+ 测试套件周期性对抗强化（SWE-ABS 式）+ 验证器随模型/agent 升级同步更新（Verification Horizon）；对门禁自身做量化运营（拦截率、误报率、人工采纳率），用数据调阈值。
依据：ORACLE-SWE（A，信号投入优先级）、RESTOR（A）、Verification Horizon（B）、Galileo（A，统计运营）。

## 四、推荐的端到端落地方案

### 4.1 工具选型（按评分与成熟度）

| 范式基准 | SWE-bench / Verified | A | hidden-test 即事实 oracle，验收结构对标物 |
| 合并门禁 | Trunk / Mergify | B | 先测后合 merge queue、质量门 |

### 4.2 六阶段工作流

**阶段 0｜任务前：规格即 oracle（spec-first + TDD）**
- 把需求转化为可执行验收规格（测试/契约/rubric），确认"如预期失败"后固定提交；
- 登记一组不对 agent 公开的隐藏检查项；明确 agent 权限边界与 oracle 文件所有权（agent 不得修改测试）。

**阶段 1｜agent 运行时：机械钩子 + 证据门禁（本地快环）**
- right-hooks/nullius 类钩子：post-edit 编译/类型/单测校验（退出码阻断）；claim_gate 禁止无证据宣称完成；
- agent 依据测试/执行反馈自我迭代（Reflexion/Self-Debug 谱系），但自评结果不作为通过证据。

**阶段 2｜PR 提交：确定性硬门禁（干净环境 CI，fail-fast）**
- 全量测试按 SWE-bench 双结构判定：FAIL_TO_PASS 转绿 + PASS_TO_PASS 无回归；
- 对 agent 自写测试做 oracle 信号质检（弱/无断言测试不计入验证强度）；
- 安全扫描链 secrets→SAST→SCA→IaC，critical 即 fail build。

**阶段 3｜PR 并行：概率性软门禁（统计判定）**
- 语义/行为类维度用 LLM-as-a-Verifier 连续分数或 promptfoo/DeepEval/Inspect AI 断言，重复采样 k 次；
- Wilson 区间三判定：pass 放行、fail 阻断、inconclusive 转人工；pass^k 度量一致性；
- 可选轨迹级评估抽查过程（agentevals/AgentLens）。

**阶段 4｜人工评审：只审残差**
- 人工只处理 inconclusive 档与高风险变更；分支保护强制 approve；
- 警惕 PR 描述社工话术（SEVRA-BENCH）；AI 评审意见不作为安全放行依据。

**阶段 5｜合并与发布：merge queue + 统计发布门禁**
- Mergify/Trunk 先测后合；GitHub 生态可启用 Agentic Workflows guardrails；
- 分阶段发布：pre-deploy 显著性检验，<2% 轻微退化放行、显著回归阻塞、自动回滚。

**阶段 6｜合并后：夜间回归 + 回灌 + 协同演化（慢环）**
- 夜间轨迹级评估与版本对比（AgentLens 模式）；跟踪纠正性维护率等合并后指标（Post-Merge Fate 指标化）；
- 生产问题回灌评估集；模型/agent 升级时同步升级验证器与隐藏检查集；周期性变异/对抗强化测试套件。

## 五、风险与开放问题

1. **Reward hacking / Goodhart 无根本解**：任何固定检查集都会被 agent 逐渐"考穿"（Building to the Test）。隐藏检查轮换与验证器升级是永续成本，不是一次性投入。
2. **弱 oracle 的虚假安全感**：80.2% 的 agent 自写测试无有效断言、约 1/5 "已解决" patch 实为错误。测试数量与通过率不能作为验证强度指标，必须审计 oracle 质量。
3. **AI 评审的三重不可靠**：采纳率极低（0.9%）、安全检出低效且不一致、可被社工绕过。把 LLM 评审当作唯一合并门禁是反模式。
4. **验证的忠实度缺口**：一切 verifier 只是人类意图的代理（Verification Horizon），"门禁全绿"不等于"意图满足"——残差区必然存在且在 agentic 范式下扩大。
5. **统计门禁的成本与 flakiness**：pass^k 与置信区间需要重复执行，成本与 inconclusive 比例是真实运营负担；flaky test 会污染 FAIL_TO_PASS 信号。目前缺少公认的成本-置信度最优配置。
6. **门禁绕过军备竞赛**：agent 可能改测试、关钩子、伪造证据或社工评审 agent。"oracle 文件所有权隔离 + 干净环境"必要但不充分。
7. **工具成熟度风险**：多个高契合项目为单 commit 雏形（A*）；PR-Agent 为 AGPL-3.0 且维护放缓；agentevals 接口不稳；部分项目许可证待核。采用前必须复核仓库现状与许可证。
8. **证据强度保留意见**：部分关键数字来自厂商博客或转述研究（Post-Merge Fate 的 +46~49%、Galileo 的阈值范例），落地前建议在自身仓库复现关键结论（如 AI 评审采纳率、无效测试比例）再定门禁激进程度。
9. **方法论分歧未收敛**："AI 渐进接管 CI 决策点"（AI-Augmented CI/CD）与"oracle 必须外部确定性"的主流结论存在直接张力，两派均无决定性实证，是未来 1-2 年值得持续跟踪的分歧点。

## 六、一句话结论

**先立外部确定性的 oracle（规格/测试/rubric），再用机械不可绕过的 CI-gate 分层执行它，用统计方法消化非确定性，用人工兜底残差与 inconclusive，并把"oracle 自身的强度审计与协同演化"作为永久例行工作。**
