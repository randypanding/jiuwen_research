# Spec 形式化语言设计研究 — 最终报告与建议（2026-08-15）

## 一、研究问题

本报告回答的最初问题是：

> 如何设计一种既能被人类精确表达意图，又能被机器可执行验证的 Spec 形式化语言？

围绕该问题拆解出三个子问题：

1. 自然语言与形式化契约的融合机制：如何将 L1 业务意图（自然语言）自动转化为 L2 开发契约（可执行验证的契约）？
2. Don't-Care 区的显式声明与验证：Spec 如何表达"未定义即自由"，并避免无限膨胀？
3. Spec 版本化与增量演化：如何管理 Spec 的变更历史，并确保向后兼容性（特别是对于 R2/R3 级制品）？

## 四、三个子问题的证据性结论

### 子问题一：L1→L2 融合必须走"消歧+约束生成+验证器闭环"管线

多篇独立研究形成一致证据链：LLM 做 NL→形式化生成"语法易、语义难"。Can LLMs Write Correct TLA+（30 个 LLM、205 条规范，SANY+TLC 双验证）测得句法正确率最高 26.6%、语义正确率仅 8.6%，并归纳 5 类幻觉模式。TLA+-Bench 提出 correctness envelope：仅改变评分口径，同一批输出的正确率在 10.0%~1.7% 间波动六倍，评测必须锚定"可执行验证"。TLA-Prover 证明"验证器即奖励"有效：SFT 加 TLC 奖励的修复式 GRPO，将语义通过率从 8.6% 提升至约 30%。另一侧，nl2spec 证明"子公式↔自然语言片段"映射可交互式暴露并消解歧义；nl2postcond 证明后置条件断言能捕获 Defects4J 中 64 个真实 bug；Daikon 可从执行轨迹自动挖掘候选不变量。

L1→L2 不能靠一次性直译，必须是"交互消歧 + 约束生成 + 验证器闭环修复 + 执行级评测"的管线；L2 契约形态以 pre/post/invariant 断言（Meyer DbC）为根基。

### 子问题二："未定义即自由"已有成熟数学刻画，且必须显式声明

CASL 宽松语义"一个规格 = 一族模型"与 TLA+"规格 = 允许行为集合、未约束即自由"两条主流路线收敛于同一思想，验证语义随之确定：性质成立当且仅当在该规格的所有模型（所有允许行为）上成立。Alpern-Schneider《Defining Liveness》证明任何时序性质 = 安全 ∩ 活性，规格只需声明这两类性质、其余默认 don't-care，这是避免无限膨胀的分类学基础。C 标准对未定义行为的官方立场是"不施加任何要求"，而《Defining the Undefinedness of C》用可执行语义把 77 种未定义行为建模为 stuck，证明 don't-care 边界可被机器执行；《What Prompts Don't Say》的实证则显示隐式默认推断脆弱（跨模型回归率翻倍），支持显式标注。

膨胀控制有三条工程路径：分类学限域（safety/liveness）、委托给环境（Interface Automata / rely-guarantee 的假设-保证分离）、部分指定加延迟解析（Relaxed NFL，其 elaboration 阶段将宽松表达转为语义确定的形式并保持每步可验证）。

### 子问题三：向后兼容不能靠自律，必须机器化验证

对 3,075 个 Web API 的实证显示 SemVer 合规率最坏仅 25%（ICWE 2024），版本号语义与实际破坏性变更严重脱节。TLA+ Trifecta 确立"refinement 即蕴含"：新版本规格蕴含旧规格（Spec ⇒ TD!Spec）时，向后兼容成为可经 TLC/Apalache/TLAPS 机器验证的定理，把兼容问题从约定问题转化为证明问题。YANG Semver 用 BC/NBC 标注使版本号携带机器可读的兼容信息；oasdiff v1.27.0（2026-07-30 核实）新增 versioning policy 检查，自动报告"发生了破坏性变更但版本号未升 major"，实现版本号与变更严重度的一致性闭环。R3 级（元模型）演化需要共演化机制而非线性迁移：共演化综述（TSE 2017）给出 31 种方法的分类学，"Don't Touch my Model!"（ICSE NIER 2024）主张多版本并存、按需迁移。

生态现状：OpenAPI 3.2.0 稳定、3.3.0 开发中，4.0（Moonwalk）截至 2026-08 仍停留在 ADR 讨论阶段，无正式规范；Optic 已于 2026-01 归档，oasdiff 成为破坏性变更检测的事实标准。

## 五、对 Spec 语言的设计建议

以下建议整合三个子代理的工作，按语言内核、生成管线、验证闭环、版本治理四个层面组织，每条注明主要依据。

### 语言内核

1. 契约语义以 pre/post/invariant 加 assume-guarantee 为核心，接口层用假设-保证分离把环境行为的 don't-care 委托给假设，规格本体不定义环境。依据：Meyer DbC（1992）、Interface Automata、Jones rely/guarantee、Pacti（契约组合/精化的参考实现）。
2. 语义内核采用宽松语义（一个规格 = 一族模型）加允许行为集合，验证即"对所有模型全称量化"。依据：CASL、Lamport《Specifying Systems》、Why3 VCGen 的验证模式。
3. 提供一等公民的显式 don't-care 标注，区分三类：输出自由（欠规格）、不可达状态、可忽略输出，映射 Don't Care Set Specifications 的 SDC/ODC 分类；双轨语义标注 undefined（越界即 stuck）与 unspecified（任选其一皆合法），依据 CH2O 与 K 框架 C 语义的卡死/任意选择建模。
4. 允许部分指定的表达式，配套 elaboration 阶段延迟解析（Relaxed NFL）；表达式级未定义项采用 LPF"空洞"语义避免污染整个表达式；前置条件域外提供"自由"与"阻塞"两种显式模式（Z 中 guards/preconditions 研究）。
5. 语言层仅接受 safety 与 liveness 性质声明，其余自动视为 don't-care（Defining Liveness）；引入完备性度量对抗"过度宽松"（如 ensures true 型空规格），借鉴 SpecRL 的负测试完备性奖励作质量分、VERIMED 的随机形式化差异作编辑器实时提示。
6. 每个 L2 子句可回溯到 L1 片段，内置"子公式↔自然语言"双向映射（nl2spec）；轻量断言式契约作为 L2 最小落地单元，直接可执行检查（nl2postcond）。

### 生成管线

7. 以 fm-universe 7~8B 微调模型为底座（From Informal to Formal 的 18k 五语言指令数据），在自有 Spec 语料上续训，再做"验证器即奖励"的 GRPO 训练，让模型自修复被拒规格（TLA-Prover）。
8. 采用"生成-验证-修复"智能体循环（Event-B Agent；LiveFMBench 证实 agentic 工作流有实质增益）；用文法归纳/约束解码约束生成输出空间，保证机器可解析（Doc2Spec、Grammar-Forced Translation）。
9. 用 Daikon 从运行轨迹挖掘不变量，自底向上补充 L2 契约候选，与自顶向下的 L1 翻译互补；Daikon 产物需置信过滤。

### 验证闭环

10. 句法检查（SANY 类）加模型检查（TLC 类）作为强制关卡，反例回传生成端修复；防真空检查：对性质做小幅变异，验证器必须能检出违例，否则判定契约恒真作废（TLA-Prover 的 Diamond 级变异测试）。
11. L1 与 L2 的一致性、以及新旧版本的兼容性，统一用 refinement-as-implication 交叉验证（TLA+ Trifecta）。
12. 执行级四档评分：Bronze（可解析）/Silver（无警告）/Gold（通过模型检查）/Diamond（通过变异测试），不用字符串匹配；显式声明并版本化 correctness envelope 评分口径；基准采取防数据污染设计（LiveFMBench）。

### 版本治理

13. 采用 SemVer 风格版本号加语言级 BC/NBC 兼容性标注，工具强制"版本号与变更严重度一致"检查（YANG Semver、oasdiff v1.27.0 versioning policy、OpenAPI 3.x 实践）。
14. 双层兼容性验证：语义层用 refinement-as-implication 经模型检查/证明器判定；结构层用变更分类规则（新增/删除/收紧/放宽，oasdiff 覆盖 509 类变更）做快速机器判定，两层结论合并产出 BC/NBC 判定。
15. deprecation 建模为语言一等概念，"deprecated → removed"需经状态机并预留至少一个 minor 版本的缓冲期（RADA 及弃用协议实证）。
16. 对 R3 制品支持非线性多版本并存，以 revision（时间戳/内容哈希）标识版本，消费方按版本选择匹配（YANG Module Versioning、"Don't Touch my Model!"、Pact consumer version selectors）；按制品等级/成熟度分级施加兼容义务，等级越高义务越严（FHIR Versions 的 Normative 分级治理）。
17. 破坏性变更检测嵌入 PR/CI 强制门禁，未过检不得合并，同时自动生成人类可读 changelog（Azure/openapi-diff 的逐 PR 强制实践）；R3 制品每次变更须附带共演化策略（迁移操作/变换规则），变更历史组织为可查询的演化图谱（共演化综述、COPE、KCoEvo）。
18. 规格作为"super-doc"随系统持续演化并分层（系统规格 → 测试/消费规格），保持长期可维护性（ZooKeeper TLA+ 工业案例）。

## 七、风险与开放问题

1. 语义正确率绝对值仍低（8.6%~30%），L2 产物必须保留人工确认环节，需定义信任阈值与回退路径；5 类幻觉模式到自有错误分类的映射及各类型修复策略尚待设计。
2. 评测口径敏感性高（六倍波动），评测协议须与语言版本绑定发布。
3. 标注负担与隐式默认的平衡：强制显式 don't-care 标注增加编写成本，过松则退化为隐式推断，需要审计工具（VERIMED 式）辅助决定何时必须标注；交互消歧的用户成本与"低摩擦表达"目标冲突。
4. 自由与空洞验证的矛盾：规格过宽导致验证 vacuous，过窄导致膨胀，完备性度量尚无公认标准；允许行为集合的模型检查受限于有限实例，需符号后端（Apalache 类）支撑。
5. refinement 蕴含判定在复杂规格下可能不可判定，需有界模型检查或证明辅助；结构 diff 只覆盖句法层，行为层兼容需模型检查，两层结论冲突时的裁决规则待定义。
6. 豁免机制：现实中"确需破坏性变更"不可避免，需设计显式豁免/降级流程，否则门禁会被绕过，重蹈 SemVer 失守覆辙；多版本并存的兼容义务可能无限累积，需定义各版本的支持窗口与退役策略。
7. LLM 交互风险：LLM 训练语料含过期契约，参与 Spec 生成/迁移时会产生跨版本知识冲突（arXiv:2604.09515），必须以最新版 Spec 为强制上下文约束。
8. 证据集中于 TLA+/ACSL/LTL 与 API 规范，机制在业务域契约上的可迁移性待实证。

## 八、建议的下一步

- 语法草案：融合契约语义（pre/post/invariant + A/G）、三类 don't-care 标注、版本化元数据（SemVer + BC/NBC + revision）。
- 验证后端：以 TLC/Apalache 类模型检查加 Why3 式多 SMT 后端为双轨，落地"对所有模型全称量化"的验证语义。
- 生成管线：fm-universe 底座加自有语料续训，验证器即奖励微调，"生成-验证-修复"智能体循环。
- 评测基准：执行级四档评分口径，与语言版本绑定发布，防污染采集。
- 兼容门禁：oasdiff 式变更分类加 refinement 蕴含判定的双层检查，嵌入 PR/CI。
