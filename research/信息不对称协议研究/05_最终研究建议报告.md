## 一、研究问题（原始问题）

**在双流水线（交付与标定）中，如何设计严格的信息不对称协议，并防止信息泄露？**

三个子问题：

1. **场景 Holdout 的自动管理与隔离**：如何为 Architect 自动生成和管理 Holdout 场景集，并确保 Builder 无法访问？
2. **生成者与判别者的上下文隔离**：在系统层面（如通过沙箱、不同的 Session、不同的模型实例）如何确保 Builder 和 Verifier 的上下文完全不共享？
3. **对抗性攻击的防御**：如何防止 Builder 通过代码注释、命名等隐式信道"传递"信息给 Verifier？

## 四、核心共识（跨方向实证结论）

以下四条结论由多个独立 A 级工作交叉印证，是整个协议设计的基石：

1. **静态公开基准必然被污染，事后检测对推理模型不可靠——隔离必须前置设计。** OpenAI 弃用 SWE-bench Verified（2026-04）与 Fragility（ICLR 2026：GRPO 训练后 10 种检测方法退化为随机猜测）共同表明：不能依赖事后检测兜底，Holdout 必须"私有 + 持续更新"。
2. **生成者与判别者同源（同模/继承/同族）本身就是泄露源。** Preference Leakage（ICLR 2026）与 LLM Evaluators Favor Own Generations 证明：判别者能认出并偏袒自己的输出，自识别与自偏好线性相关；即使上下文完全隔离，共享训练数据仍造成"行为纠缠"（BEI/CIG 可量化），必须做模型关系三查与独立性审计。
3. **安全边界必须落在应用代码/基础设施层，而非模型或提示词内。** Evaluation of Prompt Injection Defenses 在 2 万+ 次自适应攻击下证明：所有提示工程类防御全部被攻破，唯一有效的是应用代码中硬编码的输出过滤；ALIBI 同样证明 prompt 级防御对自适应攻击无效。
4. **隐式信道只能降容管控，不能宣称完全消除。** 零修改种子信道（Steganography Without Modification）、微调隐写（TrojanStego）、注释/命名/风格信道（ALIBI/When Names Disappear/BITE）表明信道形态多样且检测器本身可被自适应规避（Now You (Still) See Me）；正确目标是"把信道容量压到可忽略并持续度量残余容量"（Covert-Channel Reference Monitor 的漏桶账本范式）。

## 五、最终建议

### 5.1 子问题一：Architect 自动生成 Holdout 并隔离 Builder

#### 核心机制（均有 A 级依据）

| 机制 | 依据 |
| --- | --- |
| 私有基准评测范式（测试集永不公开，仅回传聚合分数） | TRUCE |
| 自动化策展流水线（实例创建→环境搭建→验收全自动） | SWE-bench-Live |
| 构造"训练集中明确不存在的新知识"样本 | AntiLeakBench |
| 时间戳隔离（仅采集晚于 Builder 模型训练截止日期的内容）+ 月度更新 + 场景 3 个月退役 | LiveCodeBench、LiveBench |
| 多答案随机化 + 贝叶斯准确率上界内置泄漏警报 | CapBencher |
| 显式私有分割 + Z3 机器验证 + 对抗硬化 + 受控提交制 | LLMEval-Logic |
| Docker 隔离执行 + 测试对模型不可见（FAIL_TO_PASS/PASS_TO_PASS） | SWE-bench |

#### 协议设计要点

1. **生成来源三路并行**：真实任务流主干（仿 SWE-bench-Live 持续抓取新 issue，每任务自动生成 Docker 验收环境）；时间隔离的新鲜内容辅干（仿 LiveBench 月度更新）；显式新知识构造（仿 AntiLeakBench，防止"新瓶装旧酒"——新采集≠无污染）。
2. **新鲜度准入规则**：来源产生时间 > max(Builder 侧所有模型训练截止日期) + 安全缓冲期；每批入库发布内容哈希承诺，保证时间隔离可举证。
3. **发布前四道质量闸门**：真值机器验证（Z3/测试套件/客观真值）；缺陷测试过滤（gold 解强制跑通，吸取 SWE-bench Verified 缺陷测试教训）；对抗硬化与难度分层；text-dedup 重叠校验（与 Builder 可见语料零重叠）。
4. **保密发布**：默认不发布内容只发布接口——Builder 提交产物，Architect 域内评测，仅回传降维反馈（只给总分/通过率区间，切断反馈回路过拟合）；必须露出题干的场景用 CapBencher 多答案随机化加固。

#### 隔离实现（确保 Builder 无法访问）

1. **技术强制层**：评测执行节点运行于 TEE/机密空间（TRUCE 证明机密计算开销可忽略；PySyft 已支持 GPU Confidential Space），Holdout 仅在 enclave 内解密；强互不信任场景可选 MPC（原理参考 CrypTen）。
2. **系统流程层**：按五边界分类法设防（重点 agent–tool 与 system–environment）；Builder 身份在 IAM 层显式 deny；Builder 侧开发调试一律使用 mock 场景集（PySyft 式 mock/私有数据分离）；OpenShell 式策略引擎默认拒绝+全量审计；Holdout 主库双人控制+密钥分存（防内部泄漏）。
3. **审计兜底**：CapBencher 贝叶斯上界监控（唯一与训练方式无关的泄漏信号）；canary GUID 取证扫描；灰盒检测工具（Time Travel/选项打乱/KDS）仅作周期性抽查，不作验收标准。

### 5.2 子问题二：Builder/Verifier 上下文完全不共享

#### 总体架构：可信编排器 + 最小充分中继

不共享是默认状态，任何信息流动都必须穿过显式、受策略管控的中继。设可信编排器 O 作为唯一跨边界中介：

```
Builder（会话S_B/模型M_B/沙箱X_B/凭据K_B）
   │ 仅出站：交付物全文（对 O 可见，对 V 不可见）
   ▼
O：原子化 + 净化 + 哈希承诺 + 策略强制（默认拒绝）
   │ 仅出站：最小充分中继 R = {原子命题, 公开证据, 场景规格}
   ▼
Verifier（会话S_V/模型M_V/沙箱X_V/凭据K_V）→ 仅回传评分/判定
```

形式化不变式：**View(B) ∩ View(V) ⊆ 公开集**；D（交付物原文）、T_B（Builder 推理链）、K_B、S_B 状态均不得进入 View(V)。

#### 六项关键设计

1. **模型关系三查（硬规则）**：Builder 与 Verifier 不得同模、不得有继承关系（蒸馏/SFT 后代）、不得同族，建议跨厂商部署（Preference Leakage、LLM Evaluators Favor Own Generations）。
2. **Session 隔离**：独立 session/checkpoint/记忆库/向量库，禁止共享 KV cache；编排框架选 LangGraph（独立 checkpointer+子图隔离），避开上下文默认共享的框架。
3. **沙箱隔离**：双方执行环境分别置于独立 Firecracker microVM（E2B）或 gVisor；无共享文件系统/网络命名空间/IPC；Verifier 沙箱默认禁止出站网络；叠加 OpenShell 策略引擎。
4. **消息边界**：MARCH 式原子化中继——Proposer 把交付物分解为 claim 级原子命题，Verifier 只收 {原子命题+证据+量规}，不收原文/推理链/注释原文；中继在 O 处做应用层硬编码净化。
5. **密钥凭据隔离**：K_B/K_V 完全分离；采用 Auth Proxy 模式（密钥由代理持有，运行时进程不可触达，防 Comment and Control 式注入外传）；水印检测密钥只归标定侧。
6. **独立性审计（必选项）**：系统隔离解决不了权重层的行为纠缠——用 BEI/CIG 指标季度审计，超标即换模型或做去纠缠集成重加权（最高 +4.5% 精度）；辅以自识别盲测与自偏好解耦测量。

#### 隔离程度的权衡（信息瓶颈视角）

不要追求零中继——目标是**最小充分中继**。依据信息瓶颈研究：中继近充分时多智能体稳定有益，中继信息损失时收益反转（强模型尤甚）。建议按 Verifier 强弱调节中继粒度：Verifier 越强，中继信息要更足；用判别准确率与人类一致性扫描中继带宽找拐点，同时用 CALM 监控判别端 12 类偏差。

### 5.3 子问题三：防止 Builder 经隐式信道向 Verifier 传信

#### 威胁模型（五类信道）

| 信道 | 证据 | 危险度 |
| --- | --- | --- |
| 注释/隐藏指令（含 HTML 注释、PR 元数据、字符串、诱饵代码） | ALIBI（ASR>90%）、When Skills Lie、Comment and Control（CVSS 9.3-9.4）、Compliance Paradox（>95% 失败率） | 极高，交付物即信道 |
| 标识符与命名 | When Names Disappear、SrcMarker（变量名可编码比特串） | 高 |
| 风格与表面形式 | BITE（风格编辑 ASR>65%）、Emoji Attack、零宽字符/同形字（Invisible Safety Threat） | 高 |
| 解码种子/推理栈（零修改信道） | Steganography Without Modification（32-bit 秘密 300 token 内最高 100% 恢复） | 最高，文本净化完全无效 |
| 训练级/权重级（微调隐写）+ 行为纠缠 | TrojanStego、Now You (Still) See Me（逃逸探针仅 1%-8% 能力代价） | 长期威胁 |

#### 三层四区防御设计

**交付侧净化（第一道强制边界，平台托管、确定性执行）**：
1. 注释全量剥离（Tree-sitter 解析，CodeSentinel 的"检测即移除/中和"策略）；必须保留注释时用独立净化模型改写+打分复核。
2. AST 级标识符规范化重命名，消除命名信道。
3. 风格归一化（统一 formatter + Unicode NFC + 零宽字符/同形字清除），消除 BITE 式操纵面。
4. **解码种子没收**：PRNG 种子由平台注入且 Builder 不可见不可选——这是唯一能封堵零修改信道的措施。
5. 净化前后跑同一测试套件做语义等价校验（PASS_TO_PASS），保证净化不改变程序行为。

**标定侧鲁棒性**：
1. Verifier 只消费"净化后交付物+程序证据（测试执行、静态分析）"，对交付物内自然语言显式降权（ALIBI 结论）。
2. 激活水印式密钥监控（Activation Watermarking，推理期引入攻击者不知密钥的不确定性，相对 guard 基线最高 +52%）。
3. 防御验收按 PIEval 双维框架（有效性×通用效用）+ 自适应攻击压测；验收标准是"自适应攻击收敛后残余 ASR 达标"而非静态攻击集成绩。
4. 检测器多探针集成+重上下文化评估分布+周期更新（单探针必被规避）。
5. CALM 12 类偏差审计 + BITE 式风格敏感性测试 + 季度行为纠缠审计。

**出口管控与水印溯源**：
1. 出口参考监视器：文本多级降容流水线+漏桶容量账本；媒体出口加扰+启动时签名认证；以 Miller-Madow 校正互信息度量残余容量，目标"可摧毁信道残余容量归零"。
2. 交付侧打 KGW/SynthID-Text 类密钥水印（仅标定侧可验，不用公开可验方案——那会削弱信息不对称）；源码可叠加 SrcMarker 式 AST 水印；水印兼具泄露溯源与净化失效告警双重用途。
3. 同集群场景参考 Fingerprinting AI Cluster I/O：对进出线缆做哈希承诺指纹，安全网关消除模拟/时序侧信道与协议头隐写。

#### 推荐组件组合

净化/检测：Tree-sitter+Dynamic Min-K%（CodeSentinel 方案）、Open-Prompt-Injection（DataSentinel/PromptLocate）；运行时护栏：NeMo Guardrails（含 YARA 代码注入检测）、Guardrails AI；水印：MarkLLM、SynthID Text、SrcMarker；红队验收：PyRIT、Garak、PISmith；审计：CALM、BEI/CIG 统计框架。

### 5.4 总体架构：双流水线信息不对称协议（三子问题整合）

```
┌─────────────────────── Architect 域（可信）───────────────────────┐
│  Holdout 策展管线：时间戳准入 → 新知识构造 → 质量四闸门 → 哈希承诺   │
│  Holdout 主库：TEE 加密存储 + IAM deny + 双人控制                  │
└──────────────┬──────────────────────────────────────────────────┘
               │ 场景规格（公开部分）
┌──────────────▼──────────┐        ┌───────────────────────────┐
│ Builder 流水线           │        │ Verifier 流水线            │
│ S_B / M_B / X_B / K_B   │        │ S_V / M_V / X_V / K_V     │
│ mock 场景集开发调试      │        │ 与 M_B 跨厂商、无继承关系   │
└──────────────┬──────────┘        └───────────▲───────────────┘
               │ 交付物 D                       │ 最小充分中继 R
               ▼                                │（原子命题+证据+量规）
┌───────────────────────────────────────────────────────────────┐
│ 可信编排器 O：净化（注释剥离/标识符规范化/风格归一/种子没收）       │
│ → 应用代码硬编码过滤 → 水印打标 → 哈希承诺日志 → 策略强制          │
└──────────────┬────────────────────────────────────────────────┘
               │ 产物提交（Builder 不接触 Holdout 内容）
┌──────────────▼────────────────────────────────────────────────┐
│ 标定执行：TEE 内用 Holdout 评测 → 降维反馈（仅聚合分）→           │
│ 贝叶斯上界监控 + canary 取证 + 季度行为纠缠审计                   │
└────────────────────────────────────────────────────────────────┘
```

**协议不变式**：
- View(B) ∩ View(V) ⊆ 公开集；View(B) 不含 Holdout；View(V) 不含交付物原文与 Builder 推理链。
- 所有安全边界由应用代码/策略引擎/TEE 强制，不依赖模型自我约束。
- 隔离是默认状态，任何跨边界信息流必须经 O 的显式策略许可并留哈希承诺日志。

### 5.5 分阶段落地路线（整合）

| 阶段 | 工作内容 | 关键依据 |
| --- | --- | --- |

## 六、风险、局限与注意事项

1. **反馈回路过拟合**：私有提交制仍允许反复试探（CapBencher）。对策：限制提交频次、反馈降维、分数突变人工复核。
2. **检测手段的脆弱性不可逆**：灰盒检测对推理模型近乎失效（Fragility），任何检测器都不应作为验收标准；内置上界警报是唯一与训练方式无关的信号。
3. **canary 的局限**：可被恶意删除，只对"原样进入语料"有效，仅作合规声明与取证线索。
4. **行为纠缠无法靠协议消除**：同族/共享训练造成的自我偏好只能降低不能消除（异构模型+去纠缠重加权），标定分数解释中须保留此不确定度。
5. **零修改信道**：不在推理栈层没收种子控制权，该信道始终开放（32 bit/次生成）。
6. **净化副作用**：注释剥离与标识符重命名可能影响依赖注释语义的任务；必须用测试等价性校验兜底，并按 PIEval"通用效用"维度验证未伤害合法交付物。
7. **过度隔离反伤判别质量**：中继信息损失时强模型 Verifier 收益反转，须按信息瓶颈经验调优中继粒度。
8. **证据成熟度**：多处关键依据为 2026 年预印本（MARCH、Preference Leakage、CodeSentinel、ALIBI、Steganography Without Modification 等），尚未经长期同行评议；重大架构决策前建议对关键数值（F1=0.80、ASR>90%、+52%、TEE 开销）做小规模复现实验。
9. **运维面是更现实的泄漏面**：编排器 O 被攻破则全局失效，须独立部署域+双人审计；TEE 将信任转移给硬件厂商与 enclave 证明链；日志、备份链路需同等防护。
10. **成本与规模**：月度全量更新+每场景独立 Docker 环境成本显著，建议场景池分层：核心保密池小而精（TEE 评测），外围池大而松（时间隔离即可）。
