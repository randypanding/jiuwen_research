## 四、方向一建议：黄金输出的生成与维护

> 子问题 1：如何为 R3 级制品生成可信的黄金输出，并管理其演化？
> 以下建议由方向一终审子代理输出（深读 26 条清单 + 总表方向一部分，并对 syrupy、insta、arXiv:2410.21136、arXiv:2607.10277、LLMShot 做了在线核验）。

### 4.1 核心判断

1. **黄金输出只是回归护栏，不是正确性证明。** 快照测试实证研究反复确认：快照"只检测输出是否变化，不检测输出是否正确"（ICSME 2023 对 569 个 Jest 项目的实证）。对加密/金额这类 R3 制品，一次错误的"批准更新"会把 bug 固化为新黄金，因此机制必须是"黄金输出 + 独立预言机"双轨。
2. **黄金输出本质是 derived oracle（从执行/历史推导的预言机）**（TSE 2015 预言机综述分类）。当推导源不可信（不可再生输出、LLM 生成）时，必须转向 specified oracle（规格/已知测试向量）与 implicit oracle（可逆性、守恒律等隐含属性），并以人类批准兜底。
3. **"期望基准"与"现状快照"必须显式分账。** LLM 生成预言机被实证倾向于捕获"实际实现行为"而非"期望行为"（arXiv:2410.21136）；而表征测试（Feathers）的方法论恰恰是"先固化现状"。两者混用是 R3 场景最大的隐性风险，机制设计上必须物理隔离两类制品。

### 4.2 机制设计

**黄金输出生命周期（五阶段闭环）**：生成 → 规范化 → 比对 → 分诊 → 批准更新（含溯源记录）。

- **生成**：以表征测试（characterization testing）为起点——无权威规格时先捕获当前实际行为作为基准，并明确标注这是"现状快照"而非"期望值"。对加密制品，优先使用标准测试向量（RFC/KAT/NIST 向量）作为 specified oracle，其地位高于任何自捕获快照。
- **规范化**：比对前把不可再生字段（时间戳、nonce、随机盐、UUID、会话 ID）通过 matcher/redaction/模板占位替换掉，使剩余部分可字节级比对。
- **比对**：对逐行语义敏感部分采用字节级/位级精确比对（goldie 模式、LLM4FP 的 hex 位级比较）；金额计算额外要求规范化序列化（固定小数位、固定舍入模式、CRLF→LF 归一）。
- **分诊**：失败先分类——真回归 / 有意变更 / 非确定性噪声。可用 LLM 做初筛（LLMShot 范式，Gemma3-12B 召回 >84%），但高风险制品必须人工终审。
- **批准更新**：任何黄金更新走人工批准 + diff 审查 + 独立验证（见 4.4 纪律）。

**双轨预言机体系（R3 的核心机制）**：

| 轨道 | 作用 | 具体机制 |
| --- | --- | --- |
| 轨道 A：黄金输出比对 | 回归护栏，防"无意变化" | 快照/黄金文件 + 规范化 + 字节级比对 |
| 轨道 B：独立正确性预言机 | 防"错误被固化" | ① 蜕变关系 MR（加解密互逆、金额守恒/交换/舍入往返一致）② 参考实现对拍（OpenSSL/EverCrypt/Fiat-Crypto 作 golden oracle）③ 组合操作 oracle（`decrypt(encrypt(m))==m`）④ 校验和 oracle |

关键工程原则（来自 Tardigrade/OpenSSL 差分测试 PR 的实践）：**oracle 侧必须使用与被测实现独立的常量与中间值**，避免两边犯同样错误导致假绿。

**不可再生输出的专门处理（三层递进）**：

1. **字段级剥离**：matcher/redaction 只剥离确证不可再生的字段，其余一律精确比对。被剥离字段的正确性必须用轨道 B 单独验证（如 nonce 唯一性、时间戳单调性用属性测试验证），**剥离不等于免责**。
2. **两阶段记录**（借鉴 Linux 内核 randstruct.seed 实践）："把不可复现部分当源"——随机性一次生成后固化为输入资产（如预生成 nonce 存为测试数据），之后流程全部确定性可比对。
3. **分布比较替代单点比较**：若制品含 LLM 采样等无法消除的随机性，黄金输出应升级为"行为指纹 + 统计检验"（SPRT 三值判定 PASS/FAIL/INCONCLUSIVE），而非精确快照。

**演化管理（防断言漂移）**：

- **更新触发预测**：借鉴 DRiFT 的方法级共演化预测，把"盲目全量更新黄金文件"细化为"精准定位受影响的断言"；生产代码变更与黄金更新的关联必须显式记录。
- **黄金输出元数据**：每份黄金文件附带 manifest——生成时的代码版本、依赖锁、随机种子、模型版本/采样配置、生成者（人/工具/LLM）、批准人与批准理由。对标 Reproducible Builds 的 `.buildinfo` 与 Debian 迁移门禁思想：把"可比对性前提"制度化记录。
- **演化模式归档**：参考测试共演化五种模式，为每次更新打标签（意图变更 / 重构等价 / 缺陷修复 / 规格升级），便于审计与回滚。
- **豁免（waiver）注册表**：无法消除的已知差异登记在册并定期复审（Tardigrade 实践），禁止静默忽略。

### 4.3 工具选型

| 栈 | 首选 | 关键机制（已核验） |
| --- | --- | --- |
| Python | **syrupy** | `matcher`（path_type/path_value/compose_matchers）与 `exclude`（props/paths）对不可再生字段替换/过滤；soundness 原则——快照不存在即失败；`--snapshot-update-new-only` 支持"只新增不覆盖"；2026-08 仍活跃 |
| Rust | **insta** | `cargo insta review/accept` 交互式逐条人工批准；Redaction 机制替换敏感/非确定值；v1.47.2（2026-03） |
| Go | **sebdah/goldie** | 字节级比对，天然适配金额/序列化的逐行敏感输出；模板断言做简单占位 |
| JS/前端 | **Jest** | property matchers（`expect.any(Date)`）+ "快照即评审产物"纪律 |
| 多语言流程范式 | **ApprovalTests** | "生成 golden master → 不一致时拉起 diff 工具 → 人工批准后才更新"的完整工作流范本 |

选型要点：优先选**带人工批准环节（interactive review）+ 带字段级替换（matcher/redaction）+ 缺快照即失败（soundness）**三要素齐全的工具。syrupy 与 insta 恰好同时满足三条。

独立预言机侧工具：属性测试 **Hypothesis**（Python）/ **Proptest**（Rust）；变异分析 **mutmut**（Python，增量缓存适配有限预算）；加密参考实现 **EverCrypt/HACL\***、**Fiat Cryptography**、OpenSSL（out-of-process EVP oracle 模式）；等价变异采用 VizDetour 式"端点保持变异 + 输出一致性"。

### 4.4 维护与批准纪律（可写入团队规范的硬条目）

1. **CI 永不自动写黄金。** 快照/黄金文件只能由人工在本地显式触发更新，作为代码提交并走评审（Jest 官方最佳实践）。CI 上只允许比对模式。
2. **更新即评审，评审即 diff 审查。** 每次黄金更新必须逐行看 diff 并回答"这是期望的变化吗"。禁止批量 `-u` 不看 diff。
3. **批准需独立证据。** 对加密/金额，批准一次黄金更新前，除 diff 外还要求至少一条轨道 B 证据（MR 通过 / 参考实现对拍一致 / 已知测试向量吻合）。
4. **首次记录显式确认。** 采用 swift-snapshot-testing 的"首次记录即失败、需显式重跑确认"纪律，防止无意识生成黄金。
5. **期望基准与现状快照分目录、分标签存放**，分别适用不同的更新审批严格度；现状快照禁止直接升格为期望基准。
6. **waiver 必须有期限与责任人**，定期复审清零。
7. **黄金 manifest 随文件入库**（版本、种子、环境、批准人），环境按 Reproducible Builds 清单固定（时间戳、locale、路径、随机种子等 16 类来源）。
8. **用变异得分持续度量预言机健康度**：若某断言被变异后判定结果不变，视为形同虚设，限期修复。

### 4.5 LLM 预言机使用的注意事项

1. **LLM 预言机会固化 bug，而非发现 bug。** 受控实验表明 LLM 生成的预言机倾向捕获"实际实现行为"而非"期望行为"，且更擅长生成而非判别。**LLM 可用于起草黄金输出/断言，但不得自动批准**；批准前必须人工确认其捕获的是规格语义。
2. **数值敏感领域表现不稳，需重点人工核查。** 从业务需求生成断言的实证显示预言机正确性存在显著 bug 级与模型级方差，预训练覆盖与行为的语义特异性是主导因素；金额舍入规则、加密参数边界恰属此类。
3. **多模型对照 + REQ 黄金预言机。** 为关键规则建立需求派生的 REQ 黄金预言机，用多个 LLM 生成结果与之对照，分歧即风险信号。
4. **多智能体共识可提升可靠性但非充分条件。** CANDOR 表明多智能体讨论共识生成的预言机正确性显著优于单模型（比微调 SOTA 高 ≥21.1pp），可作为起草阶段的降幻觉手段，但仍须叠加人工批准。
5. **LLM 只适合做分诊初筛，不适合做终审。** LLMShot 分类快照失败根因召回 >84%，可降低人工分诊成本，但对加密/金额只能改变"审查顺序"，不能改变"是否通过"。
6. **警惕静态分类的语法捷径。** FlakyLens 等实证表明 LLM 基于代码文本的分类会被语法线索误导——判定"差异是随机还是偏差"必须依据执行证据，而非 LLM 读码结论。
7. **命名质量显著影响 LLM 预言机质量**：R3 制品的变量/函数命名规范化本身就是提升 LLM 辅助验证效果的工程手段。
8. **语义等价分诊可用基础模型。** 重构/再生成后的输出等价性判定，可用基础模型零样本分诊（GPT-5.4 达 93.8%）标记可疑变换，再交人工与轨道 B 复核——定位为"分诊器"而非"判定器"。

## 五、方向二建议：非确定性的容忍与检测

> 子问题 2：如何区分代码再生的非确定性（随机性、并发时序、LLM 采样）与真正的行为偏差？
> 以下建议由方向二终审子代理输出（深读 28 条清单 + 总表方向二部分，并对 AgentAssay、arXiv:2606.25797、arXiv:2607.24372、arXiv:2606.26185、arXiv:2512.18088、agrepl、Reprise、Reproducible Builds 做了在线核验）。

### 5.1 总体方法论

**先控制、再差分（DT² 范式）→ 残余差异统计化判定（SPRT 三值）→ 重放兜底（record/replay）→ 门禁制度化（Debian 迁移门禁范式）。**

四个已被证据支撑的核心原则：

1. **非确定性无法从代码静态判定**：86 个端到端 flaky 案例中仅 42% 可由代码+日志解释，其余 58% 必须依赖执行证据（arXiv:2607.09345）；LLM 分类器在真实数据上 F1 从 81.82% 跌至 56.62%（FlakyLens）。任何"一次差异"都不能凭代码阅读归因。
2. **先固定所有可控非确定性来源，再做差分**，使剩余差异可归因于真实行为变化（DT² 事务测试协议）。
3. **LLM 输出是分布的抽样，不是固定测量值**：T=0 只消除"刻意采样"，无法消除静默模型更新、数值舍入、专家路由（arXiv:2607.24372）；即使强制贪心解码，690 次调用中 7 个边界项仍有 1–2 个翻转（arXiv:2606.26185）。
4. **单次运行判定在统计上无意义**，必须用带置信度的多次采样判定。

### 5.2 归因框架：四类非确定性来源的判定特征

| 来源 | 可观测特征 | 控制手段 | 判定手段 |
| --- | --- | --- | --- |
| 程序随机性（RNG、迭代序、时间戳、UUID） | 固定种子后稳定；扰动种子时输出在"合法空间"内变化 | 种子注入+派生（randstruct.seed 模式）；排序遍历；SOURCE_DATE_EPOCH | 多种子重跑：差异随种子变化且落在规范允许空间 → 随机性（NonDex 扰动范式） |
| 并发时序（线程交错、调度、锁竞争） | 顺序敏感；固定调度后稳定；失败概率通常极低（中位数 ~10⁻⁴） | 确定性调度/交错控制（DT² 协议、CONDIFF 交错穷举）；rr/DRT 记录重放 | 固定 vs 打乱顺序各跑 N 次（iDFlakies 协议）；重放一致性判定 |
| 环境/依赖（时间、locale、路径、依赖版本、编译器） | 换机器/换依赖版本才复现；16 类环境变异有系统清单 | 锁定依赖+容器化+固定环境变量（Reproducible Builds 清单）；三层依赖框架 | 同环境重跑一致而跨环境不一致 → 环境噪声，非行为偏差 |
| LLM 采样/供应链（刻意采样、静默模型更新、舍入、专家路由） | 同 prompt 同参数仍波动；未设温度时边界项翻转率可达 ~50% | 固定 model 版本/快照、temperature/top_k/seed、本地权重+固定软硬件栈 | 多次采样+不一致率作为一等健康指标；分布比较而非精确匹配 |

### 5.3 非确定性来源控制清单（按层落地）

- **层 A 环境与构建**（对照 Reproducible Builds 16 类环境变异）：固定时间戳（SOURCE_DATE_EPOCH）、构建路径（BUILD_PATH_PREFIX_MAP）、locale/编码/umask/时区/主机名；所有文件系统与哈希表遍历显式排序；消除内存地址泄漏进输出。
- **层 B 依赖与运行时**：依赖锁定到精确版本+哈希（lockfile + checksum），区分声明/工作/运行时三层依赖（AI 生成项目仅 68.3% 可复现，声明到运行时依赖平均膨胀 13.5 倍）；容器镜像固定 digest；浮点行为固定（编译器版本/优化级别/指令集一致）。
- **层 C 程序内随机性**：所有 RNG 强制种子注入，主种子→派生种子两级结构；不可再生字段比对前用 matcher/exclude 规范化，但被屏蔽字段需独立属性验证（长度、唯一性、格式）；主动扰动合法随机源验证稳定性，扰动空间必须受规范约束（NonDex）。
- **层 D 并发与时序**：测试态提供确定性调度开关（单线程化、固定交错）；无法单线程化时用 record/replay 运行时（rr/DRT）；顺序依赖检测用固定 vs 打乱各跑一轮。
- **层 E LLM 采样与供应链**（R3 再生成场景独有）：**不要相信 T=0**——显式设置 temperature/top_k/seed，核验供应商是否静默用默认值 1.0，注意新一代模型已弃用 temperature 参数；固定模型版本/快照 ID，优先本地部署开源权重；完整"采样配置清单"写入黄金输出 manifest；用 MITM 代理/录制层（agrepl/Reprise）捕获全部 LLM/工具/API 交互，使再生成过程可离线重放。
- **通用纪律——环境 manifest**（仿 Debian `.buildinfo`）：每次黄金输出录制与每次 CI 运行都产出机器可读的 `.r3info`（版本、依赖锁哈希、全部种子、采样参数、模型版本、环境指纹）。**manifest 不一致则比对结果无效**。

### 5.4 统计判定方法

1. **重跑预算（Wilson 区间 + 规则三）**：flaky 失败概率中位数仅 9×10⁻⁴，"数千到数万次执行"才够可靠判定（arXiv:2512.18088）。检出预算：要以置信度 1−α 至少观测到一次失败，需重跑 `n ≥ ln(α)/ln(1−p̂)`（p̂=10⁻³ 时 95% 置信需 ≈3,300 次）。排除预算（规则三）：n 次重跑零失败则失败概率的 95% 置信上界 ≈ 3/n——**"跑 3 次都绿"不构成任何证据**。结果编码保留异常类型/消息等细粒度信息，不要只存 pass/fail。自适应预算（AgentAssay）按观测方差校准最少试验数，对稳定工作流可减少 4–7× 试验量。
2. **置信序列（在线、随时可停）**（arXiv:2606.25797）：边采样边更新置信界、任意时刻可停且保证有效，平均比 union-bound 方法少 50× 采样。用途：持续监控"再生成输出稳定性"的长时任务（夜间批量再生成、回归历史回放），不必预先决定样本数。与贝叶斯序贯检验互补：先验可编码"该输出本应稳定"的工程预期，证据充分即提前停止。
3. **三值判定引擎（SPRT）**（AgentAssay，底层论文 arXiv:2603.02601）：用 Wald 序贯概率比检验把二值判定替换为 PASS / FAIL / INCONCLUSIVE。**铁律：INCONCLUSIVE 永不默认通过**——它显式表示"证据不足"，触发追加试验或升级人工审查。配套行为指纹 + Hotelling T²：把执行轨迹压缩为工具调用模式、决策频次分布、输出特征等向量做多元偏移检测；对"无功能失败的行为漂移"类回归，检测力 86% 而二值测试为 0%。注意来源风险：单作者论文+早期框架，采用前自建 harness 复核。
4. **判定决策树（综合）**：

```
再生成输出与黄金输出出现差异
 ├─ 步骤1：manifest 比对。环境/依赖/种子/采样配置不一致 → 判定"环境噪声"，修复控制后重测
 ├─ 步骤2：全受控条件下重放（相同种子/录制轨迹）
 │    ├─ 重放仍不一致 → 真行为偏差（FAIL，阻断）
 │    └─ 重放一致 → 差异来自非受控随机源，进入步骤3
 ├─ 步骤3：扰动检验。改变种子/顺序/采样参数重跑 N 次
 │    ├─ 差异随扰动在规范允许空间内变化 → 合法非确定性（记录+容忍，可加属性断言）
 │    └─ 差异稳定复现、不随扰动变化 → 真行为偏差（FAIL）
 └─ 步骤4：无法消除的随机源（LLM 采样等）→ 统计通道
      ├─ SPRT 三值判定；INCONCLUSIVE → 按预算追加重跑（置信序列可随时停）→ 仍不收敛 → 人工审查
      └─ 行为指纹 T² 漂移超阈值 → 即使功能全绿也阻断（行为漂移回归）
```

### 5.5 确定性重放工具选型

| 工具 | 作用层 | 成熟度（2026-08 核验） | 适用场景与警示 |
| --- | --- | --- | --- |
| **rr**（Mozilla） | 系统调用/指令级 | 非常成熟，持续维护 | 原生二进制的并发/时序 bug 复现（加密库 C/Rust 实现层）；不适用 LLM/高层采样；Linux only |
| **DRT** | Python 并发运行时 | 单作者原型 | Python 并发制品；`DivergenceError` 即"非确定性 vs 真偏差"的直接信号；需代码改造 |
| **agrepl** | HTTP/LLM 交互层 | 早期（单作者，Go，2026-07 活跃） | LLM 再生成流水线的"录制一次、确定性重放"，语言无关；CI 集成在 roadmap；采用需自托管并锁 commit |
| **Reprise** | LLM/工具/MCP 调用层 | v0.1.0，9 commits，单作者 | AI 智能体再生成的黄金轨迹门禁：录黄金 trace → `diff --gate --threshold T` 分歧超阈值即失败；极早期，但其 gate 设计与 R3 门禁需求完全同构，可作设计参考甚至 fork 基线 |
| **rewind** | 种子派生层 | 早期 | "给定种子即确定"的循环型再生成；作者明确声明不为非确定性 GPU/LLM 栈服务，与 LLM 场景错位 |
| VCR/cassette 模式（自研兜底） | API 响应层 | 成熟范式 | 上述工具不可用时的最小实现；需自行处理请求匹配与状态漂移 |

**选型结论**：LLM 再生成场景以 Reprise 式"调用级录制 + diff gate"为目标架构、agrepl 式 MITM 录制作零插桩补充；两者均为单作者早期项目，必须锁定 commit、自托管、关键断言自写，或按其设计自研精简版。系统级并发：C/Rust 用 rr，Python 用 DRT 思路。通用兜底：种子派生 + 响应夹具。

### 5.6 CI 门禁设计（四层门禁 + 治理机制）

- **L0 清单门禁（manifest gate）**：每次运行产出 `.r3info`；与黄金输出录制时的 manifest 不一致 → 直接判 INCONCLUSIVE（比对无效），而非 PASS/FAIL。
- **L1 确定性门禁（replay gate，硬门禁）**：对全受控制品同种子/同录制轨迹重放，逐字节比对（diffoscope 式），任何差异阻断——仿 Debian 14 迁移门禁把"逐位复现"变成硬门槛的制度化范式。
- **L2 统计门禁**（含 LLM 采样、残余并发的制品）：SPRT 三值判定（建议 α=0.05、β=0.10）；PASS → 合并；FAIL → 阻断+报告分布证据；INCONCLUSIVE → 自动追加重跑直至预算上限，到顶仍不收敛 → **默认阻断并升级人工**（宁严勿松）。
- **L3 分布门禁（行为漂移 gate）**：行为指纹 + Hotelling T²，漂移超阈值即使功能全绿也阻断；阈值用历史数据校准，T² 统计量作为一等健康指标入盘。
- **治理机制**：判定为非确定性的用例不删除，进隔离区并打 IDoFT 式细粒度标签，修复后回归主套件；把"偏差引入的再生成点"当 FIC（flakiness-introducing commit）记录——再生成点必须立即跑非确定性检测，而非等下游；豁免登记册（waiver registry）管理一切放宽门禁的行为；统计重跑设预算上限与成本熔断；禁止自动静默通过、禁止 LLM 静态分类归因（归因只认执行证据）。

### 5.7 方向二落地路线图与风险边界

| 阶段 | 动作 |
| --- | --- |
| 第 1–2 周 | 落地层 A/B 控制清单 + `.r3info` manifest；锁依赖、固定环境变量与种子注入 |
| 第 2–4 周 | 实现 L1 重放门禁（自研精简版或 fork Reprise 设计）；建立"重放不一致即阻断" |
| 第 1 个月 | 统计通道：SPRT 三值判定 + Wilson/规则三预算公式；INCONCLUSIVE 处理流程入 CI |
| 第 1 个季度 | 行为指纹+T² 分布门禁；置信序列用于夜间批量监控；隔离区+waiver 登记册；NonDex 式扰动做周期性"非确定性审计" |

**风险边界**：AgentAssay、Reprise、agrepl 均为单作者早期项目，建议借鉴设计与协议、自研关键断言，勿在生产门禁中裸依赖；T=0 的实证边界意味着含 LLM 采样的制品必须把"逐位复现"目标降级为统计/概率验证；10⁻³~10⁻⁴ 量级的非确定性需要数千至数万次执行才可靠检出，低频 flaky 探测应放到夜间/周级批量任务并用置信序列降低采样成本；主动扰动只探索"规范允许的行为空间"，否则会把合法变化误判为偏差。

### 6.2 轻量差分流程设计（无 fan-out）

核心思想：**fan-out（同时跑 N 个实现）不可用时，把"第二实现"替换为三种廉价等价物——历史版本/参考实现、等价变异后的自身、不变量属性**，并按成本分层部署。

**四层流水线**：

- **L0 确定性预处理（前置硬条件）**：固定种子/环境（借鉴 DT²"先控制非确定性再差分"）；对不可再生字段（nonce、时间戳、随机盐）在比对前做规范化/豁免（syrupy matcher/exclude 机制）。否则一切差分差异都无法归因。
- **L1 CI golden dataset（每次 PR，秒级~分钟级）**：把精选输入+期望输出存于持久位置，每个 PR 跑候选实现，出现非预期差异即构建失败。这是最轻量、收益最快的一层。
- **L2 历史全量回放（周期性/重大变更前，小时级）**：把确定性核心逻辑从传输层/副作用中剥离，包装成批处理变换，离线回放数月~数年历史输入，跑"当前实现 vs 候选实现"并产出可查询、可 diff 的差异数据集。Stripe 强调这不需要在线并行展开，是离线批量，正对应"不能 fan-out"的约束。
- **L3 定向扩展（按需）**：对 L1/L2 覆盖不到的盲区，用变异算子和属性测试定向生成新输入（见 6.4）。

**两条必须遵守的工程纪律（来自 Tardigrade 核验）**：

1. **差分测试必须走真实生产路径**：该 PR 评审中明确指出"生产派生 helper 被绕过、transcript 检查从未调用被测实现"属于假阳性路径——测试绿了但实际没有测到目标代码。落地时每个差分用例需断言"确实调用了被测 seam"。
2. **差分框架从项目第一天就建，且极简**（KConfigReader 经验）：输入空间小时直接用参考实现暴力枚举生成 ground truth，成本最低。

**加密制品的自差分策略**（Cryptofuzz 的启示）：即使只有一个实现，也可用**自差分**（同库不同代码路径对比）与**组合操作 oracle**（`decrypt(encrypt(m)) == m`、KDF 展开/提取链式一致性）获得差分信号，不需要第二个库。

### 6.3 历史回放与 golden dataset

**Golden dataset 的构建（Stripe 模板）**：

- **选取四象限**：常见主流程、资格/边界条件（如费率临界点）、历史事故案例、"小输入变化→大结果差异"的敏感案例。
- **Living specification**：每次事故暴露的漏网边界、每次迁移发现的细微差异，都固化为新用例存入数据集。这正好回答"黄金输出如何维护演化"——它不是静态快照而是单调积累的回归资产。
- **diff ≠ bug 的三分类**：Stripe 明确"完美匹配不总是目标"——差异可能是①有意行为变更 ②旧实现 bug ③真回归。流程上应产出**量化 diff 报告**（多少条记录变了、集中在哪个业务分段、由哪条规则触发），供人工分诊，而不是直接失败。
- **隐私边界**：回放输入最小化到决策相关字段，敏感标识符 token 化，期望输出/diff/日志不落 PII。对金融制品这是合规硬要求。

**回放输入的扩展（在历史实例之外）**：

- **反馈式变异**（LLM4FP）：把"曾触发过不一致/差异的历史成功实例"单独建库，对其做变异形成反馈循环，优先扩展最能暴露差异的输入方向。这是对 golden dataset 最廉价的增长方式。
- **历史实例作种子 + 结构变异**（mucerts/SBDT）：对结构化输入（金额配置、费率表、证书），用语法树模型保证变异后输入合法；mucerts 用 1K 变异证书触发差异为随机变体 14.5 倍，说明"种子质量 + 定向变异"远优于盲目生成。
- **预算引导**（Transcert）：若可插桩，用覆盖率信号决定保留哪些变异；黑盒制品则用 SBDT 的"搜索-更新-剪枝"代替覆盖率，更轻量。

**无历史流量时的退化方案**：用参考实现 + 小规模枚举（KConfigReader）或 RFC/标准官方测试向量（加密场景）充当初始 golden dataset；服务层制品可用 GoReplay 类录制回放，但纯逻辑制品应先剥离为可离线调用的纯函数形态。

### 6.4 变异/属性测试选型

**两类变异，用途不同，勿混淆**：

| 类型 | 对象 | 作用 | 代表 |
| --- | --- | --- | --- |
| **程序变异**（注入缺陷） | 被测制品代码 | 度量测试套件/oracle 的缺陷检出能力，定位验证盲区（存活变异体 = 盲区指示器） | mutmut（Python，v3.7.0 活跃）、Stryker（JS/C#/Scala） |
| **输入/调用序列变异**（语义保持） | 测试输入或 API 调用序列 | 直接制造差分验证信号，无需第二实现 | VizDetour 端点保持变异、SBDT/mucerts 输入变异 |

**端点保持变异：无参考实现时的首选差分机制（已核验）**。VizDetour 把 oracle 缺失问题转化为等价性检查：对种子执行追加一段"临时改变状态再恢复"的等价调用序列，正确实现下终态输出必须一致，任何差异即缺陷。三个算子可直接翻译到 R3 场景：

- **Set-Revert** → 金额计算：舍入模式设为 X 再设回原值后重算；加密：参数切换再恢复后重推密钥；
- **Redundant-Set** → 重复施加幂等操作（重复规范化币种、重复 trim）后输出应不变；
- **Remove-Readd** → 删除某费用分量再按原规则加回，总额应还原。

该机制零 fan-out、无需历史数据、判定只需一次输出比对（数值场景直接精确比对），且在 matplotlib/bokeh/plotly 上确认 39 个未知 bug。

**变异分析造 oracle**（Staats 等，ICSE 2012）：无参考实现时的关键替代路径——对被测系统生成变异体 → 用外部输入跑变异体 → 统计每个**中间变量**能在多大比例上暴露变异体缺陷 → 只对排名靠前的小变量集合定义期望值比对（缺陷检出最多提升 145.8%）。落地到金额计算：不比对最终账单，而比对"舍入后分量、适用费率、资格判定位"等关键中间量，人工成本大幅下降。

**属性测试选型**：Python → Hypothesis；Rust → proptest（均活跃）。核心属性按领域写——加密：加解密往返、密文/标签长度、已知向量命中、`HKDF-Expand(HKDF-Extract(...))` 链式一致；金额：守恒律（分账后合计=原额）、舍入一致性、交换/结合律（与求和顺序无关的场合）、幂等（重放同一笔计费结果不变）。**关键警示**（PROGRESS）：预言机若取自当前实现的执行结果，会把现存 bug 固化为预期行为（其实验中回归测试生成检出 0 个当前版本 bug）。属性必须来自规格/业务规则，不得从被测代码反推；LLM 生成 oracle 有同样警示（倾向捕获"实际"而非"期望"行为）。失败用例持久化回归（proptest-regressions / Hypothesis example DB），自然并入 golden dataset。

### 6.5 Oracle 选择与误报控制

**Oracle 优先序（从高到低）**：

1. **独立参考实现 / 已验证实现**：加密用 OpenSSL CLI 作进程外 oracle（Tardigrade 模式）或 EverCrypt/fiat-crypto 等已验证实现；金额用十进制库 + 可执行规格对拍。
2. **历史/当前生产实现**（current vs candidate，Stripe）——重构场景的首选。
3. **等价/往返关系**（端点保持变异、`decrypt(encrypt(m))==m`）——无第二实现时的主力。
4. **属性/不变量**（Hypothesis/proptest）。
5. **Golden 输出文件**：仅作回归护栏，不作正确性证明（实证警示：快照测试"只检测变化，不检测正确"）。

**误报控制清单**：

1. **Oracle 独立性**：oracle 侧的常量与中间值必须独立于被测实现的派生逻辑，否则"两边犯同一个配置错误时差分测试仍然绿"——这是 Tardigrade 评审反复强调的阻塞级问题。
2. **真实性检查**：差分用例必须实际执行被测 seam。
3. **Waiver 登记簿**：有意不支持/策略性不一致的能力，以 checked-in 注册表 + 书面理由 + tracking issue 管理，缺失不允许静默消失。
4. **正反例双向断言**：非法输入（坏 tag、坏签名）要求双方都拒绝，并检查失败路径的副作用（如明文缓冲被清零）。单向正例差分远不够。
5. **容差 oracle 慎用**：浮点/费用估算类中间量可用经验百分位容差（TAO）；但金额**最终值**建议保持最小货币单位的精确十进制比对，容差只作为估算类输出的豁免机制，且阈值用历史数据校准。
6. **反向变异评估 oracle 质量**：对断言式 oracle 施加变异，若判定结果不变则该断言形同虚设（SOFTENG 2017）。可做成季度性 oracle 体检。
7. **分诊而非自动判决**：L2 回放差异按"有意变更 / 旧版 bug / 真回归"三分类人工分诊；LLM 辅助分诊可参考 LLMShot，但高风险制品保留人工终审。
8. **差分信号的形式化解释**（DDYF 思路，本轮未能独立核验）：用协议/领域模型解释差异来源（如 RFC 条款映射），过滤实现细节级的伪差异。

### 6.6 方向三落地路线图

| 阶段 | 动作 |
| --- | --- |
| P0（1–2 周） | 剥离确定性核心为纯函数；建 golden dataset（主流程+边界+事故案例）入 CI；加密制品接入 RFC 向量 + OpenSSL 进程外 oracle；落实 oracle 独立性与正反例 |

## 七、综合建议：R3 级制品黄金输出与验证机制的统一设计

> 本节为在三个子代理建议基础上的综合，将三个方向的机制合并为一套可落地的统一参考架构。

### 7.1 统一参考架构（六层）

```
┌─ 层 1：环境固定与 manifest ─────────────────────────────────────────┐
│ 依赖锁定、环境 16 类变量固定、种子注入与派生、LLM 采样配置清单；      │
│ 每次运行产出 .r3info（仿 Debian .buildinfo），manifest 不一致则比对无效 │
├─ 层 2：规范化与不可再生字段处理 ────────────────────────────────────┤
│ matcher/redaction/模板剥离确证不可再生字段（剥离≠免责，需独立属性验证）；│
│ 金额固化十进制+舍入模式序列化；加密接入 RFC/KAT/NIST 标准测试向量       │
├─ 层 3：双轨比对 ───────────────────────────────────────────────────┤
│ 轨道 A 黄金输出比对（回归护栏）：快照/黄金文件 + 字节级精确比对；        │
│ 轨道 B 独立正确性预言机：蜕变关系、参考实现对拍、组合操作、校验和 oracle │
├─ 层 4：轻量差分验证（无 fan-out）────────────────────────────────────┤
│ L1 CI golden dataset（每 PR）→ L2 历史批处理回放（周期性）→            │
│ L3 定向扩展（端点保持变异 / 反馈式变异 / 属性测试）                     │
├─ 层 5：统计判定（无法逐位复现时）─────────────────────────────────────┤
│ SPRT 三值判定（INCONCLUSIVE 永不默认通过）+ 行为指纹 Hotelling T²；     │
│ 重跑预算按 Wilson 区间/规则三计算，长时监控用置信序列（少 50× 采样）    │
├─ 层 6：门禁与治理 ─────────────────────────────────────────────────┤
│ L0 manifest gate → L1 重放 gate（逐字节）→ L2 统计 gate → L3 漂移 gate；│
│ waiver 登记册、隔离区标签、FIC 归因锚点、黄金更新人工批准纪律           │
└────────────────────────────────────────────────────────────────────┘
```

### 7.2 七条统一原则

1. **黄金输出 ≠ 正确性证明**：黄金输出只是回归护栏，R3 制品必须叠加独立预言机（蜕变关系/参考实现/标准测试向量）构成双轨。
2. **先控制，再差分**：任何差异归因之前，先固定环境、依赖、种子、顺序、采样配置；剩余差异才可归因于行为变化。
3. **归因只认执行证据**：不依赖代码静态分析或 LLM 读码判定"随机还是偏差"；按 manifest → 重放 → 扰动 → 统计的决策树逐级归因。
4. **不可再生≠不可验证**：剥离字段必须另有属性验证（唯一性、长度、单调性）；随机性一次生成后固化为输入资产（两阶段记录）。
5. **期望基准与现状快照分账**：表征测试捕获的是现状，LLM 生成的断言倾向捕获实际实现——两者都不得直接充当期望基准；期望基准必须来自规格/业务规则并经人工批准。
6. **oracle 必须独立**：参考实现的常量、中间值、派生逻辑与被测实现隔离；正反例双向断言；差分用例必须真实执行被测路径。
7. **一切豁免显式化**：waiver 登记、期限与责任人、定期复审；禁止静默忽略差异、禁止自动静默通过。

### 7.4 关键风险汇总

- **工具成熟度**：AgentAssay、Reprise、agrepl 均为单作者早期项目——借鉴设计与协议、自研关键断言，勿在生产门禁裸依赖。
- **T=0 的实证边界**：含 LLM 采样的制品必须把"逐位复现"目标降级为统计/概率验证。
- **低频非确定性的预算现实**：10⁻³~10⁻⁴ 量级的问题需要数千至数万次执行才可靠检出，应放到夜间/周级批量任务。
- **LLM 预言机风险**：只能起草与分诊，不能批准与终审；数值敏感领域表现不稳，必须人工把关。
- **快照的脆弱性**：黄金标准需频繁更新，唯有"人工批准 + 独立证据 + 变异体检"能防止 bug 被固化。
