## 逐项精读

### A 档

**【A】RCC: Speculative Write Versioning with Redo Logs（2026-07）** — 利用 redo log 为写操作创建"推测式写版本"，将写写冲突事务在冲突点后流水线化为并发执行，配合提交时死锁检测与列级 redo log（RCC-C）消除假冲突；MySQL/PostgreSQL 上 TPC-C 吞吐提升一个数量级。直接回答"写冲突下如何用版本化提升并发度"，思想（推测版本+惰性提交+轻量回滚）对 Spec 细粒度版本化有直接借鉴价值。

**【A】MergirafSemi（2026-08）** — 用轻量具体语法树（CST）在部分区域做结构化合并、其余降级为行级合并，多阶段流水线（diff3→局部→全局），无需语言特定实现；五语言真实场景显著减少伪冲突。与"结构化 Spec 三方合并"高度契合，可直接借鉴的引擎级成果。

**【A】The Art of the Fugue（2023）** — 提出"最大非交错"正确性属性，指出既有 OT/CRDT 序列算法普遍存在交错劣化，给出满足该属性的 Fugue/FugueMax；性能接近 Yjs，是 Loro 文本 CRDT 的实现基础。对列表序列合并语义有奠基性指导价值。

**【A】JSON Schema Migration 指南（2026）** — 系统讲解 schema 版本化工程实践：区分破坏性/非破坏性变更、四种版本化策略（字段版本/请求头/URL/schema registry）、运行时 upcaster 与属性化测试。直接对应"Spec 版本控制"工程落地，契合度最高。

**【A】Loro（活跃）** — Rust/TS 高性能 CRDT，主打 JSON 协同+版本控制，原生支持时间旅行、可移动树/列表、浅快照（类 Git shallow clone），文本基于 Fugue。唯一把"版本控制+实时协同"作一等公民的 CRDT，最贴近"多 Agent 并发改 Spec+版本管理"需求形态，可作为底座。

**【A】Automerge（活跃）** — Rust 核心+WASM 的 JSON/树形 CRDT，v3 内存较 v1 降约 10 倍，提供 save/load/merge API 与压缩二进制，定位"local-first 的 PostgreSQL"。与结构化 Spec 数据模型最匹配，成熟度生态兼备。

**【A】Yjs（活跃）** — CRDT 事实标准框架，Shared Types（Map/Array/Text）、网络无关、支持离线/快照/undo、海量编辑器绑定与 provider 生态，被 Notion/Linear/Proton 采用。生态最成熟、文档最全，工程采用价值极高。

**【A】StructuredMerge Spec（活跃）** — 语言中立的"结构化文档合并"规范，定义可移植合并规则、结果形状、诊断与 review/replay 词汇，配套 Go/TS/Rust/Ruby 多实现与共享 fixture 语料。是"结构化 Spec 合并"的规范层成果，可作合并语义契约与测试基准。

**【A】Concurrency Control in Groupware Systems（dOPT/GROVE，1989）** — 首次提出 OT 形式化并发控制算法，用状态向量（vector clock）保持因果，定义因果保持与收敛两个一致性属性。本方向的源头，理解后续 OT/CRDT 的必备基础。

**【A】A Conflict-Free Replicated JSON Datatype（Kleppmann 2016）** — 首个将 map/list/register 组合为任意嵌套 JSON CRDT 的算法，用多值寄存器记录叶节点冲突，证明强最终一致与"无更新丢失"。结构化 Spec 数据模型的直接对应物，几乎所有 JSON 协同的理论根基。

**【A】Prevent Collaboration Conflicts with Fine Grained Pessimistic Locking（Eyl 2017）** — 为源码定义元模型（AST），在模型构件上做细粒度悲观锁，允许多人并行编辑同一类/同一方法而杜绝直接/间接合并冲突。与"细粒度悲观锁策略"最直接的一篇，思想可直接迁移到"在 Spec 结构节点上加锁"。

### B 档

**【B】ESBT（2026）** — 扩展 Stern-Brocot 树设计复合标识，约束序列 CRDT 标识无限增长，集成红黑树 O(log n)。针对标识膨胀痛点，对表格/列表类 Spec 有参考；但以 map 为主的 API Spec 适配度中等。

**【B】cMVBT（2026）** — 重设计多版本 B 树并发控制：乐观 latch 写、范围扫描无锁、无尖峰连续 GC。对"版本存储与扫描并发"有启发性，但属底层存储结构，距文档级 Spec 较远。

**【B】LLM vs. Search-based Merge（2026）** — 首次实证对比 LLM 生成式与搜索式两种冲突解决范式：LLM 善非均衡内容但泛化弱，SBSE 泛化强。聚焦冲突自动解决，对 Agent 语义级裁决有参考，但未涉及锁/版本化机制。

**【B】Living Databases（ICDE 2026）** — 用"快照图"（DAG）统一 schema 演化/版本化/物化视图/变换，支持分支合并、依赖级联版本化。概念与 Spec 版本管理相通，但偏数据库/愿景，落地较远。

**【B】Acumen（OSDI 2026）** — 首个提供强快照一致性的加密 CRDT 协作系统，用密码累加器实现可验证快照、防访问模式泄露。解决协作安全/可问责，与治理与验证相关，但核心是加密而非锁/版本控制。

**【B】ESSN（2025）** — 将可串行化判定分解为版本函数/版本序/已知全序三要素，放宽排除条件使更多事务安全提交，长事务中止率降约 50%。MVCC 可串行化判定的最新理论精进，对"何时允许并发提交"有理论价值，距文档协同较远。

**【B】2026 实时协作 CRDT 指南（2026-05）** — 韩文综述，系统梳理 Yjs/Automerge/Loro 对比、SaaS 生态、OT vs CRDT、Figma 架构。最佳地图式综述，用于快速建立生态全局观与选型决策。

**【B】ShareDB（活跃）** — 基于 JSON OT 的实时数据库后端，支持任意 JSON 文档并发协同、查询订阅、投影、历史版本访问与离线重连。OT 路线的成熟实现，可作"服务器权威+OT"替代方案参考。

**【B】Hocuspocus（活跃）** — Tiptap 团队打造的 Yjs 即插即用服务端，支持 WebSocket、SQLite/Postgres/Redis 持久化、鉴权扩展。是"Yjs 服务端托管"的标准方案，对落地服务器端有直接工程价值。

**【B】Liveblocks（活跃）** — 商业级"多人+AI 协同基础设施"，提供自有 CRDT、Yjs 适配、Presence/Awareness、AI Agent 支持。代表"协同即服务"成熟形态，但核心闭源 SaaS、自托管受限。

**【B】Replicache（已归档）** — Rocicorp"本地-优先同步引擎"，mutator+服务器权威+乐观 UI 模型，非 CRDT。代表"服务器版本校验+乐观回滚"路线，与 CRDT 收敛路线形成对照；仓库已归档。

**【B】Git（活跃）** — 分布式版本控制，分支/提交/三路合并/冲突标记。作为版本管理基线，任何 Spec 版本管理设计都需对齐；但本身不解决细粒度并发写入。

**【B】COT（Context-Based OT）** — 指出因果理论不足以满足 OT 正确性，提出以"操作上下文"为理论基础的 COT 控制算法。解决 dOPT puzzle 的关键控制算法，属背景理论。

**【B】Real Differences between OT and CRDT（2019）** — 解构 OT（并发中心）与 CRDT（内容中心）的正确性/复杂度/隐藏缺陷，指出 OT 在存量产品占主导、CRDT 优势被高估。选型决策关键对比文献。

**【B】Peritext（2022）** — 富文本 CRDT，将格式 span 与文字分离并以稳定标识锚定，使并发格式操作可交换。对带注释/格式的 Spec 有参考，但 Spec 多为 map/树结构，契合中等。

**【B】JSON CRDT with Move（2023）** — 在 Automerge OpSet 增加 move 操作，通过"最大 ID 获胜"+祖先检测保证无环无重复移动。为 JSON CRDT 补齐"移动/重排"语义，对 Spec 节点重排有价值。

**【B】MVTL（2019）** — 提出"锁时间戳而非锁对象/版本"的多版本时间戳锁，事务只需在对象集合上找到共同可锁时间戳即可提交，作为悲观锁与时间戳排序统一框架。与"平衡并发度一致性"密切相关，但实现复杂、偏事务数据库。

**【B】Sadoghi MVCC（VLDB 2014）** — kV-Indirection 结构，用逻辑/物理标识间接层支撑乐观与悲观 2 版本并发控制，降低索引维护、消除读写锁竞争。数据库 MVCC 减竞争代表作，偏存储层。

**【B】In-Memory MVCC（VLDB 2017）** — 在多核内存数据库 Peloton 实证评估 MVCC 四大设计决策（协议/版本存储/GC/索引）。版本管理设计权衡的权威实证基准。

**【B】SETTA 2022 Three-Way Merge（未能抓取）** — 基于标题判断：AST/结构化文档三方合并的自顶向下/自底向上/兼而有之方法论。与 Spec 合并相关，细节未核实。

**【B】Spork（2022）** — 基于 3DM 算法在 AST 上做 Java 三方结构化合并，显著减少伪冲突，格式保持比现有工具强 4 倍。结构化合并工程化范本，格式保持经验可借鉴；面向 Java 特定。

**【B】KAIST JSON OT** — 首次为 JSON 对象给出 OT 形式化基础（借助 n 叉树 OT），实现支持线性/树/JSON 三种结构的 OT 库。OT 路线扩展到 JSON 的早期严谨工作，学术实现、无活跃维护。

### C 档

**【C】NetEdit（未能抓取）** — 基于标题判断：协作编辑器实现案例，含 OT/并发控制实现与 dOPT 失效分析。历史性系统案例，信息已被更权威文献覆盖，价值有限。

## 逐项精读

### A 档

**【A】Merge-Bench（ICPR 2026）** — 构建 7938 个真实冲突 hunk 基准（1439 仓库、11 语言），ground truth 为开发者合并结果，免人工标注；用 GRPO 训练 14B 的 LLMergeJ，引入"免测试"合并评测范式。给出"LLM 自动解决合并冲突"的完整数据/评测/训练闭环，评测范式可迁移到 Spec 合并；最佳正确率仍 <60%，正适合本方向切入。

**【A】LLM vs. Search-based Merge（2026）** — 首次实证对比生成式（MergeGen/CodeT5）与搜索式（SBCR）合并：LLM 善内容不均衡冲突但易过拟合/长输入截断，搜索式泛化强但不生成新代码。对本方向"自动合并策略"选型有直接指导——Spec 合并应采"LLM 生成+规则/搜索校验"混合与人工确认。

**【A】MPAC（2026）** — 应用层协议，填补"多个独立 principal 的 Agent 并发改共享状态"空白：五层语义（Session/Intent/Operation/Conflict/Governance）、21 种消息、冲突为一级对象、pre/post-commit 执行模型与乐观并发控制，协调开销降 95%。几乎是对"多 Agent 并发改同一 Spec 库"问题的直接回答，协议层可直接借鉴。

**【A】MergirafSemi（2026）** — 用 CST + 选择性结构化解析 + 行级合并，在少假阳性与漏报间平衡，语言无关（Tree-sitter）。细粒度结构提升自动解决率。可作为 Spec 合并引擎的实现蓝本。

**【A】ConflictLens（SEKE 2025）** — 实证归纳 4 类语义冲突模式（双向：Overlap Contamination/Confluent Interference；单向：Assignment Override/Execution Perturbation），两阶段 LLM（静态定位+动态验证）达 0.91 精度/0.76 召回。最直接命中"语义冲突自动检测"——冲突模式分类可作 Spec 契约冲突判定模板，两阶段验证降误报极具借鉴价值。

**【A】FSTMERGE（ESEC/FSE 2011）** — 奠基性半结构化合并：在语法树层级用"注释化文法"声明式提供结构信息，自动解决排序冲突与部分语义冲突，实证 60% 场景减少 34% 冲突。语义合并引擎理论源头，其"通用性/表达力权衡+冲突 handler+非结构化回退"框架仍是核心参考。

**【A】Shen 2021: Are We There Yet?** — 系统实证对比文本/编译/动态三类冲突，指出 79% 编译冲突、75% 动态冲突现有工具完全无法检测，归纳开发者解决模式。清楚定位"语义冲突检测"盲区与机会，提供问题分类学与评测基准思路。

**【A】ASE 2024 Merge Tools Eval（Ernst 阵营）** — 大规模实测合并工具（Spork/IntelliMerge/Hi-res），引入"用测试校验合并正确性+计入错误合并成本+含已删分支"评测方法论，结论是简单方案（如增强 import 处理）常优于复杂算法。评测方法论与"简单胜复杂"洞见对设计取舍有直接指导。

**【A】oasdiff（活跃）** — 命令行比较并检测 OpenAPI spec 的 breaking/release 变更，支持 diff/breaking/changelog/validate，含 MCP server 接口。对字段类型改、参数增删、返回结构变化等 breaking 分类正是 Spec 语义冲突判定的现成方案，工程可直接采用。

**【A】oasdiff-action（活跃）** — oasdiff 的 GitHub Action 封装，PR 上直接拦 breaking change、发评论、可 gate 合并。把 Spec 语义冲突检测落到 CI 门禁的现成工程。

**【A】delimit-action（活跃）** — GitHub PR 上的 API 契约合并门禁：diffs OpenAPI/JSON Schema 与 base，分类 breaking、给 semver 建议与迁移指南，带 Sigstore 签名，号称"AI 写代码的 merge gate"，明确面向 AI/多 Agent 场景。几乎就是"并发改 Spec 时自动检测语义冲突并提示/拦截"的现成工程。

**【A】Mergiraf（活跃）** — 语法感知的 git merge driver，用语法树合并而非文本行，多语言多格式，v0.18.0 持续提交。可直接作为 Spec/YAML 等结构化文件的合并驱动集成。

### B 档

**【B】StateFuse（2026）** — 基于 OpSet/CRDT 复制合并的多 Agent 冲突感知内存契约，用 claim_id/claim_ref 保留显式冲突对象与纠错句柄，"保守保留矛盾而非过早塌缩"。对口"多 Agent 并发改 Spec"共享状态层，可借鉴冲突保留+可审计纠错；但面向 Agent 记忆而非 Spec 语义合并。

**【B】SINT-Flow（2026）** — 五个 LLM 操作符组装成工作流做端到端 schema 集成，含 Rollup/Drilldown 分层对齐与自一致性/复审回路，附 SINT-Bench（93 表）。"LLM 操作符编排+对齐+复审"模式可迁移到 Spec 结构对齐，但针对库表集成。

**【B】Gmerge 2021** — 用 GPT-3 k-shot 修复文本/语义合并冲突，Edge 分叉真实语义冲突上 SOTA 精度 64.6%，验证 LLM 零微调即可解语义冲突。经典参照，方法较老（2048 token 限制），作历史基线。

**【B】Mastery/SETTA 2022** — 提出"自上而下+自下而上"结合的结构化合并方法，把有序列表合并归约为约束图强连通分量拓扑排序，40533 场景优于代表工具。结构化合并算法层方法论，对合并引擎对齐/合并阶段有直接借鉴。

**【B】IntelliMerge（OOPSLA 2019，未能抓取）** — 基于程序单元图（PEG）的图式三路合并，检测/规避重命名等重构相关语义冲突。ASE 2024 实证其"适用场景少、易产生错误合并"，故为参考而非直接采用。

**【B】RefMerge（TSE 2023）** — 复兴并实现基于操作的重构感知合并，实证评估重构场景合并效果。对口"重构/改名导致的语义冲突"，操作级建模与评估方法可借鉴。

**【B】LLMatch（2025）** — 把 schema 匹配分解为准备/选表/列对齐三阶段，用 Rollup/Drilldown 分层匹配提升复杂多表对齐，附 SchemaNet 基准。对口 schema 对齐子领域，可迁移到 Spec 结构对齐，但针对库表。

**【B】cargo-semver-checks（活跃）** — Rust crate API 的 semver 破坏检测，基于 rustdoc JSON 做类型级兼容检查。展示"类型变更即契约破坏"的检测思路（字段/参数类型变），可借鉴其把类型级破坏建模成 lint/规则；仅限 Rust 生态。

**【B】JDime（经典）** — Java 结构化/半结构化合并工具（带 auto-tuning），支持 linebased/semistructured/structured 模式。FSTMERGE 学术路线成熟实现，可参考其结构化合并代码；针对 Java。

**【B】jFSTMerge（经典）** — FSTMERGE 工程实现，集成 git merge driver。半结构化合并实体参考，可借鉴驱动与冲突处理机制；活跃度低（2021 后停更）。

**【B】3dm-rs** — Rust 实现的 XML 3-way Diff/Merge（3DM 算法），结构感知、支持 move/copy 检测、可作 git merge driver。XML/YAML 树形 Spec 合并可借鉴其匹配与冲突判定（2026-01 停更）。

**【B】openapi-diff（活跃）** — Python 实现的 OpenAPI breaking 分类工具，三级严重度、扁平化 schema 比较、明确 breaking 判定规则。轻量、规则清晰，可直接改造成 Spec 语义冲突分类器（单人维护、无 release）。

### C 档

**【C】OT vs CRDT（2019）** — 实时协作编辑两大一致性技术路线对比。属实时编辑一致性之争，与"Spec 语义冲突检测"间接相关，仅作大背景。

**【C】Extensible CRDT（2022，未能抓取）** — 面向实时协同软件工程的 CRDT 框架。属数据层协同一致，与语义冲突检测关联弱，作补充背景。

**【C】CPL（2020）** — 规则化形式语言描述模型合并中的语法/语义冲突。规则化冲突表述思路可借鉴，但面向模型驱动工程、引用少，背景级。

**【C】SmartDiff** — 面向 Excel/XML 配置数据的语义 diff 与三路合并，ID 行匹配、单元格级语义合并。通用性弱、定位表格配置数据，"语义级三路合并+冲突分类"思路可作参考。

**【C】apidiff** — 语义 API diff，支持 OpenAPI/Swagger/Protobuf/GraphQL。概念对口且多格式，但仅 12 次提交、无 release、早期阶段，工程成熟不足。

**【C】Automerge / Yjs（本子问题下）** — 数据层 CRDT，解决"并发写入不冲突/可收敛"，是并发控制数据层基础，但**不含语义冲突检测**，与本子问题关联弱，作底层背景。

## 逐项精读

### A 档

**【A】Atomix（2026-02）** — 把 LLM Agent 的工具调用建模为"事务性副作用"，用 epoch 逻辑时间戳+每资源 frontier 进度门控决定何时安全提交，缓冲型副作用延迟到提交、外部化副作用在 abort 时逆序补偿；WebArena/OSWorld 注入故障下任务成功率从 0–7% 提升到 37–57%。本清单唯一直接命中"AI Agent 分布式事务+投机并发+冲突隔离"的论文，frontier 门控在投机分支间串行化冲突资源、无需全局锁，本质就是"把一批 Agent 操作作为一个事务波次提交"，与本方向核心问题高度重合。

**【A】Gray 1978: Notes on Data Base Operating Systems（未能抓取全文）** — 基于标题与公认内容判断：两阶段提交（2PC）首次正式提出，定义分布式节点原子提交协议。波次原子性（A）的直接理论源头。

**【A】Sagas（1987）** — 把长事务分解为可交错执行的子事务序列，失败时执行补偿事务语义撤销，牺牲强隔离换取非阻塞与可用性。Saga 模式源头，正是"长运行波次不用持锁、用补偿实现全有或全无"的范式。

**【A】Consensus on Transaction Commit（2004）** — 分析 2PC 协调者故障时的阻塞问题，提出用 Paxos 共识跑每个参与者 commit/abort 决策，得到 2F+1 协调者、任一 F+1 存活即可推进的非阻塞提交协议，2PC 为其 F=0 特例。为"波次提交在协调者崩溃时仍达一致"提供理论方案。

**【A】Percolator（OSDI 2010）** — 在无内建事务的 Bigtable 上叠加快照隔离+2PC+时间戳 Oracle+锁，实现跨行跨表 ACID，支撑 Google 网络索引增量处理。直接示范如何把一批增量变更作为原子事务波次提交，工程借鉴价值极高。

**【A】Spanner（OSDI 2012）** — 用 TrueTime 时钟 API 暴露时钟不确定性+Paxos 复制+2PC，实现全球规模外部一致（线性化）分布式事务、无锁只读与原子 schema 变更。为强一致波次边界提供权威设计。

**【A】Apache Seata（活跃）** — 分布式事务框架，TC/TM/RM 三角色，全局事务=一批分支事务，支持 AT/TCC/SAGA/XA 四模式。其"一个全局事务聚合一批分支事务、统一提交/回滚"模型几乎是"波次作为全局事务"的标准实现，可直接借鉴 XID 传播与分支协调。

**【A】Temporal（活跃）** — 持久化耐久执行平台，工作流自动处理故障与重试，Saga/补偿、幂等、信号内建。业界事实标准的"长运行工作流/Agent 编排"基础设施，是把"波次"作为可恢复工作流执行的成熟载体，强烈建议采用。

**【A】TiKV（活跃）** — Rust+Raft 的分布式事务 KV，事务模型源于 Percolator，提供快照隔离、SELECT...FOR UPDATE、外部一致分布式事务。作为"波次事务存储层"可直接落地跨行跨表 ACID，工程借鉴价值高。

### B 档

**【B】Distributed Sagas ICDCS 2023（二手讲义）** — 所给 URL 实为 Brown 课程讲义，覆盖 Saga 起源、2PC 阻塞/单点问题、编排式 vs 事件驱动、AWS Step Functions 案例，非论文原文。印证"无分布式锁前提下用 Saga 保证全局一致性"主题，但为二手材料，仅作参考。

**【B】Prefect 3.0 事务接口（2026，二手）** — CSDN 解读：3.0 引入 `@task(rollback=...)` 事务接口，为数据管道带来 ACID 语义，单步失败自动 rollback。与"一个波次的批量提交原子化"思想一致，可作数据管道侧工程参考；来源二手、面向批处理而非多 Agent 并发写 Spec。

**【B】DTM（活跃）** — Go 实现的跨语言分布式事务管理器，支持 Saga/TCC/XA/二阶段消息/Outbox/Workflow，覆盖 MySQL/Redis/MongoDB/Postgres，被腾讯字节采用。模式齐全是"把波次映射为不同分布式事务形态"的现成工具箱；但面向微服务数据一致性、无 AI/多 Agent 抽象，需适配。

**【B】saga-engine-go（2026）** — Go 崩溃恢复型 Saga 执行器，单张 PostgreSQL 表持久化状态、pg_try_advisory_lock 避免并发执行同一工作流、强制幂等键、逆序自动补偿、dead-letter 队列，"单进程单库、不做 2PC"。"单库+幂等+补偿+崩溃恢复"组合非常轻量，适合作为波次事务最小落地模板。

**【B】Gravtory（2026）** — Python 崩溃安全工作流库，宣称"零基础设施、Temporal 级可靠性"，checkpointed 持久化、精确续跑、幂等、Saga 补偿、LLM step/agent loops。"每步原子 checkpoint+精确恢复+Saga 补偿"正是波次原子性/持久性的工程实现思路，且内置 LLM/Agent 能力贴合场景；项目较新、AGPL 许可需注意。

**【B】kivo2/workflow-engine（2026）** — Kafka 电商 checkout saga 编排器，事务性 outbox 保证"状态变更与发消息原子提交"，幂等消费者+去重。outbox+幂等消费是"波次提交+可靠发布"成熟范式，适合作编排参考；面向电商。

**【B】Bernstein 1987（未能抓取全文）** — 基于标题与公认内容判断：并发控制与恢复权威专著，覆盖 ACID 隔离与持久，含 2PL、串行化、日志恢复。提供波次隔离（I）与持久（D）系统化理论，重要背景书。

**【B】Linearizability（1990）** — 线性化是最强实时一致性条件，与串行化结合成"严格串行化"，是并发对象/分布式存储正确性基准。为"波次提交应满足何种串行化语义"给出判定基准，属定义性/理论背景。

**【B】Distributed Sagas / Jepsen（2019）** — 把 Saga 形式化推广到异步网络分布式系统，证明子事务请求/补偿到达约束、逆序补偿等，研究第三方服务不可控时的可达性语义。为波次补偿协调在异步网络下的可达性提供形式化基础；偏理论。

**【B】MicroProfile LRA 规范** — LRA（Long Running Actions）用补偿而非锁，通过注解让一批 JAX-RS 服务共同参与一个"长运行动作"，活动取消时逐服务通知补偿。是"把一批服务作为一个协调单元一起提交/一起补偿"的工业规范，与"波次作为原子活动边界"几乎一一对应，是最贴近本方向的现成标准；偏 Java/Jakarta 生态。

**【B】Unit of Work（Fowler 2002）** — 单体应用层把一批受影响对象的变化作为一个业务事务统一协调落库并解决并发问题。是"波次本地原子边界"概念的直接来源；属模式文档，粒度小。

**【B】Cadence（活跃）** — 长运行工作流编排引擎，Temporal 前身，Cassandra/MySQL/PostgreSQL 后端。与 Temporal 思路同源，可作自托管/轻量替代或架构参考；主推方向已转向 Temporal。

**【B】CockroachDB（活跃）** — Raft+串行化隔离的分布式 SQL，构建于强一致事务 KV 之上。可作"波次事务强一致存储底座"，但定位为完整数据库而非事务框架，距多 Agent 写 Spec 场景较远。

**【B】Eventuate Tram Sagas** — Quarkus/JPA 编排式 Saga 框架（Chris Richardson 出品）。清晰教学实现，适合理解波次编排；维护放缓、无正式 release。

**【B】Axon Framework（活跃）** — DDD+CQRS+事件溯源框架，内建 Saga。事件溯源+Saga 可支撑"波次审计与补偿"，但重心在 DDD/事件溯源，与"波次映射分布式事务"直接关联较弱。

**【B】Narayana LRA（活跃）** — JBoss 事务中间件，含 XTS 与 compensations 模块，是 MicroProfile LRA 参考实现。若走 LRA 路线是现成参考实现，与"波次作为长运行动作"对应；偏 Java、复杂度高。
