# 多 Agent 并发修改 Spec 的并发控制与冲突解决机制 — 最终研究报告

> 完成日期：2026-08-15
> 研究方式：三方向并行检索 → 时效性/代表性审查 → 逐项精读评分（A/B/C 三档）→ 三子 Agent 独立成文建议 → 汇总

---

## 一、研究问题

**总问题**：如何设计高效的并发控制与冲突解决机制，以应对多个 Agent（或 Builder）并发修改 Spec（如 API 接口规范）时的语义冲突？

三个子问题：

1. **Spec 并发访问的锁机制与版本控制**：如何设计 Spec 的细粒度锁策略，平衡并发度与一致性？
2. **语义冲突的自动检测与合并策略**：如何自动检测两个并发 Spec 修改在语义上的冲突（如同一接口的不同契约变更：改字段类型、改参数、改返回结构），并提示人类或自动合并？
3. **波次（Wave）作为事务边界的实现**：如何将波次的概念映射为分布式事务，确保其原子性、一致性、隔离性和持久性（ACID）？

## 三、最终建议

以下建议由三个独立子 Agent 分别基于各自方向的 A/B/C 评分证据形成，本节为汇总版。

### 3.1 子问题一：锁机制与版本控制

**推荐技术路线：混合方案（短租约悲观细粒度锁 + MVCC 版本化底座 + 结构化合并兜底）**

不建议单走任何一条纯路线：

- 纯 CRDT 乐观合并不可行作主路线：CRDT 只保证数据层收敛、不含语义冲突检测；对 API Spec 这类契约文档，字段类型并发修改"自动收敛"恰恰是错误行为。
- 纯悲观锁不适合 Agent：Agent 任务长、可能崩溃，长期持锁会阻塞整个波次。
- 纯 MVCC 乐观并发在写冲突密集时中止率高，但 RCC（2026，A）证明"推测式写版本+惰性提交"可将写写冲突流水线化。

**具体机制设计**：

1. **四级锁粒度**：文档级 → 接口级（path+method）→ 字段级（schema property）→ 约束级（type/enum/required 叶属性）。默认加锁单元为接口级；只改单字段时降级为"接口意向锁+字段排他锁"，允许同接口不同字段并发修改（迁移 Eyl 2017 的构件级锁结论）。
2. **租约化锁**：所有锁带 TTL 租约 + 心跳续期，Agent 崩溃即自动释放；字段锁数超阈值时升级为接口锁，防止锁表膨胀。
3. **版本模型**：每节点维护 MVCC 版本链，读基于快照永不阻塞写；提交采用 RCC 的"推测版本+提交时校验"模式；跨节点约束（如 $ref 完整性）在提交点一次性检查；版本命名对齐 JSON Schema Migration 指南的四种策略，破坏性变更递增 major。
4. **冲突窗口兜底**：锁未挡住的并发写入，以 base 版本做结构化三方合并（MergirafSemi CST 引导 + StructuredMerge Spec 语义契约），合并结果过 breaking 检测门禁；判定语义冲突的生成结构化冲突对象留待人审，绝不静默覆盖。

**风险与权衡**：锁只防同节点并发写，跨接口的契约联动必须靠提交门禁兜底；锁粒度建议从接口级起步、按实测冲突率决定是否下探；租约 TTL 需与波次时长对齐；MVCC 版本链需定期 GC/快照压缩；若并发实测很低，可退化为"Git 分支+结构化合并门禁"的轻量基线。

### 3.2 子问题二：语义冲突的自动检测与合并

**推荐技术路线：四层流水线（规则检测 + 结构化合并 + LLM 裁决 + 协议协调）**

1. **检测层（确定性优先）**：oasdiff 的 breaking 规则对合并结果与 base 做三方 diff，直接分类"类型变更/参数增删/返回结构变化"；CI 侧用 oasdiff-action / delimit-action 做 PR 门禁（delimit-action 明确面向"AI 写代码的 merge gate"，自带 semver 建议与迁移指南）。
2. **合并层（结构化）**：Mergiraf（语法感知 git merge driver）集成进合并流程；MergirafSemi 已验证"轻量 CST 关键区域结构化合并、其余降级行级合并"可大幅减少伪冲突且语言无关。
3. **裁决层（LLM 混合）**：必须采用"LLM 生成 + 规则/搜索校验"混合（LLM vs. SBSE 实证结论），而非纯 LLM。
4. **协调层（协议）**：采用 MPAC 作为多 Agent 协调协议——五层语义（Session/Intent/Operation/Conflict/Governance）、21 种消息、冲突为一级对象、乐观并发控制，实测协调开销降 95%、墙钟加速 4.8 倍。

**具体机制设计**：

- **冲突分类法**：以 ConflictLens 实证归纳的四类模式为模板迁移到 Spec 契约场景——双向的 Overlap Contamination（一方删/改字段，另一方新接口引用它）、Confluent Interference（两方各改一个被同一逻辑共用的 schema），单向的 Assignment Override（枚举/默认值被静默覆盖）、Execution Perturbation（校验规则被另一方改变）；其上叠加 oasdiff 的 breaking/non-breaking 作严重度维度。
- **三道检测闸**：①操作前——MPAC 要求 intent declaration 前置，提前发现意图级冲突；②合并时——结构化合并产出冲突对象；③提交后——CI 中 breaking 检测 gate 合并。
- **自动合并条件（仅三类）**：结构不相交区域；双方均 non-breaking 且不触及同一节点；低风险且通过双重校验（oasdiff 复核 + 契约测试）的 LLM 裁决结果。
- **降级人工判据**：任何 breaking 命中；ConflictLens 式动态验证（LLM 生成针对性测试跨分支执行）确认冲突；双方 intent 语义矛盾；LLM 多次采样不自洽。降级时生成 MPAC 一级结构化冲突对象，进入 Governance 层人工仲裁队列。

**风险与权衡**：Merge-Bench 实测最优 LLM 合并正确率仍 <60%，LLM 只能做"提案+校验"，breaking 类冲突不应全自动合并；ConflictLens 召回 0.76，约 1/4 语义冲突会漏检，必须规则层兜底；结构化合并粒度越细漏报风险越高，默认保守可配置；ASE 2024 结论"简单方案常优于复杂算法"——优先用规则覆盖高频冲突类型，LLM 只处理长尾；oasdiff 仅覆盖 OpenAPI，非 OpenAPI Spec 可从 openapi-diff（B 档）规则起步改造。

### 3.3 子问题三：波次（Wave）作为事务边界

**推荐技术路线：Temporal 编排波次（控制面）+ Percolator/TiKV 式快照隔离事务承载提交（数据面）+ Saga 补偿处理外部化副作用**

选型结论（均有 A 档证据支撑）：

| 路线 | 角色 |
| --- | --- |
| Temporal | 控制面首选：耐久执行、自动故障恢复、内建 Saga 补偿与幂等，编排波次生命周期，支撑人工裁决等长步骤 |
| Percolator/TiKV | 数据面首选：快照隔离+2PC+时间戳 Oracle，波次=一个大事务，写写冲突判定下沉存储层，最"原生"的 ACID 落地 |
| Apache Seata | 若修改落在关系型服务/库上，"全局事务=一批分支事务"模型与波次一一对应，可直接套用 |
| Saga 补偿 | 仅用于波次内不可缓冲的外部化副作用兜底，不作主路径 |
| 2PC/XA 裸用 | 避免跨服务裸用 |

**具体机制设计（波次生命周期，参照 Atomix 事务模型）**：

1. **收集**：Agent 修改写入波次暂存区，每条修改携带 `(epoch, wave_id)`。按 Atomix 副作用二分法：可缓冲副作用（文件/存储写入）延迟到提交点才可见；外部化副作用（远程 API、通知）立即执行但登记补偿句柄与幂等键。
2. **冲突裁决**：先写写冲突检测（存储层乐观并发控制），再语义冲突检测（借用方向二的 oasdiff breaking 分类 + ConflictLens 四类模式），裁决路径：自动合并 → LLM 裁决 → 人工审。
3. **原子提交（frontier 门控）**：采用 Atomix 提交谓词——仅当波次触及的每个资源（接口/schema 节点）的 frontier 推进到不低于本波次 epoch 时方可提交（"确认没有更早的未完成工作还会到达"）。该机制按资源串行化冲突 Agent、无需全局锁，不相交资源的波次仍可并行；提交本身以存储层 2PC 完成。
4. **失败补偿**：abort 时按依赖逆序执行补偿；可缓冲副作用直接丢弃；不可逆副作用（已发通知/已生成产物）应被门控——推迟到提交点之后或要求人工批准；全流程日志化以支持崩溃恢复与审计。

**风险与权衡**：2PC 协调者故障会阻塞参与者（Paxos Commit 证明可用共识消除，工程上可用 Temporal 耐久状态承担协调者职责）；Saga 弱隔离可能出现中间态可见——故 Saga 只做兜底，主提交路径坚持快照隔离；Atomix"安全优先于活性"，frontier 停顿换一致性，需监控停滞并设超时回收；波次过大拉长裁决时长、过小丧失批量裁决优势，建议按业务单元切分；不可逆副作用无法真正回滚，只能门控前置，需在协议层向用户显式声明。

## 四、总体架构建议（三个子问题的整合）

将三个子问题的建议整合为一个分层架构：

```
┌─────────────────────────────────────────────────────┐
│  协议层：MPAC（intent 前置声明 / 冲突为一级对象 /      │
│         乐观并发 / 人工仲裁 Governance）              │
├─────────────────────────────────────────────────────┤
│  编排层：Temporal（波次生命周期：收集→裁决→提交→补偿）  │
├─────────────────────────────────────────────────────┤
│  并发控制层：MVCC 节点版本链（读不阻塞写）+            │
│             短租约细粒度锁（默认接口级，可降字段级）    │
├─────────────────────────────────────────────────────┤
│  冲突处理层：结构化合并（Mergiraf/MergirafSemi）+      │
│             breaking 检测门禁（oasdiff/delimit）+     │
│             LLM 裁决（提案+校验，非全自动）            │
├─────────────────────────────────────────────────────┤
│  事务/持久层：frontier 门控提交 + 存储层 2PC 快照隔离   │
│             （Percolator/TiKV 或 Seata 全局事务）      │
└─────────────────────────────────────────────────────┘
```

**关键设计原则**：

1. **锁管并发、版本管读、门禁管语义**：细粒度锁只防同节点写写冲突；语义一致性一律由提交点的结构化合并+breaking 检测兜底——两者职责严格分离。
2. **波次是唯一的原子边界**：所有 Agent 修改只在波次暂存区可见，提交点（frontier 门控 + 存储层事务）之前对外不可见；外部化副作用必须登记补偿或推迟到提交后。
3. **LLM 只做提案，规则做闸门**：鉴于 LLM 合并正确率 <60%，任何 breaking 类冲突必须经过确定性规则检测与（可选）动态验证，自动合并范围收敛到"结构不相交 + 双 non-breaking"两类。
4. **人审是一级公民**：冲突不是异常而是协议对象（MPAC），降级路径清晰：自动合并 → LLM 裁决 → 人工仲裁，全链路留痕。
5. **从简单基线起步**：若初期并发压力低，可用"Git 分支 + Mergiraf 结构化合并 + oasdiff CI 门禁"的最小组合起步，再按实测冲突率逐步引入锁层、波次事务层（ASE 2024 的"简单胜复杂"结论）。

**最小可行原型（MVP）建议**：

1. 存储：以 Git/结构化文档仓库存放 Spec，启用 Mergiraf 作为 merge driver。
2. 门禁：CI 接入 oasdiff-action / delimit-action，breaking 变更必须人工批准。
3. 协调：实现 MPAC 的 intent 声明与结构化冲突对象子集，Agent 修改前先声明意图。
4. 波次：以 Temporal 工作流定义"收集→裁决→提交→补偿"四阶段，第一版可用单库（saga-engine-go 模板）承载状态。
5. 演进：并发压力上升后，将锁层（接口级租约锁）与版本层（MVCC 节点链）引入，数据面迁移到 Percolator/TiKV 式事务存储。
