## 二、专题一精读总结：动态前缀缓存与智能检索

> 子问题：如何根据当前 Spec-delta 和任务，动态地从代码库检索最相关的上下文（而非全量）？

### A 档（采用价值高）

**1. SGLang（RadixAttention）** — 跨请求复用共享前缀 KV cache 的 radix 树系统，LRU 淘汰 + cache-aware 调度，吞吐提升高达 6.4x。前缀缓存理论+技术基石，可直接作为智能检索+前缀缓存方案的技术基座。**A**。代码：https://github.com/sgl-project/sglang

**6. EPIC（Position-Independent Caching）** — 位置无关上下文缓存，用 LegoLink 缓解 attention sink 效应，使 KV 可在任意前缀后模块化复用，TTFT 提升最高 8x。突破"共享前缀"硬性要求，对"动态拼装检索片段"场景尤为关键。**A**。

**11. SGLang（项目）** — RadixAttention 官方开源实现，前后端一体推理框架。同条目 1，可直接落地。**A**。代码：https://github.com/sgl-project/sglang

**10. vLLM（APC）** — 主流定制推理引擎，自 v0.4.0 支持自动前缀缓存，按块缓存复用共享前缀。落地前缀缓存的事实标准，是"控制 token 成本"最直接的工程底座。**A（近3个月活跃）**。代码：https://github.com/vllm-project/vllm

**15/30. RepoCoder** — 迭代检索-生成（RG）框架 + RepoEval 基准，把检索结果反馈进下一轮检索，显著优于单次检索。仓库级检索-生成奠基工作。**A**。代码：https://github.com/microsoft/CodeT/tree/main/RepoCoder

**17. Repoformer** — 选择性检索 RAG 框架，自监督训练让模型判断"是否需要检索"，主动放弃不必要/有损检索，在线提速 70%。直接贴合"智能检索而非全量"主旨。**A**。

**22/32. CodeRAG（KDEGroup）** — EMNLP 2025，log-prob 引导查询构建 + 多路径检索 + BestFit 重排，聚焦"相关且必要"知识。同时优化查询构造与去冗余重排，有官方实现。**A**。代码：https://github.com/KDEGroup/CodeRAG

**23/33. RepoGraph** — 行级代码依赖图（定义/引用关系），作为 agent 即插即用导航模块，plug 进四种方法均提升 SWE-bench 性能（ICLR 2025）。工具版含增量缓存与 MCP。**A**。代码：https://github.com/ozyyshr/RepoGraph ；https://github.com/algorisys-oss/repograph

**25. Hierarchical Context Pruning (HCP)** — 函数级建模仓库，保留拓扑依赖同时剪掉无关函数实现，显著压缩仓库级补全输入。直接压缩上下文、删除无关代码，与 token 成本直接挂钩。**A**。代码：https://github.com/Hambaobao/HCP-Coder

**27. Practical Code RAG at Scale** — 计算预算下比较分块/打分/粒度：PL-PL 用稀疏 BM25 + word 级拆分最优且快一个数量级。给出可操作、有证据的检索设计选择。**A**。

**28. SWE-Pruner** — 面向编码 agent 的自适应上下文剪枝，轻量 neural skimmer（0.6B）按任务目标动态选行，SWE-Bench Verified token 减 23-54% 且成功率不降反升。**A（近3个月有代码）**。代码：https://github.com/Ayanami1314/swe-pruner

**29. LaMR（Multi-Rubric Latent Reasoning）** — 结构化剪枝框架，把相关性分解为"语义证据+依赖支撑"两个可解释维度，各用独立 CRF 建模，多轮任务省最多 31% token。**A（偏B+）**。

**31. AutoCodeRover** — 自动解决 GitHub issue 的 agent，通过代码库检索/搜索定位补丁位置。完整开源 agent 检索路线，可直接借鉴其定位/检索流程。**A（近3个月活跃）**。代码：https://github.com/AutoCodeRoverSG/auto-code-rover

**34. CodeContext** — C# CLI + MCP server，把代码库转成面向 LLM 的结构化上下文，含 token budget 优化、基于任务描述的相关性打分与多种选择策略（GreedyByScore/ValueOptimized/Balanced）。直接实现"按任务动态选上下文 + token 预算约束"。**A（近3个月活跃）**。代码：https://github.com/DavidVeksler/CodeContext

**36. CORVUS** — 针对"高频变动代码库"，解耦文件读取与其观察，维护同步的"相关文件注册表"，每推理循环只注入当前内容，消除陈旧快照与重复读文件，每任务输入 token 降 9-50%。**对"高频变动"最直接命中，最高优先级 A（2026-07-20）**。

**37. Cat（Context as a Tool）** — 把上下文维护提升为可调用的一等工具，结构化 context workspace（稳定任务语义+浓缩长期记忆+高保真短期交互），SWE-Bench-Verified 57.6% solved。克服 append-only 与被动压缩局限。**A**。

**38. CoMEM** — 将内存管理与主 agent 解耦并行执行，k-step-off 异步流水线掩盖压缩延迟（1.4x 延迟提升），奖励驱动训练内存模型。SWE-Bench-Verified 验证。**A（2026-05-29）**。代码：https://github.com/horizon-llm/CoMem

**39. Context Rot（Progressive Prompt Ephemerality）** — 诊断"上下文腐败"——累积无关内容挤占上下文导致输出退化，提出分层架构 PPE（系统指令永久缓存、会话历史增量摘要、当前轮临时化）。证明"必须精简上下文"的核心动机证据。**A（2026-06-15）**。

**40. CocoIndex** — 增量索引框架，保存时对 AST 做 diff，仅对变更函数重新 embed、未变函数保留 embedding，避免全仓库重建。**直接解决"高动态代码库缓存失效/增量索引"，成熟可落地**。**A（近3个月活跃）**。代码：https://github.com/cocoindex-io/cocoindex

**42. Append-Only Coding** — 论证 append-only 上下文 vs 多上下文切换对 prompt cache 命中率的影响（对话 99%+ vs 编程 88-94%），提出让 agent 输出 diff 指令而非整文件以保持前缀命中。**与"缓存命中率+高频变动"直接相关，附实测**。**A（偏B+，2026-07-17）**。

**45. PACMS** — 预算感知子模函数在候选上下文池中做预算约束的覆盖最大化选择，作为 agent 即插即用上下文选择引擎，替代 recency 截断。**A（偏B+，2026-06-18，无代码）**。

### B 档（中等）

**2. CacheBlend** — RAG 中非前缀片段的"选择性 KV 重算"融合，TTFT 降 2.2-3.3x。解决动态拼装场景但属 KV 层优化。**B**。代码：https://github.com/LMCache/LMCache

**3. Prompt Cache** — prompt module 可复用片段 schema，模块化注意力复用，首 token 延迟降 8-60x。**B**。

**4/12. Mooncake** — KVCache 分离式架构，聚合空闲 CPU/DRAM/SSD 做分布式缓存，长上下文吞吐提升最高 525%。最接近生产可用的前缀缓存架构。**B（偏A工程参考）**。代码：https://github.com/mooncake-labs/mooncake

**5. HotPrefix** — SIGMOD 2025，热度感知 KV 调度（动态热度追踪+选择性准入），比 vLLM 延迟降 2.25x。"前缀热度长尾分布"支撑"哪些上下文值得缓存"决策。**B**。

**7. KVShare** — 语义感知多租户 KV 缓存共享，hash 识别可复用片段，TTFT 降最高 9.39x。**B**。

**8. KVCache in the Wild** — 大规模云厂商真实负载刻画，发现复用偏斜、命中可预测。为"高频变动缓存命中率"提供实证依据。**B**。

**16. RepoBench** — 仓库级代码补全基准（检索/补全/流水线三子任务），评估检索质量的标尺。**B**。

**18. RepoHyper** — Repo-level Semantic Graph + Expand-and-Refine 检索，提升上下文检索质量。**B+（偏A）**。代码：https://github.com/FSoft-AI4Code/RepoHyper

**19. GraphCoder** — 代码上下文图（CCG）粗到细检索，提升跨文件上下文选择，EM+6.06。**B+**。

**20. CodeGRAG** — 控制流/数据流代码块图 + GNN 软提示，图结构检索增强代码生成。**B**。

**21. CodeRAG-Bench** — 系统评测"检索能否增强代码生成"，发现当前检索器在低词汇重叠时仍难取到有用上下文。**B**。

**24. DraCo（Dataflow-Guided RAG）** — 扩展数据流分析建立 repo 上下文图，精确检索生成 well-formed prompt，EM+3.43%。**B+**。

**26. MRG-Bench** — 多语言仓库级代码生成基准，实证不同语言上下文需求差异显著。**B**。

**35. CodePromptZip** — token 感知代码压缩，5 类 token 类型感知贪婪删除，41% token 削减、12% 性能损失。**B+**。

**41. Engineering Handbook** — hybrid 检索 + 动态索引新鲜度策略（commit SHA 惰性失效、优先重索引打开文件）。系统级、可操作。**B+（近3个月）**。

**43. dscache** — DeepSeek prefix-cache 命中率可视化工具，给出前缀重排建议以保缓存折扣。缓存失效的工程观测工具。**B（近3个月活跃）**。

## 三、专题二精读总结：长上下文模型利用与智能压缩

> 子问题：如何评估和利用支持长上下文的模型，并对上下文进行智能压缩（如通过摘要、检索增强）？

### A 档（采用价值高）

**1. RULER** — "有效上下文长度"概念，量化模型真实可用长度。评估压缩/检索后模型是否仍保住长上下文能力的标杆工具。**A**。代码：https://github.com/hsiehjackson/RULER

**2. LongBench** — 中英双语多任务长上下文基准，事实标准之一。**A**。代码：https://github.com/THUDM/LongBench

**3. ∞Bench (InfiniteBench)** — 100K+ 超长文本评测，直接推向真实长文档/代码库场景。**A**。代码：https://github.com/openbmb/infinitebench

**4. Long Code Arena** — 唯一聚焦"代码长上下文"的专设基准（仓库级/库级补全、跨文件依赖）。**A**。代码：https://github.com/JetBrains-Research/lca

**10. ReCUBE** — 仓库级上下文利用率评测 + CCE 依赖图工具，指出既有基准（∞Bench/SWE-bench/Commit0）缺陷，GPT-5 全上下文仅 37.57% 严格通过率，CCE 最高提升 7.56%。**A**。代码：https://github.com/JiseungHong/ReCUBE

**11. SWE-bench** — 真实 GitHub issue 修复基准，编码 agent 上下文管理的终极评测场。**A**。代码：https://github.com/SWE-bench/SWE-bench

**12. Do Context Files Help Coding Agents?** — Claude Code/Codex 上 288 次受控消融，用等价性检验得出"策略不显著改变正确率"的零结果，失败主因是实现技能而非缺失仓库知识。**对"上下文注入策略"给出关键反例，A（2026-07-28）**。

**13. Evaluating AGENTS.md** — AGENTbench 138 实例，LLM 生成上下文文件平均降成功率约 3%、推高推理成本 20%+，开发者手写文件仅微升 4%。**A**。代码：https://github.com/eth-sri/agentbench

**14. LLMLingua** — 粗到细 prompt 压缩奠基作，用困惑度信号估计 token 重要性。**A**。代码：https://github.com/microsoft/LLMLingua

**15. LLMLingua-2** — 压缩建模为 token 分类任务，数据蒸馏 + 双向编码提升保真度。**A**。代码：https://github.com/microsoft/LLMLingua-2

**16. LongLLMLingua** — 面向长上下文+检索场景的压缩，解决成本、位置偏差与关键信息密度。**A**。

**18. RECOMP** — 训练"信息冷凝器"压缩检索文档，首次把压缩与 RAG 显式结合。**A**。代码：https://github.com/cxcoding/RECOMP（正确 arXiv:2310.04408，文件 2312.10997 为 RAG 综述号，已勘误）

**23. Acon** — 统一压缩框架压缩环境观察与交互历史，压缩准则自然语言空间梯度无关优化，峰值 token 降 26-54% 且保持/提升成功率。模型无关、工程可落地。**A**。

**24. Cat** — 专为 SWE agent 设计，把压缩变成模型主动能力，SWE-Bench-Verified 57.6%。**A**。

**25. RAG or Long-Context LLMs?** — 系统对比 RAG 与长上下文，提出 RAG-or-LongContext 混合决策方案，可按情境调整"检索比例"。给出可量化决策框架。**A**。

**27. RAG Survey (Gao et al.)** — RAG 三阶段范式导航综述，含压缩相关内容。**A**。

**31. A Survey of Context Engineering** — 将上下文工程正式化，组件层+实现层两级分类，上下文管理总纲。**A**。

**34. CoMEM** — 解耦长上下文内存模型，异步 k-step-off 流水线掩盖压缩延迟，LRL 奖励驱动训练。SWE-Bench-Verified 验证，代码开源。**A（2026-05-29）**。代码：https://github.com/horizon-llm/CoMem

**35. Context Rot** — 诊断上下文腐败，白盒代码审计量化 onset/频率/严重度，证明不加管理的长上下文会主动腐烂。**"为何必须压缩"的最直接证据，A（8-01）**。

**36. MemGPT** — 上下文窗口类比为 OS 内存，显式 memory 函数搬运数据，记忆分层奠基作。**A**。代码：https://github.com/cpacker/MemGPT（现 https://github.com/letta-ai/letta）

**37. Mem0** — 开源通用 Agent 记忆层，User/Session/Agent 多级记忆，生产级成熟。**A**。代码：https://github.com/mem0ai/mem0

**39. Agent 压缩综述** — 三维分类 + 三类失败模式（F1 压缩前决策错误/F2 压缩中信息丢失/F3 压缩后访问失败），对工程规避错误极具价值。**A（2026-05-28）**。代码：https://github.com/YerbaPage/Awesome-Context-Compression

**40. Learning by Distilling Context** — 上下文蒸馏开创性工作，把上下文增益内化进参数。**A**。

**43. OPCD (On-Policy Context Distillation)** — 微软，把 on-policy 蒸馏与上下文蒸馏结合，解决 off-policy 暴露偏差。**A**。代码：https://aka.ms/opcd-code

**44. OPSDL** — 百度，用模型自身短上下文能力作 self-teacher，token 级反向 KL，RULER 上 7B-32B 一致提升。**A**。

### B 档（中等）

**5. BABILong** — 百万 token 文档中的事实链路推理压力测试。**B**。

**6. LongBench 批判** — 去混淆指标（long-context gain），方法论价值高。**B**。

**7. LongPPL** — 比 PPL 更可靠的长上下文度量。**B**。代码：https://github.com/PKU-ML/LongPPL

**8. Marathon** — 同场对比"长上下文 vs 压缩 vs RAG"，长上下文语言建模更优但代价更高。**决策关键证据，B（评测性质）**。

## 四、专题三精读总结：Cartographer 工具与上下文隔离

> 子问题：Cartographer 如何在不污染主流程缓存的情况下，为定位、检索等任务提供高效服务？
> **重要**：本专题存在两个同名"Cartographer"实体，已分别精读评分。

### A 档（采用价值高）

**1. PEEK（学术源头：Cartographer 组件）** — 把可复用"定向知识"缓存为常驻 system prompt 的恒定大小 context map，由 Distiller（提取知识）、**Cartographer（把知识转成结构化 ADD/DELETE/REPLACE 编辑）**、Evictor（强制固定预算）协同维护。长上下文推理比强基线提升 6.3-34.0%、减少 93-145 次迭代、成本降至 ACE 的 1/1.7-5.8。**本专题学术核心，最高优先级 A（2026-05-19）**。代码：无公开（arXiv 2605.19932）。

**2. Icarus-afk/Cartographer「Repository Intelligence OS」** — 把代码库转成可导航语义知识图谱，提供 CLI + 15 工具 MCP server（search/impact/neighbors/path/file_summary/context），图查询替代整文件读取，`file_summary` 省 90% token、`summarize` ~98.8%，22 个真实仓库实测。索引独立 SQLite + 增量 watch，完全隔离于 agent 主流程。**工程成熟度高，A（2026-06-29）**。代码：https://github.com/Icarus-afk/Cartographer（MIT）。**注意：与 PEEK 的 Cartographer 组件是不同实体**。

**5. AgentSys** — 受 OS 进程内存隔离启发，worker 在隔离上下文执行、可递归嵌套，只有 schema 校验的 JSON 返回值能越过隔离边界。隔离单独即可把攻击成功率降到 2.19%。**"子任务不污染主流程"的范式论文，最高优先级 A**。代码：https://github.com/ruoyaow/agentsys-memory

**6. CodeDelegator** — 规划与实现角色分离，持久 Delegator 只分解/写规格/监控，每个 Coder 带干净上下文（屏蔽先前失败），EPSS 隔离执行状态。**代码-as-动作场景下防止调试污染主上下文的直接方案，A**。

**7. FastContext** — 把"仓库探索"与"求解"分离的专用探索 subagent，按需并行读取/搜索，只返回 file-and-line 紧凑实证，SWE-bench 分辨率提升最高 5.5%、主 agent token 降最高 60%。**方法层面 A；注意：论文已因产品 IP 撤回（v4），官方仓库下架（2026-06-30），方法论仍有效**。

**11. memex RFC #256** — OS 式进程内存隔离的子任务委托：child context 写入默认不向父传播，schema 校验返回值才越过边界，支持嵌套与 sandbox。**"不污染主流程缓存"的落地设计蓝本，A（2026-07-21）**。

**18. Synaptic（graphify 真实实体）** — tree-sitter 构建可查询持久化代码知识图谱（符号+类型化边+置信度标注），30+ 语言，MCP server 供给多种 agent，token 经济。**工程成熟度高（210 commits，活跃至 2026-08-15），A**。代码：https://github.com/ColinVaughn/Synaptic

## 五、关键结论与决策线索

### 1. 答案"如何不污染主流程缓存"（专题三，最核心）

- **理论范式**：AgentSys（OS 式隔离）、CodeDelegator（角色分离+EPSS）、FastContext（探索/求解分离）、memex RFC（隔离默认+promote 显式）。
- **工程实现**：Synaptic、CodeGraph、Icarus-afk/Cartographer（语义知识图谱 + MCP，图查询替代整文件读取）。
- **学术源头**：PEEK 的 Cartographer 组件——把知识转成结构化编辑，维护固定预算 context map，本身即"不进入主流程的定向缓存"。

### 2. 答案"动态检索最相关而非全量"（专题一）

- **选择性/任务感知**：Repoformer、SWE-Pruner、LaMR、PACMS、CodeContext（token 预算内选最相关）。
- **增量索引解决高频变动**：CocoIndex（AST diff 增量 embed）、CORVUS（解耦文件读取+同步注册表）、Append-Only Coding（维持前缀命中）。
- **缓存系统底座**：SGLang/vLLM（前缀缓存宿主）、EPIC（位置无关缓存）。

### 3. 答案"评估与智能压缩长上下文"（专题二）

- **评估**：RULER、LongBench、∞Bench、Long Code Arena、ReCUBE、SWE-bench。
- **压缩**：LLMLingua 系列、Acon、Cat、CoMEM、Context Rot（必须压缩的动机）。
- **反直觉实证**：AGENTS.md 两篇消融证明静态上下文注入未必提升正确率——**提示应聚焦"动态、任务感知"而非"静态全量注入"**。

### 4. 交叉结论

三个子问题的答案高度收敛于同一架构：**用独立的、隔离的上下文服务（图检索/增量索引/压缩工具）在主流程之外提供按需、紧凑、新鲜的上下文**，主流程只接收 schema 校验后的小体量结果。这正是 PEEK/Cartographer、AgentSys、Synaptic/CodeGraph/CocoIndex 共同指向的方向。
