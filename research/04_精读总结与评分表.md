# 01 自然语言与形式化契约融合机制

> 子问题：如何将 L1 业务意图（自然语言）自动转化为 L2 开发契约（可执行验证的契约）？

## 一、论文（22 篇）

### A. NL→形式化规格（LLM 方法）— 本子方向核心

**1. [重大] Can LLMs Write Correct TLA+ Specifications? — A**
- 定位：首个系统评测 30 个 LLM（8 家族、205 条 TLA+ 规范）做 NL→TLA+ 生成、并经 SANY+TLC 验证打分的权威基准研究。
- 核心贡献：用 SANY（句法）+TLC（语义）双验证器打分，得出句法正确率最高仅 26.6%、语义正确率仅 8.6%；归纳 5 类幻觉模式（错误操作符、遗漏约束、时序误用等）。关键结论：LLM 生成规格"语法尚可、语义不可信"，必须接验证器闭环。
- 采用建议：其评测方法论与 5 类幻觉模式可直接用于我们 Spec 语言的生成质量评估与错误分类。

**2. [近3月] TLA+-Bench — A**
- 定位：以"跑模型检验器"精确打分的执行级 NL→TLA+ 基准与数据集。
- 核心贡献：提供 403 条 gold + 897 条 silver 配对数据；提出 "correctness envelope" 概念——仅改变评分选择，同一批输出的正确率可在 10.0%~1.7% 间六倍波动。关键结论：评估口径对结论影响巨大，必须明确"机器可执行验证"的评分定义。
- 采用建议：其"执行级打分 + correctness envelope"方法论直接决定我们 Spec 语言评测基准的设计口径，可照搬。

**3. [近3月] TLA-Prover — A**
- 定位：以 TLC 验证器为奖励、偏好优化的 20B TLA+ 规格合成模型。
- 核心贡献：SFT + 以 TLC 为奖励的 GRPO 训练，模型可自修复被拒规范；在 30 题 held-out 基准上 Gold/Diamond 达 30%，约为未调优基线 3.5 倍。关键结论："验证器作为奖励"能显著提升可验证规格的生成质量。
- 采用建议："验证器即奖励"训练范式可直接迁移到我们 Spec 语言配套模型的训练管线。

**4. [近3月] LiveFMBench — A**
- 定位：首个防污染的 C 程序 ACSL 规范生成基准，系统对比 LLM 直推与智能体工作流。
- 核心贡献：构建 630 个可验证程序（含 360 个新采集以缓解数据泄漏）；对比直推与 agentic 工作流；数据集托管于 fm-universe 生态。关键结论：智能体工作流与验证反馈对规范生成有实质增益，防污染设计可复用。
- 采用建议：与 fm-universe 生态直接衔接，其防污染基准与智能体工作流评估可直接借鉴。

**5. [2026] Doc2Spec — B**
- 定位：用 LLM 从自然语言规则自动归纳规范文法、并据此生成形式化规格的多智能体框架。
- 核心贡献：多智能体先归纳规范文法再生成规格；在 7 个基准、3 种编程语言上优于无文法归纳基线，逼近手工文法效果。关键结论：显式文法归纳能提升生成规格的结构正确性。
- 采用建议：文法归纳思路可借鉴以约束我们 Spec 语言的生成结构，但方法较专、非本子方向核心。

**6. [近3月] LLM2Alloy — B**
- 定位：探索用 LLM 从需求文档与生产代码生成 Alloy 规格并派生可执行测试的探索性研究。
- 核心贡献：在 Flipper、Cerberus 两个开源 Python 库上评估 LLM 生成 Alloy 规格并派生测试，探讨"规格→测试"自动化链路。关键结论：LLM 生成的 Alloy 规格可用于测试派生，但质量仍需验证。
- 采用建议："NL→Alloy→测试"链路与规格驱动测试思路可借鉴，但属探索性、Alloy 特定。

**7. [重大] From Informal to Formal — A**
- 定位：蒸馏 gpt-4o 构建覆盖 5 种形式化语言指令数据并微调开源 LLM 的奠基工作，fm-universe 模型家族源头。
- 核心贡献：构建 18k 条覆盖 Coq/Lean4/Dafny/ACSL/TLA+ 的指令数据；评估 10 个开源 LLM；微调模型发布于 fm-universe。关键结论：多语言形式化规格指令微调可行，提供了可复用的数据与模型资产。
- 采用建议：fm-universe 是我们工具链的直接依赖，其数据构建与微调方法可直接复用。

**8. [重大] nl2spec — A**
- 定位：用 LLM 将非结构化自然语言交互式翻译为时序逻辑规格的开创性工作（TACAS 2023）。
- 核心贡献：提出"子公式↔自然语言片段"映射，通过交互式对话检测并消解需求歧义。关键结论：交互式歧义消解是"人类精确表达意图"的关键机制。
- 采用建议：其交互式歧义消解机制正是我们 Spec 语言"人类精确表达"诉求的直接答案，虽工具停更但方法论必读。

**9. [重大] nl2postcond — A**
- 定位：用 LLM 将自然语言意图转为可编程检查的方法后置条件断言（微软研究院主导）。
- 核心贡献：定义 nl2postcond 问题；生成的断言可捕获 Defects4J 中 64 个真实历史 bug；提供工业验证视角。关键结论：后置条件断言是"机器可执行验证契约"的轻量落地形态。
- 采用建议：后置条件断言形态与"可执行验证"直接契合，其问题定义与评估方法可直接采用。

**10. [2026] NL2LTL-SecDev26 — B**
- 定位：系统评估 LLM 在 6 类 NL→LTL 任务 × 3 种提示策略下表现的研究。
- 核心贡献：核心结论"语法易、语义难"——LLM 易学 LTL 语法，但语义正确性必须靠模型检验（NuSMV）验证。关键结论：语义验证闭环不可省略。
- 采用建议："语法易、语义难"是重要设计原则，但属确认性评测，方法与 #1/#2 重叠。

**11. [参考] On the Effectiveness of LLMs in Writing Alloy Formulas — C**
- 定位：受控实验评估 LLM 从自然语言写完整 Alloy 公式、生成等价公式及补全 Alloy sketch 的能力。
- 核心贡献：系统测量 LLM 在 Alloy 公式生成三类任务上的能力边界。
- 仅参考原因：Alloy 特定且结论与主流评测一致，无新增可采用的机制。

**12. [参考] A Short Survey on Formalising Software Requirements using LLMs — C**
- 定位：汇总 35 篇用 LLM 辅助编写形式化规格关键论文的聚焦综述（VERIFAI 项目）。
- 核心贡献：梳理 LLM 形式化规格化（Dafny/C/Java）的研究脉络与关键文献。
- 仅参考原因：综述用于补全文献地图，无可直接采用的机制或工具。

### B. NL→时序逻辑基准与评测

**13. [参考] VLTL-Bench — B**
- 定位：含数千条 NL-LTL 配对与样本轨迹的统一 NL→LTL 可验证性评测基准。

- 采用建议：其"可验证性"评测口径与样本轨迹设计可借鉴到我们 Spec 的评测基准。

**14. [参考] Grammar-Forced Translation of NL to Temporal Logic — B**

### C. Design by Contract / assume-guarantee / contract-based design

**15. [重大] Applying "Design by Contract" — A**

- 采用建议：我们 Spec 语言的契约语义（pre/post/invariant）直接源自此文，是语言设计的理论根基。

**16. [重大] Pacti — A**
- 定位：assume-guarantee 契约代数工具，用于高效组合式系统分析与设计。
- 核心贡献：提供契约组合/细化/一致性检查的代数运算；当前契约式设计的活跃工具。
- 采用建议：其 A/G 契约代数可直接作为我们 Spec 语言组合式契约语义的参考实现。

**17. [参考] A Boolean algebra of contracts — C**
- 定位：为 assume-guarantee 推理建立契约布尔代数理论（INRIA, 2008）。
- 核心贡献：给出契约运算（组合、精化、一致性）的代数公理化。
- 仅参考原因：纯理论公理化，为契约代数提供数学基础但无工程可采。

**18. [参考] CONDEnSe — C**

# 02 Don't-Care 区与未定义自由

> 子问题：Spec 如何表达"未定义即自由"，并避免无限膨胀？

## 一、论文（32 篇）

### A. 代数规范与宽松语义（Loose Semantics / Underspecification）— 理论根基

**1. [重大] CASL — A**
- 定位：提出"一个规格对应一族模型"的宽松（loose）语义，是"未定义即自由"在代数规范中的标准表达。
- 核心贡献：CASL 的宽松语义允许一个规格拥有多个不同实现模型，未约束的部分自动成为自由选择。论文给出了完整的语义定义和证明理论，为"未定义即自由"提供了最精确的数学语义模型。
- 采用建议：可直接采用其"规格=一族模型"的语义模型作为 Spec 语言的数学基础。

**2. [重大] Foundations of Algebraic Specification and Formal Software Development — A**
- 定位：代数规格理论的集大成专著，系统阐述模型类语义与精化理论。
- 核心贡献：系统总结签名、公理、模型类语义、结构规格（union/translate/hide/derive）和逐步精化。精化关系中"一个规格的各实现可以走不同路径"即"未定义即自由"在开发过程中的体现。
- 采用建议：可直接采用其精化理论（refinement calculus）与结构规格操作符来设计 Spec 语言的模块化组合机制。

**3. [参考] On the role of nondeterminism and refinement — B**
- 定位：区分"固有非确定性"与"欠规格化（underspecification）"两类非确定性，并讨论其在逐步精化中的角色。
- 核心贡献：前者不可消除，后者在精化中逐步消解。这一区分为 Spec 语言中"何种自由是可保留的"提供了分类学。
- 采用建议：可直接借鉴到 Spec 语言中设计"显式区分某一非确定性是固有还是欠规格"的语法标记。

### B. 抽象状态机（Abstract State Machine / Evolving Algebras）

**4. [重大] Evolving Algebras — B**
- 定位：提出演化代数（ASM），用"抽象状态+状态转换规则"在任意抽象层次建模，天然支持未指定即自由。
- 核心贡献：Gurevich 提出 ASM 方法，未约束的状态分量自动保持自由，允许从极高抽象到具体实现的逐步精化。ASM 论题主张"任何算法都能在适当抽象层次上被 ASM 模拟"。
- 采用建议：ASM 的"抽象层次自由"理念值得借鉴，其状态转换模型可作为 Spec 语言的执行语义基座，但整体方法论偏建模而非 Spec 语言设计，直接采用成本较高。

**5. [参考] The Abstract State Machines Method — C**
- 定位：ASM 方法的近期综述文章，涵盖 Gurevich 新论题到行为理论的发展。
- 核心贡献：综述 ASM 方法从奠基到现代的发展脉络，说明 ASM 如何在任意抽象层次描述算法。
- 仅参考原因：综述性质，无针对本子问题的新增贡献。

### C. 未定义行为的形式化（Undefined Behavior Formalization）— "未定义"的显式建模

**6. [重大] Defining the Undefinedness of C — A**
- 定位：用 K 框架给出可执行 C 语义，将 77 种核心未定义行为显式建模为语义卡死（stuck）。
- 核心贡献：将"未定义"建模为执行到某状态后无下一步规则可匹配（即 stuck state）。未定义不是错误值，而是语义层面的"无路可走"。验证了 7000+ 测试用例，覆盖 C11 标准。
- 采用建议：可直接采用"未定义=语义卡死"的建模策略，在 Spec 语言中为 don't-care 区域提供可执行的语义边界——超过规格约束范围即 stuck。

**7. [参考] Educational Undefined Behavior Technical Report — B**
- 定位：C 标准委员会对未定义行为（UB）的官方解释文档。
- 核心贡献：WG14 文档 n3308 给出 UB 的权威定义——"标准对该构造不施加任何要求"，即"未定义即自由"的官方标准表述。解释了 UB/unspecified behavior/implementation-defined behavior 三者的层次关系。
- 采用建议：可作为 Spec 语言设计文档中"未定义"语义的引用锚点。

**8. [参考] A Typed C11 Semantics for Interactive Theorem Proving — B**
- 定位：在 Coq 中形式化 C11 语义（CH2O 项目），将未定义/未指定行为建模为卡死或任意选择。
- 核心贡献：将未定义行为建模为"卡死"（no transition），将未指定行为建模为"任意选择"（nondeterministic choice）。
- 采用建议：提供了"未定义=卡死，未指定=任意"的双轨建模模式，可借鉴到 Spec 语言中区分"禁止行为"与"自由选择"的语义设计。

### D. Assume-Guarantee / 契约式设计 — "把未定义留给环境"

**9. [重大] Interface Automata — A**
- 定位：用"输入假设/输出保证"刻画组件交互，采用乐观组合与交替式精化，把环境行为留给假设而非规格。
- 核心贡献：组件接口声明"输入假设"和"输出保证"；组合采用乐观原则；交替式精化允许在接口层面精化。这直接回答了"如何把未定义留给环境"——环境行为由假设描述，规格不必定义。
- 采用建议：A/G 契约的奠基性理论，"假设-保证"分离策略可直接采用到 Spec 语言的接口声明中，让 don't-care 通过假设机制自动委托给环境。

**10. [重大] Specification and Design of (Parallel) Programs — B**
- 定位：rely/guarantee 方法奠基之作，用"依赖条件"描述环境干扰，是 assume-guarantee 思想的源头。
- 核心贡献：引入"依赖条件"（rely condition）描述环境对共享变量的干扰，用"保证条件"（guarantee condition）描述组件自身行为。通过 rely 条件将"未定义"的环境行为显式声明为假设。
- 采用建议：更偏并发程序验证而非 Spec 语言设计本身。其"rely 条件"机制可借鉴但需适配。

**11. [参考] Assume-Guarantee Verification for Interface Automata — B**
- 定位：给出接口自动机首个可靠且完备的 assume-guarantee 推理规则（兼容性/安全/精化）。
- 核心贡献：在接口自动机框架下给出了 A/G 推理规则的形式化定义，证明了可靠性与完备性。
- 采用建议：A/G 推理规则的形式化证明可作为 Spec 语言验证后端的设计参考，但偏推理逻辑而非语言设计。

**12. [2024] Composition and Merging of Assume-Guarantee Contracts Are Tensor Products — B**
- 定位：用张量积刻画 A/G 契约的组合与合并，契约的"环境假设"正是把未定义部分留给环境。
- 核心贡献：将 A/G 契约的组合与合并操作统一建模为张量积运算，契约的"环境假设"部分精确对应"未定义给环境"的语义。
- 采用建议：张量积视角提供了契约组合的数学优雅性，可作为 Spec 语言中契约组合语义的形式化工具，但偏理论而非工程采用。

**13. [参考] Assume/Guarantee Contracts for Dynamical Systems — C**
- 定位：把 A/G 契约推广到动力系统领域，假设-保证分离使规格不必定义环境行为。
- 核心贡献：将 A/G 契约从软件系统推广到连续/混合动力系统。
- 仅参考原因：偏动力系统领域，与软件 Spec 语言设计关系较远。

### E. 部分函数与未定义项的逻辑（Partial Functions / Free Logic / LPF）

**14. [参考] Free Logic — B**
- 定位：自由逻辑允许非指称项（无指称的表达式），是"未定义项"的形式逻辑基础。
- 核心贡献：传统一阶逻辑要求所有项都有指称，自由逻辑允许项无指称（即未定义项），同时保持量词和等词的良好行为。
- 采用建议：为 Spec 语言中允许部分未定义项提供了逻辑基础，但其纯逻辑表述需要工程化适配。

**15. [参考] A Semantic Analysis of Logics that Cope with Partial Terms — B**
- 定位：LPF（部分函数逻辑）把未定义处理为"空洞"（absence of value）而非具体错误值。
- 核心贡献：将未定义项视为"值的缺失"而非某种特殊错误值，并给出相应真值表（三值逻辑）。这种"空洞"语义使得未定义项不会污染整个表达式的求值。
- 采用建议：LPF 的"空洞"语义可作为 Spec 语言中 don't-care 表达式的逻辑语义基础，避免"未定义传播"问题。

### F. Z 与部分规格 / 精化（Partial Specification in Z / Refinement）

**16. [参考] Consistency and refinement for partial specification in Z — B**
- 定位：用"最小公共精化（unification）"检查多视角部分规格的一致性，部分规格允许省略不关心的行为。
- 核心贡献：多视角部分规格的一致性通过"最小公共精化"来检查——如果存在一个共同的精化则一致。
- 采用建议："最小公共精化"可作为 Spec 语言中多视角 don't-care 规格一致性检查的计算模型。

**17. [参考] Guards, Preconditions, and Refinement in Z — B**
- 定位：把 Z 操作在前置条件域外的行为建模为"任意结果"或"阻塞"，统一表达拒绝与欠规格化。
- 核心贡献：讨论前置条件域外的语义选择——"任意结果"（自由选择，对应欠规格化）或"阻塞"（拒绝执行，对应严格前置条件）。
- 采用建议："域外即自由 vs 域外即阻塞"的语义选择对 Spec 语言设计至关重要——Spec 语言需要明确提供这两种模式供规格编写者选择。

### G. Liveness vs Safety — "规格该约束什么"

**18. [重大] Defining Liveness — A**
- 定位：给出 safety/liveness 的形式定义并证明任何性质=安全∩活性，为"规格该约束什么"提供分类学基础。
- 核心贡献：给出 safety（"坏事不会发生"）和 liveness（"好事终将发生"）的拓扑学定义，并证明任何时序性质都可分解为安全性质和活性性质的合取。超出这两个范畴的约束是不必要的，从而"避免无限膨胀"。
- 采用建议：直接将 safety/liveness 分类学作为 Spec 语言的核心约束原则——spec 只要求声明 safety 和 liveness 性质，其余一切自动视为 don't-care。

### H. 时序逻辑与"不要过度约束"（TLA+）

**19. [重大] Specifying Systems: The TLA+ Language and Tools — A**
- 定位：TLA+ 权威著作，规格即"允许行为集合"，未约束的即自由。
- 核心贡献：系统阐述"规格=允许行为集合"的核心哲学。TLA+ 规格描述系统允许的所有行为轨迹，未在规格中声明的行为自动不被禁止。书中给出了完整的 TLA+ 语言定义、TLC 模型检查原理和实际案例。
- 采用建议：TLA+ 的"允许行为集合"语义是本子问题最直接的工程化方案，可大幅借鉴其设计哲学、语法模式和模型检查验证策略。

### I. 非确定性与语义（Nondeterminism / Omnisemantics）

**20. [重大] Omnisemantics — B**
- 定位：用"起始状态→结果集合"的 omni 风格判断优雅处理操作语义中的非确定性。
- 核心贡献：将传统操作语义的"单值判断"推广为"起始状态→所有可能结果集合"，使非确定性在元语言层面不再需要显式调度。omni 风格判断直接支持 don't-care 语义——如果某输入在规格中未被约束，它出现在结果集合中即合法。
- 采用建议：提供了非确定性语义的现代框架，可作为 Spec 语言的非确定性执行语义基础，但偏语义框架而非 Spec 语言设计本身。

**21. [参考] Refining UML Interactions with Underspecification and Nondeterminism — B**
- 定位：区分欠规格化与固有非确定性，并定义相应精化关系。
- 核心贡献：在 UML 交互图背景下区分"欠规格化"（实现只需满足其一）与"固有非确定性"（行为不可预测），并分别定义精化关系。
- 采用建议：该区分的概念框架与 #3 互补，可参考其精化关系的定义方式。

### J. Don't-Care 条件（硬件/逻辑综合）— 概念源头

**22. [重大] Don't Care Set Specifications in Combinational and Synchronous Logic Circuits — A**
- 定位：组合与时序逻辑中 don't-care 条件规格与计算的统一框架，don't-care 即优化自由度。
- 核心贡献：给出硬件逻辑综合中 don't-care 条件的统一计算方法，包括可满足性 don't-care（SDC）和可观测性 don't-care（ODC）。don't-care 条件被定义为"输出不受输入组合影响的自由度"。
- 采用建议："Don't-Care"术语的源头定义，其 SDC/ODC 分类可直接映射到 Spec 语言的"不可达状态 don't-care"与"可忽略输出 don't-care"两类 don't-care 声明。

### K. 未指定项语义（ACSL / 规格语言）

**23. [2024] A Semantics of Structures, Unions, and Underspecified Terms — B**
- 定位：给 ACSL 中未指定（underspecified）项以"良定义但欠规格"的语义，基于 Krebbers 的 C 语义。
- 核心贡献：为"未指定项"——有明确语法但语义未完全确定的表达式——给出"良定义（well-defined）但欠规格（underspecified）"的语义。未指定项不是语法错误，也不是完全未定义，而是在多个合法值之间自由选择。
- 采用建议：提供了在现有规格语言中处理未指定项的具体案例，可借鉴其"良定义但欠规格"的语义设计，但偏 ACSL 特定语言细节。

### L. 新增（2026 年，近三月为主）— 欠规格化与精化的最新进展

**24. [近3月] Verifiable Auto-Formalization of Mathematics Using a Relaxed Natural Formal Language — A**
- 定位：提出"宽松自然形式语言（Relaxed NFL）"作为自动形式化中间层，明确允许"部分指定的表达式与命题"（partial specification），把歧义/隐含解析推迟到后续 elaboration 阶段。
- 核心贡献：与"未定义即自由"直接呼应——明确允许部分指定，将歧义和隐含信息推迟到 elaboration 阶段处理。在 Lean 中验证了 100+ 数学定理，证明"部分指定+延迟解析"的可行性。
- 采用建议：直接回答"如何显式声明未定义即自由"——通过"部分指定+延迟解析"策略。其 elaboration 机制可直接借鉴到 Spec 语言设计中，作为"从宽松规格到精确实现"的桥梁。

**25. [近3月] Combining Axiomatic Models for Refinement Proofs — B**
- 定位：统一 Hoare / Incorrectness / Lisbon / Necessary-Preconditions 四种公理逻辑，用 forward/backward simulation 刻画并传递 refinement proof 中的安全性质。
- 核心贡献：统一了四种公理逻辑推理框架，用 forward/backward simulation 关系在 refinement proof 中传递安全性质。
- 采用建议：与 refinement freedom 相关，但更偏验证逻辑的扩展而非 Spec 语言设计本身。其 unification 思路可作为验证后端的设计参考。

**26. [近3月] Neurosymbolic Auditing of Natural-Language Software Requirements（VERIMED）— B**
- 定位：LLM+SMT 审计自然语言需求的歧义、不一致、真空（vacuousness）与欠规格化（underspecification），用随机形式化差异作为歧义信号。
- 核心贡献：用 LLM 将自然语言需求转化为形式化断言，再用 SMT 求解器检查不一致性。核心创新是用"随机形式化差异"作为欠规格化和歧义的检测信号。
- 采用建议：提供了"未定义即自由"的审计/检测工具思路。可借鉴其"随机形式化差异"方法作为 Spec 语言编辑器的实时光标——提示用户哪些部分可能欠规格化。

**27. [2026] SpecRL — B**
- 定位：针对"弱规格如 ensures true 过于宽松"（即 don't-care/loose semantics 过度宽松的问题），用负测试完备性奖励在 Dafny 中排序规格候选。
- 核心贡献：核心创新是"负测试完备性奖励"——如果规格太弱（如 ensures true），测试用例全部通过，但完备性奖励低，从而排序靠后。直接回应"避免规格无限膨胀/过度宽松"。
- 采用建议：方法偏 ML 辅助规格合成而非 Spec 语言设计本身。可借鉴其"完备性奖励"思路作为 Spec 语言的质量度量标准。

**28. [2026] Intent-aligned Formal Specification Synthesis via Traceable Refinement（VeriSpecGen）— C**
- 定位：在 Lean 中通过需求级归因与局部修复做可追溯精化的规格合成（Verina SpecGen 基准上 86.6%）。
- 核心贡献：核心创新是"需求级归因"——将规格需求追溯回原始需求文档，并在需求变更时做局部修复。
- 仅参考原因：偏规格合成和 LLM 驱动的规格生成，不直接回答"未定义即自由"的表达与验证问题。

**29. [2026] What Prompts Don't Say — C**
- 定位：系统分析 LLM 提示词中欠规格化（underspecification）的实证研究。
- 核心贡献：发现未指定需求常被 LLM 默认推断（41.1%）但极其脆弱，跨模型/提示词变化时回归率高达 2 倍。说明"未定义"需要被显式声明而非隐式假设。

**30. [2026] Lenses for Partially-Specified States — B**

- 核心贡献：在双向变换（bidirectional transformation）的 lens 框架中引入部分指定状态，用偏序关系合并来自多个视图的更新意图。
- 采用建议：对"部分指定"的形式化有参考价值，特别是偏序合并多视图更新意图的机制可借鉴到 Spec 语言中多视角 don't-care 规格的合并。

**31. [近3月] ConVer — C**

- 核心贡献：使用 LLM 从高层系统性质自动合成函数级契约，在 CEGAR-CEGIS 循环中通过 SMART ICE 技术逐步细化契约。
- 仅参考原因：偏验证工具链和契约合成，不直接回答"未定义即自由"的表达与验证问题。

**32. [2026] SpecSyn — C**

- 仅参考原因：偏规格合成而非本子问题核心，不直接回答"未定义即自由"的表达与验证。

## 二、开源项目（9 个）

**3. Why3 — A**
- 定位：程序验证平台，WhyML 规格语言对接多个 SMT/证明器，支撑 Frama-C、SPARK 等验证工具的后端。
- 核心贡献：WhyML 同时是规格语言和编程语言，支持前置/后置条件、不变式等。其验证条件生成器（VCGen）将规格验证转化为 SMT 可解问题，对接 Z3、CVC4/5、Alt-Ergo 等。在未指定部分，验证器会检查"在所有合法实现中性质是否成立"。
- 采用建议：Why3 的 VCGen 架构和验证后端对接多个 SMT 的策略可直接采用到 Spec 语言的验证工具链中，其"在所有合法模型中验证"的思路与 don't-care 语义天然契合。

**4. ASMETA（Asmeta）— B**
- 定位：ASM 工具集，含 AsmetaL 编辑器/编译器、模拟器、模型检查器、精化证明器。
- 核心贡献：包括 AsmetaL 语言、AsmetaS 模拟器、AsmetaSMV（基于 NuSMV 的模型检查器）、AsmRefProver（精化证明器，验证抽象→具体步骤的正确性）。
- 采用建议：直接支持 ASM 的逐步精化与未指定建模，但其建模范式偏软件工程建模而非 Spec 语言设计，可作为精化证明器的参考实现。

**5. Pacti — B**
- 定位：可扩展的契约式组合分析与设计工具，实现 assume-guarantee 契约的合并/组合/refinement 等操作。
- 核心贡献：提供契约的合并（merge）、组合（composition）、精化（refinement）等操作的高效算法实现。
- 采用建议：A/G 契约的操作化工具，可作为 Spec 语言中契约操作的参考实现，但偏工具而非语言设计本身。

**6. Hets — C**
- 定位：异构规格工具集，支持 CASL/HetCASL 及多逻辑（Isabelle、Maude、OWL 等）。
- 核心贡献：CASL 宽松语义的主要工具实现，支持多逻辑规格的解析、类型检查、证明和模型检查。但近一年基本停滞。
- 仅参考原因：虽然 CASL 语义有价值，但工具已停滞，不建议作为原型基础。

**7. CafeOBJ — C**
- 定位：宽松语义与执行语义结合的代数规格语言，仓库约 1.5 年未动。
- 核心贡献：将宽松语义（多个模型）与执行语义（可执行）结合，支持等式推理和重写。但已停更。
- 仅参考原因：已停更，不建议作为原型基础。

**8. CH2O — C**
- 定位：Coq 中形式化的 ISO C11 语义，未定义/未指定行为形式化的基准项目。
- 核心贡献：在 Coq 中完成了 C11 的完整形式化语义，将未定义行为建模为卡死，未指定行为建模为任意选择。但最近提交已是 2022 年。
- 仅参考原因：已停滞，但其"未定义=卡死，未指定=任意"的语义设计仍可作为参考。

**9. K framework c-semantics — C**
- 定位：K 框架中的 C 语义开源实现（与论文 #6 配套），继任者为商业工具 RV-Match。
- 核心贡献：将 C 语言的未定义行为建模为 K 框架中的 stuck state。但开源版已停滞。
- 仅参考原因：开源版已停滞，商业替代品不可自由使用。

## 三、File 02 关键结论

**最优设计骨架（五支柱）**：CASL 宽松语义（语义模型）+ TLA+ 允许行为集合（工程化表达）+ Alpern-Schneider safety/liveness 分类学（约束范围决策）+ Interface Automata 假设-保证分离（未定义委托机制）+ Relaxed NFL 部分指定+延迟解析（工程化策略）。近三个月出现一批直接处理"欠规格化"的新工作（Relaxed NFL、VERIMED、SpecRL），说明"未定义即自由"正从理论走向 LLM 时代的工具化。

# 03 Spec 版本化与增量演化

> 子问题：如何管理 Spec 的变更历史，并确保向后兼容性（尤其针对 R2/R3 级制品）？

## 一、论文 / 标准（23 项）

### A. API / 契约版本化与向后兼容（OpenAPI / AsyncAPI / SemVer）

**1. [重大] How Many Web APIs Evolve Following Semantic Versioning? — B**
- 定位：对 3,075 个 Web API 演化历史做的大规模实证，检验版本号是否真按 SemVer 规则演进。
- 核心贡献：发现现实中 SemVer 大多不被遵守（最坏情形仅 25% 合规）；揭示"版本号语义"与"实际破坏性变更"严重脱节，证明仅靠人工遵守 SemVer 约定无法保证向后兼容。这是本子问题最关键的**反面实证**：兼容性必须由机器可执行的检查来保证，而不能依赖开发者自律。
- 采用建议：不直接提供机制，但为"为何需要形式化/自动化的兼容性验证"提供了最强动机，是设计决策的重要依据。

**2. [重大] A First Look at the Deprecation of RESTful APIs（RADA）— B**
- 定位：提出 RADA 框架，从 OpenAPI 规格自动识别 deprecated 元素并实证研究 deprecated→removed 协议执行情况。
- 核心贡献：将"弃用（deprecation）"从文档注释提升为可从规范中自动检测的结构化元素；实证揭示 API 的弃用-移除协议在实际中执行不力。
- 采用建议：deprecation 状态机可直接借鉴进我们的 Spec 语言（把"deprecated→removed"建模为语言级一等概念），但 RADA 本身偏检测工具而非语言设计。

**3. [参考] To deprecate or to simply drop operations? — C**
- 定位：基于百万级 OpenAPI/Swagger 操作，实证研究 API 演化中 operation 删除造成的 breaking changes 及 deprecation 使用程度。
- 核心贡献：在更大规模上量化"直接删除 vs 先弃用再删除"两种演化路径的破坏性差异。
- 仅参考原因：与 #2 主题高度重叠、纯实证补充，对 Spec 语言设计无新增可操作机制。

**4. [参考] How Composable is the Web? — C**
- 定位：对 20,587 个公开 Web API 的 schema 兼容性实证研究，定义三级数据模型元素兼容性。
- 核心贡献：提出数据模型元素的三级兼容性分类（可用于判断 schema 变更是否破坏兼容）。
- 仅参考原因：兼容性分类学有一定启发，但停留在实证描述层面，未提供可执行的兼容性判定机制。

**5. [参考] A Formal Study on Backward Compatible Dynamic Software Updates — C**
- 定位：形式化研究动态软件更新（DSU）场景下的向后兼容性。
- 核心贡献：用"混合执行满足规格 Σ"刻画兼容条件，为向后兼容给出形式化定义。
- 仅参考原因：面向运行时动态更新（DSU）而非 Spec 制品版本化，场景距离远且年代较早（2015）。

### B. 形式化规格演化与细化（TLA+ / Event-B / B 方法）

**6. [重大] Specification and Verification With the TLA+ Trifecta — A**
- 定位：TLA+ 三件套（TLC 模型检查 / Apalache 符号验证 / TLAPS 证明）的权威综述。
- 核心贡献：系统论述 TLA+ 中 **refinement 即逻辑蕴含（Spec ⇒ TD!Spec）**——新版本规格若蕴含旧版本规格，则向后兼容得到机器可验证的保证。这是"规格演化验证"最核心的形式化机制：把"向后兼容"从约定问题转化为可证明的定理。
- 采用建议：可直接把"refinement-as-implication"作为我们 Spec 语言版本化验证的语义内核，直接回答"如何机器验证新版本向后兼容旧版本"。

**7. [重大] Leveraging TLA+ Specifications to Improve the Reliability of the ZooKeeper — B**
- 定位：TLA+ 分层规格支撑 ZooKeeper 开发的工业案例。
- 核心贡献：展示规格作为"super-doc"在真实分布式系统中的演化与复用；通过"系统规格→测试规格"的分层结构，证明规格可以随系统演进持续维护并保持可验证性。
- 采用建议：工业案例强有力地证明"规格可演化且值得演化"，分层规格思想可借鉴，但具体机制（TLA+ 生态绑定）对语言设计借鉴有限。

**8. [参考] Consistency-preserving refactoring of refinement structures in Event-B — C**
- 定位：保持一致性的事件 B 细化结构重构方法。
- 核心贡献：提出在重构 Event-B 细化结构时保持一致性（不破坏既有证明/细化关系）的方法。
- 仅参考原因：偏"重构既有细化结构"的维护性课题，且绑定 Event-B 工具链，与我们的版本化/兼容性设计契合度低。

### C. 模型 / 元模型版本化与共演化（MDE）

**9. [重大] Approaches to Co-Evolution of Metamodels and Models: A Survey — A**
- 定位：综述 31 种元模型-模型共演化方法的权威调查。
- 核心贡献：系统梳理 31 种共演化方法，给出解决方案技术分类学（手动/操作化/转换式等）与决策支持框架。对 R3 级制品（元模型）变更后如何驱动 R2 级制品（模型）共演化，提供了完整的方案地图。
- 采用建议：直接回答"元模型变更后下层制品如何增量演化"——正是 R3→R2 级制品版本化管理的核心；分类学可直接指导我们选择共演化策略。

**10. [参考] COPE — C**
- 定位：COPE 语言，用可复用的耦合演化操作描述元模型与模型的同步演化。
- 核心贡献：提出"耦合演化操作"概念，把元模型变更与对应模型迁移封装为可复用操作。
- 仅参考原因：思想（可复用演化操作）有启发，但绑定 EMF/Eclipse 且年代较早（2008），已被 #9 的综述覆盖。

**11. [2024] "Don't Touch my Model!" — B**
- 定位：记录元模型历史版本并维护各版本模型，支持按需共演化的 ICSE NIER 工作。
- 核心贡献：提出"多版本并存"思路——保留元模型各历史版本及对应模型，避免强制一次性迁移，支持模型在不同时间点按需共演化。
- 采用建议：与"管理 Spec 变更历史"直接相关，其"多版本并存、按需迁移"策略对 R2/R3 级制品的版本管理有直接借鉴价值；但属 NIER 短论文，机制未成熟。

### D. 特性模型 / 产品线演化（Feature Model / SPL）

**12. [参考] Multi-Version Decision Propagation — C**
- 定位：支持跨多个特性模型版本同时进行配置的多版本决策传播方法。
- 核心贡献：解决特性模型多版本并存时的配置一致性问题，将配置决策在"空间（多产品）与时间（多版本）"上传播。
- 仅参考原因：面向特性模型的配置场景，与我们的 Spec 语言（R2/R3 制品）距离较远。

**13. [2025] Modular Soundness Checking of Feature Model Evolution Plans — C**
- 定位：对特性模型演化计划（FMEP）做模块化健全性检查。
- 核心贡献：形式化定义特性模型演化计划，并验证各时间点模型计算的正确性（健全性）。
- 仅参考原因："演化计划的健全性检查"思想有概念共鸣，但面向特性模型领域、与我们的工具链契合度低。

### E. 语言 / 规范版本化标准与草案（W3C / IETF / FHIR / OpenAPI / AsyncAPI）

**14. [重大] OpenAPI Specification 版本化（3.2.0 稳定 / 3.3.0 开发中 / 4.0 未落地）— A**
- 定位：OAS 采用 SemVer 2.0.0 版本化、major.minor 指定功能集的 API 契约规范版本化现状。
- 核心贡献：确认 OpenAPI 3.2.0（2025-09）为稳定版、实际开发在 3.3.0 轨道、4.0（Moonwalk）仍处设计阶段——主流 API 规范短期不会大版本跳跃。OAS 本身就是 R2 级契约制品的典型代表。
- 采用建议：作为我们 Spec 语言最直接的对标物，其"SemVer + 3.x 轨道渐进演进"的节奏与兼容性治理可直接借鉴。

**15. [重大] AsyncAPI 版本与迁移（3.1.0 于 2026-01-31 发布）— B**
- 定位：事件驱动 API 规范，v3 后首个新版本，标志走出 v3 后停滞期。
- 核心贡献：v3 将 operations/channels/messages 解耦是最大 breaking change；3.1.0 为 minor 发布、无破坏性变更，示范了"大版本重构 + minor 增量"的版本化节奏与迁移治理。
- 采用建议：事件驱动契约版本化的活跃参考，其"解耦式大重构 + 增量 minor"策略与迁移文档实践可借鉴；但事件驱动领域与我们的通用 Spec 语言契合度中等。

**16. [重大] YANG Module Versioning — B**
- 定位：允许 YANG 模块非线性多版本演化、用 revision date 唯一标识版本的 IETF 草案。
- 核心贡献：突破线性 SemVer 局限，支持同一模块多版本并存（非线性演化），以 revision date 作为版本唯一标识——更贴近复杂制品的真实演化形态。
- 采用建议："非线性多版本演化 + 时间戳标识"对 R2/R3 级制品（尤其元模型/特性模型）的版本管理有直接借鉴价值，是比纯 SemVer 更先进的版本模型；但 YANG 领域绑定使其机制需自行迁移。

**17. [重大] YANG Semver — A**
- 定位：为 YANG 制品引入 SemVer 风格版本号并标注向后兼容（BC）/不兼容（NBC）变更的 IETF 草案。
- 核心贡献：将"兼容性语义"编码进版本号（BC/NBC 标注），使版本号本身携带机器可读的兼容性信息——这是"版本号编码兼容性语义"的成熟标准做法，与本子问题核心直接对应。
- 采用建议：直接回答"如何让版本号承载兼容性语义、供机器判定"——可把 BC/NBC 标注机制直接纳入我们的 Spec 语言版本模型。

**18. [重大] FHIR Versions — B**
- 定位：定义 FHIR 制品达到 Normative 状态后的前后向兼容规则的医疗领域规格治理。
- 核心贡献：以严格的兼容性治理保证跨版本数据交换安全，示范了"制品成熟度（Normative 状态）决定兼容性义务"的分级治理模式。
- 采用建议："按制品成熟度分级施加兼容性义务"的治理思想可借鉴（与我们 R2/R3 分级天然呼应），但 FHIR 偏组织/流程治理，形式化机制有限。

**19. [参考] Extending and Versioning Languages Part 1（W3C TAG）— C**
- 定位：定义语言可扩展性、向后/向前兼容性语义的 W3C TAG 概念框架文档。
- 核心贡献：为语言规范版本化提供概念框架（可扩展性、向前/向后兼容的定义与分类）。
- 仅参考原因：纯概念性框架、无具体机制且长期未更新，仅作为术语与分类的背景资料。

### F. 新增（2026 年）— LLM 与 API/契约演化的交叉

**20. [2026] When LLMs Lag Behind — B**
- 定位：系统实证研究 LLM 在 API 演化（弃用/修改/新增）下的代码生成"上下文-记忆冲突"问题。
- 核心贡献：揭示 LLM 训练数据中的旧契约会与最新规格冲突，导致生成代码基于过期 API 知识；对"LLM 辅助 Spec 编写/验证"路线提出警示。
- 采用建议：若我们的工具链引入 LLM 辅助 Spec 生成，本工作直接提示"必须用最新版本化 Spec 约束 LLM 输出"，有警示与设计约束价值。

**21. [2026] KCoEvo — B**
- 定位：构建 API 演化知识图谱辅助 LLM 生成跨版本一致代码的框架。
- 核心贡献：用知识图谱显式建模 API 版本间演化关系（add/remove/update），辅助 LLM 处理版本化约束。
- 采用建议："用图谱显式建模版本间变更关系"可借鉴到我们的 Spec 变更历史管理（把变更历史组织为可查询的演化图谱）；但偏代码生成应用。

**22. [参考] APIMig — C**
- 定位：基于演化知识图谱的跨多版本 API 迁移框架（IJCAI 2025）。
- 核心贡献：提取 add/remove/update 演化实体，支撑项目级跨多版本 API 迁移。
- 仅参考原因：与 #21 主题重叠且偏"迁移工具"应用，对 Spec 语言版本化设计无新增机制。

**23. [近3月] When Retrieval Hurts Code Completion — C**
- 定位：诊断研究检索到的过期仓库上下文对代码生成的负面影响。
- 核心贡献：实证"陈旧上下文"（含过期规范/契约）会损害代码生成质量。
- 仅参考原因：面向检索增强生成（RAG）场景的负面诊断，与 Spec 版本化/兼容性设计距离较远。

## 二、开源项目（10 个）

**1. oasdiff — A**
- 定位：Go 编写的 OpenAPI diff 与 breaking change 检测 CLI。
- 核心贡献：覆盖 509 种变更类型，支持本地、CI 与 PR review，是当前 OpenAPI 破坏性变更检测的事实标准工具（Optic 归档后成为主要替代）。
- 采用建议：可直接采用——其"变更分类 + 破坏性判定"正是"机器可执行验证向后兼容"的现成实现，可作为我们 Spec 语言兼容性检查工具链的基础。

**2. Azure/openapi-diff (oad) — A**
- 定位：npm 包，Azure REST API Specs 的 Breaking change detector。
- 核心贡献：在 azure-rest-api-specs 仓库中每个 PR 强制执行破坏性变更检测，示范了"版本化兼容性检查嵌入 CI/PR 流程"的工程实践。
- 采用建议："PR 强制检查"的 CI 集成模式可直接借鉴到我们的 Spec 版本化工作流。

**3. Pact（Pact 家族）— B**
- 定位：消费者驱动契约测试生态的事实标准。
- 核心贡献：Pact Broker 用 consumer version selectors 管理契约版本匹配，实现"契约随版本演化、消费者按版本选择匹配"的机制。
- 采用建议：契约测试生态的版本匹配机制（version selectors）对"Spec 版本与消费方兼容关系管理"有借鉴价值；但 Pact 偏运行时契约验证，非 Spec 语言设计本身。

**4. AsyncAPI（规范+生态）— B**
- 定位：事件驱动 API 规范及其迁移/变更治理生态。
- 核心贡献：3.1.0 发布并提供 v3 迁移指南，示范事件驱动契约的版本迁移与变更治理。
- 采用建议：与论文 #15 对应，作为事件驱动契约版本化的活跃参考与迁移实践样板。

**5. OpenAPI Specification — A**
- 定位：OAS 3.2.0 稳定、3.3.0 开发中、4.0（Moonwalk）设计阶段的 API 契约规范本体。
- 核心贡献：确认主流 API 规范在 3.x 轨道渐进演进、4.0 短期不落地，其版本化治理是直接对标对象。
- 采用建议：作为我们 Spec 语言最直接的对标与兼容目标，其版本化策略、变更治理与工具生态均可直接采用/对齐。

**6. api-changelog（lxgicstudios）— B**
- 定位：对比两个 OpenAPI/Swagger 文件生成人类可读 changelog 的轻量工具。
- 核心贡献：零外部依赖，自动检测新增/删除端点、必填字段、弃用等变更，输出人类可读变更日志。
- 采用建议："变更的机器检测 + 人类可读呈现"与"人类精确表达意图"目标相关，可作为 Spec 变更说明生成组件借鉴；但项目较新、成熟度有限。

**7. [剔除] Optic — C**
- 定位：曾是 OpenAPI 生态重要工具，2026 年 1 月归档死亡的 API 规范工具。

## 三、File 03 关键结论

**三大机制支柱（可直接采用，均为 A 档）**：TLA+ **refinement-as-implication**（#6，机器验证向后兼容的语义内核）+ **YANG Semver 的 BC/NBC 版本号编码**（#17，版本号携带兼容性语义）+ **oasdiff/Azure-openapi-diff 的机器化破坏性变更检测**（开源 1/2，兼容性检查的现成实现）。R3 级制品（元模型/模型）演化以 #9（共演化综述）为方案地图、#11（多版本并存）为策略参考。2026 新动向：OpenAPI 4.0 短期不落地（3.x 轨道演进）；Optic 归档、oasdiff 成事实标准；研究热点转向"LLM 与 API 演化知识冲突"（#20/#21）。

# 总评与设计启示

## 三大子问题的 A 档核心清单

| 子问题 | A 档核心条目 | 对 Spec 语言设计的直接启示 |
|---|---|---|
| 01 NL→形式化契约融合 | TLA+ 评测三件套、nl2spec、nl2postcond、From Informal to Formal、Design by Contract、Pacti、Daikon、fm-universe | 生成端必须接验证器闭环（"语法易、语义难"）；交互式歧义消解保证"人类精确表达"；契约语义（pre/post/invariant）为语言根基；不变量挖掘提供 L2 契约自动候选 |
| 02 Don't-Care 区与未定义自由 | CASL、Foundations of Algebraic Spec、Defining the Undefinedness of C、Interface Automata、Defining Liveness、TLA+ 专著、Don't Care Set Specs、Relaxed NFL、TLA+ 工具链、Why3 | "规格=一族模型/允许行为集合"为语义模型；safety/liveness 分类学决定约束范围；"未定义=卡死"提供可执行边界；假设-保证分离把未定义委托给环境；部分指定+延迟解析为工程化策略 |
| 03 Spec 版本化与增量演化 | TLA+ Trifecta（refinement-as-implication）、Co-Evolution Survey、YANG Semver、OpenAPI、oasdiff、Azure/openapi-diff | 用逻辑蕴含机器验证向后兼容；版本号编码 BC/NBC 兼容性语义；破坏性变更自动检测嵌入 CI/PR；元模型-模型共演化分类学指导 R3→R2 增量演化 |

## 全局共识

1. **验证器闭环不可省略**：File 01 多篇独立研究（NL2LTL-SecDev26、Can LLMs Write Correct TLA+、VLTL-Bench）一致表明 LLM 生成规格的语义正确率远低于句法正确率，必须依赖模型检验器（TLC/NuSMV/SANY）作为验证闭环。
2. **"未定义即自由"需显式声明**：File 02 从理论（宽松语义）到工程（Relaxed NFL、VERIMED、SpecRL）均指向——未定义区域必须被显式标记而非隐式假设，且要在"足够自由"与"避免过度宽松"之间取得平衡。
3. **向后兼容必须机器化**：File 03 的实证（SemVer 仅 25% 合规）证明兼容性不能依赖开发者自律，必须由 refinement 蕴含、版本号编码与自动 diff 检测共同保证。

## 建议的下一步

- 基于 A 档清单，可进一步为 Spec 语言设计产出：① 语法草案（融合契约语义 + don't-care 声明 + 版本化元数据）；② 验证后端选型（TLC/Why3/模型检验器）；③ 生成管线（fm-universe 模型 + 验证器奖励微调）；④ 评测基准（执行级打分 + correctness envelope 口径）。
